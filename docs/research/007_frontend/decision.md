## 我选择什么（草稿 → AI 已代拍，待人复核）

> **混合：Rust/Wasm 做壳、路由、状态与全部第一方业务 UI（框架选 Leptos）；xterm.js、CodeMirror、Univer、pdf.js 等「无对应物四件」保留为 JS 岛，经类型化桥接；按页面渐进替换，聊天面放最后。桌面端 Electron 本阶段一行不动。**

### (a) 要不要真的改成 Rust——三选项对比

| | 改成 Rust/Wasm（Leptos/Dioxus/Yew） | 保留 React、只换后端 | **混合：壳与状态 Rust、重组件留 JS 岛** |
|---|---|---|---|
| 与意向书「改成 Rust」的关系 | 完全符合 | 不符——「前端重构」名存实亡，只是阶段 A/B | 主体符合：第一方业务逻辑（≈12 万行里的绝大多数）Rust 化，例外只有无对应物的第三方件 |
| 风险 | 重写 xterm/CodeMirror/Univer：无成熟对应物（gap §四）、IME 是旧包点名的最高风险（`risks.csv:6`） | 最低 | 中：岛桥接与双技术栈共存期的工程纪律 |
| 对拍可判性 | 最难：像素级行为都要重造 | 现成（前端没变） | 可行：黑盒 e2e 35 例直接复用（gap §三），岛内行为不变 |
| 旧决策的连续性 | — | — | 与旧迁移包政策完全一致：第三方 JS 允许保留、第一方必须 Rust（`decisions.md:11`） |

**AI 代拍：混合（待人复核）。** 理由：① 意向书要求 Rust 且待人复核的是「改成 Rust」这个方向本身——混合是**保住方向**的同时不押注在「用 Rust 重写终端模拟器」这种无对应物、旧包评估两年都没人敢做的事上；② React 状态层有个自证的痛点——`WebSocketContext.tsx:21-28` 专门写了 `subscribe` 直通来绕开 React 状态批处理，细粒度响应式框架天然没有这类问题，说明状态层换 Rust 不是为换而换；③ 旧迁移包 P4 默认就是「Rust/Wasm UI + 待评估桌面」（`roadmap.md:11`），本卡等于接回那条线。

**框架 AI 代拍：Leptos（待人复核），回退条件写死。** 理由：① 内建 islands 架构，「Rust 壳挂 JS 岛」是官方路径而非自创；② 信号（细粒度响应式）直接对应「高频 `stream_delta` 不掉帧」这一旧代码补丁所指向的需求；③ 社区活跃度与文档在三候选中最优。**回退条件**：探针（计划 004 Issue F1）里若中文 IME（composer 组合键回车不发送，旧包 `contracts/ui.md:2` 的硬要求）或 stream_delta 高频更新任一不过关且 Leptos 侧无解，**换 Dioxus 重跑探针**，不硬扛；Yew 的回调式模型与 React hooks 迁移距离最远，不选。

### (b) 怎么渐进——按路由 / 按组件岛 / 整体

**AI 代拍：按页面（路由/Tab 粒度）切 + 页内组件岛（待人复核）。** 理由与顺序：

1. 应用是单通配路由（`App.tsx:50`），`AppShellV2.tsx:79-84` 按 URL 分辨页面——「按路由」的实质是**按页面**：`/settings/*`、`/cron`、`/skills`、`/sop`、`/knowledge` 等都是整页切换（跨页导航是整页加载，两套前端可经静态托管按路径前缀选 bundle 共存，不必 iframe）。
2. **顺序**：探针页（登录 + 会话列表）→ **设置页**（`components/settings/` 17,384 行，表单型、无重岛，风险最低）→ 业务页组（cron/skills/files/git/tasks，`main-content-v2/`）→ **聊天面最后**（≈4.8 万行，行为最细、fixture 用例最多）→ 壳/侧栏（`app-shell/`）收尾退役 React 构建。
3. 页内机制是组件岛：Rust 页面里挂 xterm/CodeMirror 岛（探针就要挂一个真终端岛验证桥）。
4. **放弃**「整体一次性切换」（违反 must-know ③）与「按组件逐个换」（137k 行组件两两桥接的复杂度爆炸，且旧包教训是父任务收不了口——调研 003）。
5. 双壳共存期的共享状态只有 localStorage/sessionStorage 键（`auth-token`：`api.js:29`；`pilotdeck-active-project`：`api.js:45`；主题与语言键由探针盘点），键名与语义对新前端是契约，不许改。

### (c) 对拍装置：46（实测 60+10，见 gap §三）个 e2e 用例能不能直接当验收

**AI 代拍：分四类，不能一刀切（待人复核）。**

- **能直接用（35 例）**：黑盒页面级 9 例（`formal-*`、`real-auth-*`）+ 真端到端 26 例（`real/*`）——同一套用例、同一 mock `/api`（`page.route`）与 mock LLM center（`real/launch.mjs:22-23`），分别跑旧新前端，逐例比 PASS/FAIL。**这就是主尺子。**
- **不能直接用（24 例）**：A 类 fixture 耦合用例驱动的是旧 store 的 window API（`streaming-lifecycle.spec.mjs:19-28`）。两条路：新前端暴露同等测试钩子（保留对拍能力，推荐）；或改写为黑盒用例（更长期，逐条改）。**在改写/移植完成前，这 24 例不计入新前端验收分母**，缺口由 Issue F2 补齐后回收。
- **与前端无关（1 例）**：`history-fork.spec.mjs` 是 API 级，归后端。
- **桌面专用（3 例）**：Electron smoke 只在桌面验收时跑；另 7 个 smoke 同 A 类处理。
- 截图：多数用例已带 `page.screenshot` 输出但无像素 diff 基线——**补基线机制、不补像素断言**（must-know ①：判语义，不判像素）。

### (d) 桌面端 `apps/desktop`（Electron）怎么办

**AI 代拍：本阶段一行不动（待人复核）。** 理由：Electron 壳只是 `loadURL` 到 `ui/server` 端口（`main.ts:622`），新前端是 wasm 静态产物、仍由同一端口托管，对桌面端透明；4,925 行桌面代码对 TS 后端的硬依赖（`main.ts:250-258, 921, 930, 941`）是**阶段 B（`ui/server` Rust 化）与桌面 Rust 化（旧计划 DESK-01，Wry/Tao）**的既有问题，与本阶段解耦。桌面端在本阶段的验收 = 3 个 Electron smoke 在「桌面壳 + 新前端」组合下照常通过（计划 004 Issue F6）。Wry/Tao 替换单开 issue，不做进本阶段。

## 我放弃什么

> 放弃「保留 React 只换后端」（与意向书方向不符）；放弃在浏览器里用 Rust 重写终端/编辑器/Office/PDF 渲染（无对应物，旧包两年没敢做）；放弃「整体一次性切换」与「按组件逐个换」；放弃像素级截图断言（只做基线与语义断言）；本阶段不动 Electron、不动 `ui/server`（阶段 B）、不追上游。

## 支持它的最强依据

黑盒可复用的 35 例 e2e **今天就能跑**（B 类已带 mock `/api`，D 类 `real/launch.mjs` 是现成的双进程编排）；`vite build` 产物是纯静态资产（`ui/package.json:22` `build` 脚本），Leptos 产物同为静态资产——**「渐进共存」不需要动 `ui/server` 一行**。

## 反对它的最强依据

A 类 24 例恰是行为最精细的流式滚动/生命周期/组合装配用例，主尺子在最需要机器判的地方最薄——Issue F2 补不齐，「行为一致」的成色就要打折；聊天面（≈4.8 万行）既是最大工作量又是风险最高点，若探针在 IME/stream_delta 上失败，混合方案的核心假设（Rust 壳能扛住高频流式 UI）被推翻，整个 (a) 要重拍。
