# 决策卡：#996 anchor_selfcheck 开关表审计的威胁模型（2026-10-29 07:3x）

**分级：自决 · 待复核（AI 代批，待人复核）——判断题：检查器防什么、不防什么**

## 卡在哪
#996-pr1 的 anchor_selfcheck「switches 表审计」连续 4 轮被 Codex 以刻意构造的写法绕过：r1 直接改写 → r2 别名 / getattr → r3 len 遮蔽 / globals 别名 → r4 在 `main()` 里 `globals()["swi"+"tches"].pop(0)`、伪造审计 JSON 后 `os._exit`。每轮修一层，下一轮换一种 Python 动态写法。

## 依据
- 该检查器的职责是**抓无意漂移**（负控作者改了表 / 锚点忘了同步），不是对抗**蓄意混淆**的负控作者；负控脚本本身每轮都经两家非作者评审，蓄意混淆在评审层就会被拒。
- Python 是动态语言，静态 + 导入期检查对蓄意代码不存在完备解（memory scanner-real-lexer 同类）；继续追堵即「流程马拉松替代开发」（CLAUDE.md 2026-10-17 人定）。
- 真正不可绕的真相源在**执行期**：开关执行器（`_shared/mutant_switch.py` / `schemata.py`）实际逐个运行的那张表。

## 选择
1. 检查器只承诺：静态白名单 + 导入期运行时对账 + **审计子进程非零退出即 ERROR**（r4 P1-2 的退出码部分，正确且便宜）。
2. **把分母核对下沉到执行器**：执行器在跑完后把「实际执行的开关名集合」与「静态声明集合」（由同一份提取函数得到）比对，不等即整套非零退出、summary 标 INVALID。这一步覆盖 `main()` 内改表等所有执行期篡改，是结构性闭合。
3. 蓄意混淆（伪造审计输出、`os._exit` 抢跑、运行期动态改名）**明确不在检查器威胁模型内**，写进 `specs/negative-controls/README.md`；由评审层负责。

## 能否撤回
可（检查器与执行器各一处）。不动对拍判分语义。

## 原则
**检查器写清威胁模型：防无意漂移，不追蓄意混淆；分母真相放在执行期。** 机检：执行器跑后实际集合 ≠ 声明集合即 INVALID（负控：执行器内删一行 → 整套非零）。
