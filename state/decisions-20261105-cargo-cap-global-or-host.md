## 选项与后果

| | 口径 | 全局峰值 | 单次构建 | 内存 | 代价 |
|---|---|---|---|---|---|
| **A 每台各一条池** | 每台各自计数：cb8 ≤4，本机 / macmini-01 / mbp2 ≤2（即 fleet.py 现值，CAPACITY 建议值） | **≤10** | 满载时单次构建 1m27s → **3–4 min** | cb8 4×12.3 = 49 GiB ≪ 其 101 GiB 预算，**安全**；macmini 2×12.3 = 24.6 GiB 已超 20.4 GiB 可用（既有风险，见 CAPACITY「P2（编译/测试）上限」§3.3，属另一张单） | 要把 CLAUDE.md 的「4」明确成「每台」 |

**用户可感知差异**

- **选 A**：派单后等待短——哪台机器有空就在哪台编译，四台并行，整体交付快；代价是满载时**单次**编译从 1.5 min 变 3–4 min（但同时在编的更多）。
- **选 B**：**单次**编译快（几乎独占一台机器）；但「cb8 空着 20 核、本机也不能开 cargo」会变成常态，**总吞吐与 PR 从派到合的时长都变长**。

## 建议

**选 A（每台各一条池），并把 CLAUDE.md 那句话限定为「每台」**（由人改，AI 不擅改）。三条依据都可复核：

1. **被约束的资源是每台机器的 CPU / 内存 / 磁盘**，不是跨机共享量。闸门 `scripts/cargo-slots.sh` 只看得见本机 `ps`，全局口径今天**没有执行者**——纸面 4、实际 6–10，等于没闸。
2. **既有决定已经按「本机 / 每台」读**（10-30 卡、11-05 人令卡），11-01 人定把编译搬到远端正是为了绕开本机 swap 与磁盘瓶颈；全局 4 等于把这份收益退回去。
3. **内存侧安全**：cb8 4×12.3 = 49 GiB ≪ 101 GiB 预算；每台取值有实测依据（CAPACITY「P2（编译/测试）上限」§3.3）。

若人更看重「单次编译快」，退到 **C** 而不是 B：C 至少保住每台有活干，代价只是多一道跨机闸。

## 原则（一次拍板 → 一条可复用原则）

**并发闸的计数单位必须与被约束的物理资源同域**：资源在哪台机器上，名额就记在哪台机器上；跨机合计的数字只能当观察指标，不能当闸门。
