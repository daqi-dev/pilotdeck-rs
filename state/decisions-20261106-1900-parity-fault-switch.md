## 追加（评审第 1 轮）：`check_schema.py` 的 `PDRS_REQUIRE_BASELINE` 同族 fail-open

日期：2026-11-06 · 决策分级：自决 · **AI 代批，待人复核** · 关联：#1900 / #1930

### 卡在哪

第 1 轮两家评审对同一事实给出不同等级：zai（GLM）判 P3，anthropic（Claude）判 P1 ——
`scripts/gateway-parity/check_schema.py` 的 `PDRS_REQUIRE_BASELINE` 只认
`("1", "true", "yes")`、不认 `on`、未识别值静默当 off，与本单刚收紧的 Rust 侧
`PDRS_REQUIRE_PERMISSION_FAULTS`（trim + 大小写不敏感 + 未识别 panic）口径不一致。

### 谁受影响 / 能否撤回

- 现网不踩：CI 钉死 `PDRS_REQUIRE_BASELINE=1`（`.github/workflows/ci.yml`）。
- 只有有人写 `=on` 时才会把「要求基线」读成「不要求」，方向是 fail-open（少判一次 FAIL），不会假 FAIL。
- 本单对该文件零改动；可撤回的只是 README 里那段登记文字。

### 动不动尺子

`check_schema.py` 在 `specs/gateway-parity/schema-FROZEN.md:13` 有冻结登记行。按 CLAUDE.md
「冻结尺子的变更」：须独立 issue、理由、两家评审、真实数据复算、重新登记；改判分语义须明确授权。
**本单没有这个授权**，所以「当轮修」在本单里不可执行。

### 选项与后果

| 选项 | 后果 |
| --- | --- |
| A 本单直接改 `check_schema.py` | 违反冻结程序；`check_frozen.py` 立刻报哈希不符，必须走重登记；本单无授权 |
| B 保持 P1、本单不合入，等 #1930 走完冻结变更 | 把一个先于本单存在、本单未触碰的缺陷变成挡住 5 项收尾的阻塞；与 CLAUDE.md「登记阻塞转独立工作」相反 |
| C 降级 P2 + 登记已知限制 + 转 #1930（**采纳**） | 缺陷留痕、有载体、不是假 PASS；本单可正常合入 |

### 建议与结论

按 C 处理，理由三条：

1. 分级表把「同类遗漏」明确列为 P2（P1 是「与 TS 基线或自身类型 / 文档 / 测试矛盾」）；
   该缺陷现无错误输出，需要一个具体的人为设置才变松。
2. 缺陷在冻结文件内、先于本单存在，本 diff 未改该文件；修复路径被冻结程序限定在独立 issue。
3. CLAUDE.md「冻结尺子的变更」对这类情况的指令就是「登记阻塞转独立工作」，本单照办：
   README 已知限制 + #1930（前置于下一次冻结登记窗口）。

**复核者若认为冻结装置的 P1 不得降级**，则本单应挂起等 #1930 完成 —— 这一条请在复核时明确裁定，
不要默认放行。

可复用原则：**评审给的等级是输入，不是判决**；当「当轮修」被更硬的规则（这里是冻结程序）挡住时，
写清「为什么不能在这一单修」，把缺陷转成有载体的独立工作，而不是把它标成已修或删掉不提。
