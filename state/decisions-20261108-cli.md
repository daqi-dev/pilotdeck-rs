- 卡在哪：固定 TS 基线的 `cron list` 已输出成功 JSON，仍因远端 WebSocket 存活而不退出；mbp2 隔离实测等 4 秒后仍无退出事件，需要 SIGTERM 清理。
- 谁受影响：四个旧 cron 子命令及使用它们的脚本；参数、请求、输出和业务副作用维持原约定。
- 能否撤回：可以，改动局限 CLI 连接生命周期，不改变持久数据格式。
- 是否动尺子或意向：不改既有冻结装置、分母或归一化；新增精确差异与产品测试。依现有人定“挂起属于默认修复的 bug”，不复制这项挂起。
- 选项与后果：保留连接会让一次性管理命令无终止；终态后释放连接使其按输出对应的退出码完成。
- 建议与决定：**AI 代批，待人复核**。选择终态后释放；仅在收到成功/失败响应或完成参数错误输出后结束，不给仍在执行的 RPC 新增超时，也不改变服务端任务生命周期。
- 原则与断言：一次性 CLI 已取得最终结果后不得因其自身的空闲管理连接继续挂起；子进程测试必须同时观察真实 WS 关闭及进程退出，不能只断言结果 JSON。
- 依据：`.42cog/intent.md` 的默认 bug 修复边界；`specs/gateway-parity/diffs/D2-CRON-WS-EXIT-001.md`；主仓 `_tmp/20261108-issue-124-cron/ts-lifecycle.mjs` 与 `ts-lifecycle.log`。此决定不表示 A8/P09 或 D2 已完成验收。

- 卡在哪：tungstenite 默认 16 MiB 单帧上限低于真实 TS cron 成功格；取消所有上限会重新引入项目已确认的长度头无界分配风险。
- 谁受影响：cron 管理客户端的大型响应；无持久格式变化，可撤回。
- 是否动尺子或意向：不修改冻结判分；新增独立 D2 差异，不借 D1 的旧批准扩大范围。
- 选项与后果：库默认上限截断已验证行为；无限制有资源风险；复用显式 128 MiB frame/message 预算覆盖已测成功区间并限制敌意输入。
- 建议与决定：**AI 代批，待人复核**，采用第三项，精确差异见 `specs/gateway-parity/diffs/D2-CRON-WS-RESOURCE-LIMIT-001.md`，未批准项不算冻结验收豁免。
- 原则与断言：共享传输配置应覆盖已验证的基线成功区间，有限上限须同时约束单帧和累计消息；测试核成功大帧与超限长度头的实际子进程结果。
