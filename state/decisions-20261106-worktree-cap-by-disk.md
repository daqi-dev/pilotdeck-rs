### 2. 名额现状

```
$ git worktree list | wc -l
41          # 含主仓 → 40 棵 linked worktree（把 2 棵已合入的树回收后为 39 行 / 38 棵）
```
上限 40 **正好占满**（`pdrs-ops/bin/new-tree` 当前因 lib 缺失走 40 兜底，再开一棵即拒）——这就是人说的「名额卡住满载」。

## 算式

```
可用磁盘 = 200 GiB（CLAUDE.md 上限）− 20 GiB（disk-budget 缓冲）= 180 GiB
常驻、不在名额内的占用 = 主仓 src/target 16.0 GiB + 共享 _build/cargo-target 32.1 GiB ≈ 48 GiB
可分给树的磁盘 ≈ 180 − 48 = 132 GiB

按中位数 242 MiB/棵：132 GiB ÷ 0.236 GiB ≈ 559 棵
按最坏 423 MiB/棵：  132 GiB ÷ 0.413 GiB ≈ 319 棵
```

用 23:06 复测的数重算一遍（常驻 = 共享 cargo-target 35.9 GiB + 主仓 src/target ≈ 16 GiB ≈ 52 GiB）：
可用 180 − 52 = 128 GiB；按 243 MiB/棵 ≈ **527 棵**，按带 `_tmp` 证据的最坏 588 MiB/棵 ≈ **218 棵**。
两次算式的结论一致：**磁盘可容 200+ 棵**，差一个数量级，取 80 不会碰到磁盘边界。

结论：**树数远不是磁盘约束**（磁盘可容 300+ 棵），约束是「单棵树长出来的本地编译产物」（实测 1.7–37 GiB/棵）。
后者已由两件事管住：开树时刻的 180/160 磁盘闸 + 回收时删树内 target。
所以名额可以从 60 继续放宽；`60` 先落地验一轮运行，下一档取 **80**。

取 80 的理由：当前实际用量 40（占满），60 只留 20 个空位，一轮并行提速就会再顶到；80 给到 2× 现状，
仍远低于磁盘可容的 319–559，且与 cargo ≤4、评审通道席位这些真瓶颈不冲突。

## 决定（AI 代批，待人复核）

1. **本卡不直接改常量**。`PDRS_WORKTREE_CAP_MAX` 60 先在 `chore/worktree-cap-60-1105` 落地跑一轮。
2. 下一档改动只有两处（届时另开 PR）：
   - `scripts/lib/worktree-count.sh`：`PDRS_WORKTREE_CAP_MAX=60` → `80`；
   - `CLAUDE.md` §五「资源上限」：`worktree ≤ **60**` → `**80**`（并写明依据本卡）。
   磁盘三档（180 硬闸 / 160 WARN / 200 总上限）**不变**，`pdrs-ops/bin/new-tree` 与 `wt-status` 都 source 常量，不另写数字。
3. **复查触发条件**（满足任一即重新测一遍本卡的表，再决定是否继续放宽）：
   - 名额连续 3 天 ≥ 80% 占满（≥64/80）；
   - `_build`+`_tmp` 在回收删 target 后仍 > 160 GiB 连续 3 天，或触到 180 GiB 硬闸；
   - 单棵净源码中位数 > 400 MiB，或单树本地编译产物中位数 > 10 GiB；
   - CLAUDE.md 的 200 GiB 总量上限本身被调整。

## 选项与后果

| 选项 | 后果 |
|---|---|
| A. 维持 60 | 现状 40 已满，60 只多 20 个位；一轮并行提速就再顶到，人还会再问一次 |
| B. **80（建议，60 跑一轮后再改）** | 2× 现状；仍远低于磁盘可容 319–559；磁盘闸与回收纪律不变 |
| C. 100+ | 磁盘仍容得下，但并发派单、评审通道、cargo ≤4 会先成为瓶颈；名额宽松会诱导「为填满而开单」，与「上限不是目标」冲突 |
| D. 取消名额、只留磁盘闸 | 失去「席位」这一层约束；树数暴增会让 `wt-status`/回收/进程排查变慢，且 codex 树不受控 |

## 原则

**名额跟着瓶颈走，不跟着愿望走**：树数不是磁盘瓶颈时按并行需要放宽；磁盘瓶颈由独立闸门（180/160）兜底；
每放宽一档必须带一条可复查的触发条件，而不是一次调到用不完。
