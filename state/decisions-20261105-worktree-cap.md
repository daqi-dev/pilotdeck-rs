# 2026-11-05 · worktree 上限 40 的计数口径

## 卡

- **卡在哪**：`state/decisions-20261105-parallel-speedup.md`「执行口径」节把「worktree ≤ 40」列为保留的物理约束，但没说这 40 数的是哪些树。实际现场三处口径不一致：
  - `scripts/new-tree.sh`：`git worktree list | grep -c "/_build/wt-"`，只数 `_build` 子集（当时 29→35，始终 < 40），于是放行；
  - 硬规则：数全量 `git worktree list`（37→43，越顶）；
  - `scripts/wt-status.sh`：汇总行同样只数 `_build`（报 32，真实 38），回收循环据此按偏小数字放行。

  差额恒为 8 个非 `_build` 条目：主仓 1 + codex 工作树 6 + `/tmp` 下 1。原始证据 `_tmp/20261105-tree-hyg/TREES.md`。
- **谁受影响**：协调者的开树闸门（`new-tree`）、回收闸门（`wt-status` rc）、本机磁盘与并行席位；不改任何产品代码行为。
- **能否撤回**：可撤回。改回「只数 `_build`」只需回滚一个 lib 文件与两处调用，无数据迁移、无历史重写。
- **动不动尺子/意向**：都不动。不碰 `.42cog/intent.md`，不碰任何冻结文件与判分语义；上限数值仍是 40（本次只统一「怎么数」）。

## 口径（已裁决）

**上限按全部 linked worktree 计，排除主仓工作区本身。** 等价 `git worktree list | wc -l` − 1。

理由：codex 树与 `/tmp` 下的树同样吃磁盘、同样占并行席位，口径应当反映真实占用；主仓不是副本，不计入。

## 选项与后果

| 选项 | 后果 |
|---|---|
| A. 全量计（含主仓） | 与硬规则字面一致，但主仓恒占 1 席，等于上限变 39；且主仓不可回收，永远还不上 |
| B. **全量计、排除主仓**（采纳） | 数字等于真实并行副本数；与既有硬规则只差主仓 1 个，切换后现存树 38/40 立即吃到真闸 |
| C. 维持 `_build` 子集 | 现状：codex 6 棵 + `/tmp` 树隐形，实测 43 棵仍放行，上限形同虚设 |
| D. 按磁盘占用折算 | 更贴近真瓶颈，但需要新的测量口径与阈值，且磁盘已有独立 185/200 GiB 硬闸，重复 |

## 建议

采纳 B。同一份实现放 `scripts/lib/worktree-count.sh`，`new-tree.sh`（pdrs-ops）与 `wt-status.sh` 同轮改为调用它，缺文件时 fail-closed（拒绝开树而不是退回旧口径）。第三处计数 `pdrs-ops/scripts/fleet/fleet.py`（原先含主仓、比真闸早一棵告警）同轮改为 −1 对齐。上限数值 40 不变。

**副作用（已知并接受）**：口径改真后，当前 37–38 棵已接近上限，开树会更容易被拒——这正是闸门应有的行为。

**回收口径的缺口（一并记下，不在本次修）**：`wt-status.sh` 与 `recycle-tree.sh` 只认 `_build/wt-*`，而名额现在也算 codex 的 6 棵与 `/tmp` 下的树——它们**计入名额但不在回收清单**。故「靠回收腾席位」的有效上限是 `40 − 非 _build 树数`（当前 7），非 `_build` 树由各自持有人处理（codex 树归 codex 会话，`/tmp` 树人工判定）。

**残留风险**：
- `new-tree.sh` 用绝对路径 source 主仓的 lib。主仓检出切到不含该文件的旧提交时，开树以 exit 2 拒绝并打印缺失路径（fail-closed，不静默退回旧口径）；合并到 main 后即恢复。
- 计数与 `git worktree add` 之间无锁（check-then-act）：两个会话同时读到 39 会各建一棵。这是原有的行为，口径改真后才有实际意义；上限本是人为软闸，磁盘 185/200 GiB 那条是独立硬闸。
- 上限可由环境变量 `PDRS_WORKTREE_CAP` 调低（自测用）；lib 只允许调低、>40 或非数字一律夹回 40，且生效值不是 40 时向 stderr 报警，不会静默收紧。
- `wt-status.sh` 的集成层没有回归测试（2026-11-05 评审 sibling P2）：同批改的三处——`pwd -P` 修 symlink、`linked >= cap` 满额提示、汇总行格式——只靠人工实跑。补测试要临时仓 + 假 `gh`，且 `wt-status.sh` 属协作工具（CLAUDE.md 二·只做产品代码：工具类不开 P2-跟进），故先记在这里；口径若再改，务必同时人工复核 `wt-status.sh`。
- `git -C "$root"` 的仓库发现可被环境残留的 `GIT_DIR` / `GIT_WORK_TREE` 劫持（评审 boundary P3），此时会数到别的仓、linked 数假低。hook、git 包装器、`git rebase` 子进程里可能出现这种环境；真要收紧，计数处改 `env -u GIT_DIR -u GIT_WORK_TREE git -C ...`。当前判定为低风险，不在本次改。

## 原则（一次拍板 → 一条原则）

资源上限的计数口径必须只有一份实现，且必须反映真实占用；「数不到的树」等于「不存在的约束」。
