# PilotDeck-RS：把 PilotDeck 后端从 TypeScript 重写为 Rust · 意向书

> 意向即行动。这一份文件决定这个系统会长成什么样。
> **只有一处必须你亲自过目：收敛方向。其余是草稿，看不顺眼再动。**
> 本文件写整体目标与完成边界；阶段细则见计划和规约，当前进度与下一任务见 `state/board.md`。

## 收敛方向（唯一）

以 **`OpenBMB/PilotDeck@cc7c4e6`**（standalone_alpha1，2026-10-13）为固定基线，完成 agent 循环、gateway、`ui/server` 和全部 CLI 的 Rust 重写，并按已批准范围完成前端重构，使全部产品入口在新实现上具备约定行为；以**各阶段行为验收、被替换实现的退役证据和真实使用验收**共同判定整体完成。

**分阶段计分，按依赖接续。** C（Sidecar）、A（Gateway）、B（UI Server）、前端与 D（CLI）各有验收对象和判据，分别报告；C 的场景分数不作为其他阶段的统一指标。独立任务可以并行，具体开工条件沿用已批准依赖。进入后续工作不代表前一阶段已经验收，当前结果以状态板所引证据为准。

> 依据：[边界决策](../docs/research/002_parity-boundary/decision.md)与[后续人定记录](../state/decisions-20261014.md)；本次按 2026-10-16 用户要求，将已扩展的项目范围整理为整体目标，不重设冻结判据。

## 真难题

一个 18 万行 vibe coding 的 agent 平台，**它的真实行为没有成文规格**——行为散落在 31 个模块的实现、9.8 万行测试和前端的隐含假设里。重写最难是**先把「什么叫一致」变成机器能判的东西**。尤其是在哪个颗粒度上保持一致，架构不合理怎么办，原始代码有错怎么办，测试或者探针本身有问题怎么办？

## 不做什么

| 不做 | 为什么不做 |
|---|---|
| 迁移期间不加新功能、不"顺手"改行为——**修 bug 除外**（2026-10-14 人定「默认修」） | 重写失控的第一原因。想到改进就记一条 issue，不当场做（demo-2/04 §六）。**什么算 bug（2026-10-14 人定）**：基线 ① 崩溃、挂起、丢数据 ② 与它自己的类型定义、文档或测试断言相矛盾 ③ 有安全问题。三条都不沾的是「行为偏好」，记 issue、不改。修了一律记进「已接受差异」清单（第 9 步建立），写明属于哪一条 |
| 不跨阶段擅改产品边界 | 阶段 C 只替换 Sidecar，不改 TS 的 `src/`、`ui/` 或 `apps/desktop`；阶段 A 不改 `ui/` 或 `apps/desktop`。B 承担 `ui/server` 替换及必要的启动编排，前端按自己的计划推进。整体重构完成后再进入优化；独立工作并行不取消阶段依赖或验收要求 |
| 不把整体重构解释为所有依赖和桌面壳都必须改成 Rust | 前端 Leptos 选型已有人定；Rust 前端与第三方 JS 岛、保留 Electron 等方案仍沿用[前端决策](../docs/research/007_frontend/decision.md)各自的批准状态。桌面启动编排与本地能力必须列入入口总账并验收；替换桌面壳另立任务，本次不新增范围 |
| 不追上游最新提交 | 参照物在动，对拍就没有意义。升级基线 = 单独一条 issue，整批升 |
| 不照搬 TS 的模块内部结构（Bundle / 注入层层套）；**也不在移植一个模块的同时重构它** | 一致的是**协议和行为**，不是类图：模块边界与数据流照原样映射，内部按 Rust 习惯写。要重构放在移植前或移植后（`docs/research/001` 第二节第 1 条） |
| 不自己发明协议、字段、错误格式 | 以基线 TS 实测输出为准；有疑问跑一次基线看，不猜 |
|  |

## 真相源与权重

冲突时信谁，从高到低：

1. **基线 cc7c4e6 在对应入口实际跑出来的行为**（后端、CLI、UI 与桌面实测输出）
2. 基线对应范围的测试——测试与实测冲突时，以实测为准并记录
3. 基线的源码（`resources/PilotDeck/` 中对应范围，结论必须带文件行号）
4. 基线的文档（`docs/`、README）——可能过时，只作线索

上述排序用于确认原版事实。**已批准的行为差异按登记的明确期望和适用范围验收**；仅有建议或记录不等于批准。D4 的宿主超时修正等已有决定，仍须完成对应期望登记、评审与冻结，不能只改本文件就放宽评分。

## 作品区

- 目录：`src/` 是产品实现区；现有 Cargo workspace 包含 CLI、gateway 与 Sidecar crates，后续服务和前端按各自计划落地。
- 交付形态：可组合运行的 Rust 后端、完整命令行入口和按计划重构的前端；现有桌面壳通过适用的启动编排接入。各阶段的代理/双壳共存只代表迁移中间状态，完整产品交付须满足下述完成条件。
- 覆盖范围由**产品入口总账**枚举：基线两个 bin 的全部子命令、gateway method 与 HTTP/后台入口、`ui/server` 的 HTTP/WS/SSE，以及桌面编排和本地能力。每项必须有实现状态、所属阶段/任务和验收方式，独立基线枚举与账本集合对等；总账及阶段 D 计划仍是接续待办，不能当作已有产物。

### 整体怎么算完成

以下条件同时满足才称整体重构完成：

1. **行为符合约定**：各工作面所有必需验收通过，已批准差异有精确期望和证据；代码交付通过适用的CI（fmt/clippy/test）与回归，完成独立审阅。CI绿或分数不下降本身不能代替阶段验收。
2. **迁移范围完整**：入口总账无漏项、无无主项、无必需功能占位；被替换的TS实现和临时业务回退确已退役，有实际进程/调用/状态证据。获准保留的第三方组件、桌面壳、外部provider和测试驱动按角色列明，不把未迁移内部模块伪装成保留项。适用的持久数据、切换、重启与回滚验证齐备。
3. **真实使用闭合**：人在最终组合上完成Web与CLI实际任务，以及桌面适用范围的验收，包含对话/工具、交互与恢复、历史/数据和前端操作。AI准备隔离候选、步骤和证据，未做的如实记待验；到本节点的前置债务清完，所有必需门闭合才标完成。

局部兼容、技术退役和真实使用各自记录状态；未完成的一项不阻止独立任务推进，也不因其他阶段通过而自动关闭。详细验收步骤由阶段计划落地，当前缺口与下一步只维护在状态板。
