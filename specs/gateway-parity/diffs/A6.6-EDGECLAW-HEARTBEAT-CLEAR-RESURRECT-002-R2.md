## Rust 行为

更正后的完整表述（替代 R1「TS 依据」末段括号里的那半句）：

> 复位只适用于 `clearSession`。dream / service 的三处 `delete_memory_entries` 调用不写
> `indexed` 列（它们删的是 entry，没有 session key），所以不存在「按会话复位」的作用对象；
> 但它们的 mid-delete 失败同样留下「已索引的来源 L0 行文件已删、`indexed` 仍为 1、
> `list_unindexed_l0_by_session` 永不再列、文件无从再生」的未恢复面——与 R1 在 `clearSession`
> 路径修的是同一形状。**不扩 `rearm_l0_indexed_for_session` 的真实理由是两半**：① 复位按会话
> 键控（`UPDATE l0_sessions SET indexed = 0 WHERE session_key = ?1`），这三条路径没有会话键；
> ② 更关键的是，这三条是**故意的**删除，复位 `indexed` 会让下一次 heartbeat 把用户刚删掉的
> entry 重新生成——正是 #917 要防的复活形状。故该失败面在此**登记而不修复**，后续若处理须按
> 「故意删除 + 失败面」单独设计，不能套用 `clearSession` 的 re-arm。

#1298 同时收紧同一段落的错误优先级：两处 re-arm 从 `?` 改为 best-effort——
`rearm_l0_indexed_for_session` 自身失败时**保留中止 clear 的原错误**，并把 re-arm 失败记录出来
（生产 stderr；测试用 doc-hidden 观察者），不再让 `database is not open` 覆盖注入的原始原因。
复位成功或失败都不改变「L0 行仍在、`indexed` 是否已复位」的既有语义。

该收紧**不改变失败面本身**：clear 在中途失败、且 re-arm 也不可用时（例如 storage 已关闭），session 的
memory 文件已删、L0 行仍在且 `indexed=1`，`list_unindexed_l0_by_session` 不会再列出它，下一次
heartbeat 也就不会再生文件——与上面 dream / service 三处**同一形状**的未恢复面，同样**登记而不修复**。
恢复只有两条路，都不是「等下一次 heartbeat 自己好」：① 人工把该行 `indexed` 复位（或重建文件）；
② 用户再执行一次**成功的** `clearSession` —— 那会把这条残留行一并 DELETE 掉（`entries.rs:576`），
是清除而不是再生。想让下一次 heartbeat 自己恢复，就必须把 `indexed` 复位，而那正是 dream / service
路径不能做的复活。#1298 改变的只是「调用方拿到哪个错误、失败有没有被记录」，不是这个面本身。
