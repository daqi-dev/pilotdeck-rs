## 类别

更正（#2499 fix-r5，评审 sibling#1——sms 车道同期修复的「停泊至
withholding cap 的后继头不唤醒」在本车道原样存活，镜像同一修法；R2 属
origin/main 既有文件，按冻结程序以新增文件登记；merge-main 改号——
origin/main 的 #1517 链已先占 R3（后续 R4/R5），本条由分支侧原 R3
改号 R6，内容不变，正本及 R1/R2 字节不动）：

1. **停泊唤醒已补**：`UpgradeReadGate` 的 cap 停泊分支（评审时形状
   `http_proxy.rs:627-635`——只 poll deadline sleep，r4 只修了 sms 那份）
   现在在返回 `Poll::Pending` 前把本 poll 的 waker 存进 release 槽
   （`release_waker` 字段 `:343`，注册位 `:729`，
   `serve_connection_configured` 创建 `:1223`），`IdleBody::release`
   （`:1158`，清 in-flight 之后）取槽唤醒。修法与 sms 车道 fix-r5 逐字
   同构（`A8.3-CH-SMS-017`「Rust 行为」的 release 槽条）；两侧都没有
   采用 fix-r4 的空缓冲 `poll_read`——#2499 fix-r5 的 tokio 探针
   （`_tmp/20261026-issue-2499/fix-r5/probe-tcp-empty-poll/probe-run.out`
   legs 1/2b）证明生产 `TcpStream` 上零长读在内核仍有数据时不注册
   waker（`read(fd, ptr, 0)` 返回 `Ok(0)`，tokio 只在 `WouldBlock` 存），
   恰排空形状下成立是内核依赖的偶然。唤醒后 hyper 重 poll 停泊读、
   非空 `withheld_head` 逐缓冲回喂解析路径——响应完成即回喂，恰是
   Node llhttp 逐个服务停泊头的时刻（TS 依据 leg A/B）。
2. **停泊的已完整后续头在响应永不完成时被 408**（残差登记，与
   `A8.3-CH-SMS-017` 残差 4 同族同措辞）：已完整停泊头各自首字节锚定
   的 deadline 照常落地，在飞响应未写过字节时到期分支写 408 + destroy；
   Node 对已解析请求永不被 408（TS 依据 leg B/E）——本车道与 sms 车道
   共用该 Node 实测，行为差登记为有界残差，不构成判分豁免，不改变任何
   金样格期望（金样矩阵无「已完整后续头停泊在永不完成响应之后」形状）。

`_tmp/20261026-issue-2499/fix-r5/`）：

1. `probe-node-pipeline-serve.out`（leg A/B）：请求 1 + 512 条已完整
   pipeline 头一次写出（32,768 B）后静默——leg A（headersTimeout 60 s、
   hold 500 ms）与 leg B（headersTimeout 1.5 s、hold 4 s，停泊头跨过
   自身期限）都观测到 **513 条响应、零 408**，末条 @514 ms / @4011 ms
   （恰在响应释放后）：已完整停泊头 deadline-immune，响应完成时逐个
   服务。leg C（对照，1.5 s 期限 + hold 4 s + **不完整**后续头）：
   @1606 ms 恰 51 字节 408 + close——不完整头照常自身 deadline 408，
   与 R2「首字节锚 + `_headerSent` 假则写 408」判据一致。
2. `probe-node-parse-state.out`（leg D/E）：leg D 为 leg C 的 parser 状态
   仪表化（408 后 parser freed）；leg E（**已完整**单条后续头 + held 响应）
   ：requests=2、parser present，+6 s 内无 408 无关闭，释放后两条全数
   送达——残差 2 的 Node 侧原证。
3. `probe-tcp-empty-poll/probe-run.out`（tokio 探针，非 Node）：生产
   `TcpStream` 上满 4096 读后零长 `poll_read` 的 waker 行为——内核仍有
   数据时后继字节不触发（legs 1/2b），证明空缓冲 poll 不能作停泊唤醒。

## Rust 行为

`src/pilotdeck-gateway/src/http_proxy.rs`（native lane，`UpgradeReadGate`；
代理 lane `serve_connection_with` 无超时照旧）：

- release 槽（fix-r5；行号按 fix-r9 落地后重锚）：`UpgradeReadGate` 持
  `release_waker: Arc<Mutex<Option<Waker>>>`（`:343`，
  `serve_connection_configured` 创建 `:1223`，经 service 闭包与
  `IdleBody` 共享）。停泊分支（`withholding_mid_stream()` `:441` 起，
  cap 检查 `:681`，`WITHHELD_HEAD_CAP` 32 KiB `:942`）在返回
  `Poll::Pending` 前存本 poll 的 waker（`:729`）；`IdleBody::release`
  （`:1136`）先清 in-flight 再取槽唤醒（`:1158`，变异
  `native-http-withheld-park-no-wake` 只摘唤醒供负控击杀）。停泊头自身
  的 deadline 不需额外交出：到期检查的 sleep 在同一 waker 下每 poll 注册。
  fix-r9（merge 后 DS 评审 concurrency#1/sibling#1/boundary#1 三撞 P1，
  实测复现后当轮修）：body 已结束而尾部未 flush 时，被唤醒的 poll 因
  `write_pending` 仍真而重进停泊分支、把 waker 存回槽；清该标志的唯一
  转换——`poll_flush` 的 `Ready(Ok(()))` 分支（`:865`）——同形取槽唤醒
  （共用 helper `take_and_wake_release_slot` `:1084`，先取值再唤醒、不持
  Mutex guard 跨 `wake()`），停泊的已完整后续头在 flush 完成处确定性回喂，
  即 Node `finish`（needs-the-flush）服务停泊头的时刻；机器判据格
  `native_http::tests::unflushed_tail_flush_completion_serves_the_parked_complete_head`。
- 回喂路径（既有）：响应完成后非空 `withheld_head` 逐缓冲交给 hyper
  解析路径——与 sms 车道同形；唤醒让 hyper 重 poll 该读，回喂才可达。
- 其余读门行为（锚点重武装、首字节锚、网格落地、`_headerSent` 分裂、
  预算 431）维持 R2 登记，本条不重抄。
