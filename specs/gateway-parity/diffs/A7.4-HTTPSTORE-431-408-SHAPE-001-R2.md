## 类别

更正（错误响应字节 / HTTP 头超时语义）。原条目与 R1 对 431 / 408 响应字节的描述与本次 Node v22.22.0 原始 socket 实测不符：Rust 的 431 不逐字节等于 Node，Rust 的头超时不是 408 而是直接断连；R1 留下的「431/408 是否带 `content-length: 0` 尚未逐字节比对」本轮已实测。本条只更正事实与适用范围，**未批准，非已接受差异**，不新增判分豁免。

## 基线依据

实测 2（头超时）：两条连接分别只发送不完整请求头（`POST ... HTTP/1.1\r\nHost: ...\r\n`）和完全不发送字节；默认 `headersTimeout = 60,000` ms，Node 连接检查器每 30,000 ms 扫描一次，两条都在 **89,985 ms** 收到 408（多次运行 89,985–90,002 ms）。响应共 **51 字节**，无 body、无 `content-length`、无 `date`：

读码核对（不作为实测替代）：Node 内置 `_http_server` 的 `headersTimeout` 默认 `MathMin(60_000, requestTimeout)`，`checkConnections` 以 `connectionsCheckingInterval`（默认 30,000 ms）为周期调用 `onRequestTimeout`，`ERR_HTTP_REQUEST_TIMEOUT` 走 `requestTimeoutResponse`，该常量的字节即上面的 51 字节；`requestHeaderFieldsTooLargeResponse` 即上面的 67 字节。两条都是 parser / connection 层直接 `socket.write`，不经过 `ServerResponse`，所以没有 `Date` / `Content-Length`。

对照负控（同一真实 server）：把 `X-Pad` 降到 15,000 字节（低于 16 KiB）后，真实 handler 返回 200（167 字节），不是 431；完整合法请求在毫秒级返回 200，不是 408。原始输出同上日志的 `node-header-15000-control` 与 `node-valid-request`。

## Rust 行为

被测：本树 HEAD `55df8cee`（文档分支，产品代码未改）的 `start_gateway_user_dialog_store_http_server`，默认 `ServeLimits`，绑定 `127.0.0.1:0`。探针是临时集成测试 `src/pilotdeck-gateway/tests/probe_683_raw.rs`（抓包后已删除，原文存档在 `_tmp/20261025-issue-683/probe-rust-temp-test.rs`），原始输出 `_tmp/20261025-issue-683/rust-probe-raw.log`。

实测 1（431）：同一 20,000 字节 `X-Pad` 请求，响应共 **123 字节**：

`date` 是运行时值：另一轮同请求的实测为 `date: Sun, 25 Oct 2026 10:01:45 GMT`、`date: Sun, 25 Oct 2026 10:05:58 GMT`，头名小写由 hyper 写出；三份都是 123 字节、除 `date` 值外逐字节相同。默认配置下 20,000 字节单头先撞上 hyper 的 `max_buf_size`（等于 `max_header_bytes`，16 KiB）解析器上限，**这个 431 由 hyper parser 层自己写出，不经过 store 的 `empty_response`**；`http_store.rs:1925-1927` 的自有 `header_bytes` 分支在本探针的默认 limits 下没有可区分的输出（若被触发，才经 `empty_response`（`http_store.rs:2004`）写出）。hyper parser 层这条实测带 `content-length: 0` / `date`；自有分支若被触发，预计同样由 hyper 补上这两项（未单独实测）。

实测 2（头超时）：不完整请求头和完全空闲两条连接，分别在 **60,002 ms / 60,003 ms** 收到 EOF，**共 0 字节**（没有任何 HTTP 状态行），不是 408。实现为 `http_store.rs:1784` 的 `header_read_timeout(60 s)`（`DEFAULT_HEADERS_TIMEOUT` 见 `:44`）；hyper 到期直接结束连接。408 只出现在 body `requestTimeout` 路径（`http_store.rs:1977`，`empty_response(StatusCode::REQUEST_TIMEOUT)`）；该路径本轮未重新抓包，形状按同一 `empty_response` 推断为带 `content-length: 0` / `date`，见「范围」。

对照负控：同一 server 的 15,000 字节 `X-Pad` 请求返回 200（167 字节），完整合法请求在毫秒级返回 200；说明 431/EOF 是超限/不完整头触发，不是 server 整体失联。原始输出同上日志的 `rust-header-15000-control` 与 `rust-valid-request`。

## 范围

仅限纯 HTTP/1.1、默认 limits、`127.0.0.1` 回环上的两条错误路径：

1. 请求头字节超过 16 KiB（Node 默认 `maxHeaderSize`；Rust 默认 `max_header_bytes` / hyper `max_buf_size`）→ 431。两侧状态码相同，但**响应字节不同**：Node 67 字节，Rust 123 字节且多 `content-length: 0` 与 `date`，头名大小写也不同。原条目「Rust 空 body + Connection: close，状态码与 Node 一致」只在状态码层面成立，不能据此声称逐字节一致。
2. 请求头在阈值内未收完（含零字节空闲连接）→ 头超时。Node 在约 90 s 发 408（60 s 阈值 + 最多一个 30 s 检查周期），Rust 在 60 s 直接 EOF、零字节。原条目把它与 408 并列描述为「状态码与 Node 一致」不成立；R1 已指出 Rust 无 408，本轮补上两侧字节与触发时间。

不在本条范围：① body `requestTimeout` 的 408 精确字节本轮未实测（只读码推断与 431 同形，待后续抓包）；② 431 的 name+value / 原始字节阈值边界（R1 已有探针，本条不改）；③ keep-alive / 空闲连接 5 s 超时（A7.4-HTTPSTORE-KEEPALIVE-001）；④ 正常 200 响应的头序 / 头名大小写（探针里可见 Node 与 Rust 不同，但属另一类传输层差异，未登记在本条）；⑤ TLS / HTTP/2 / 非回环网络。

影响：依赖「头超时必得 408」区分超时与断连的客户端在 Rust 上看到的是零字节 EOF；只解析状态码的 431 客户端不受影响，但逐字节比对（含 `content-length` / `date` / 头名大小写）会失败。对拍/金样如比较错误响应字节，必须显式归一化 `date`（或固定时钟），否则会得到不稳定的假失败。

## 机器判据

现有自动判据只钉住当前 Rust 形状，不钉 Node 逐字节相等：

- `src/pilotdeck-gateway/src/user_dialog/http_store_tests.rs:438` `oversized_headers_are_rejected_like_node`：断言 431、空 body、含 `connection: close`；**不断言** `content-length` / `date` / 完整字节。
- 同文件 `:602` `partial_headers_are_closed_after_headers_timeout`：断言 200 ms 配置下收到 EOF（`read == 0`）；这正是「Rust 无 408」的现状钉住，不是 Node 对齐断言。
- 同文件 `:519` `idle_keep_alive_connections_close_at_headers_timeout`：空闲连接在头超时后 EOF。
- 同文件 `:636` `slow_request_bodies_are_closed_after_request_timeout`：body `requestTimeout` 的 408、空 body、`connection: close`；不覆盖头超时。
