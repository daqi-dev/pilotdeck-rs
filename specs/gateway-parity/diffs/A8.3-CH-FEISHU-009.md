## 类别

有意改进（类型系统强制）。TS 的分段与截断都是 JS 字符串的 UTF-16
`slice`/`substring`，切点落在代理对中间时会留下孤立代理项：两个分段各带
一个 `\ud83d` / `\ude00`，`JSON.stringify` 把它们转义后照常发给飞书。
Rust 的 `String` 只能是合法 UTF-8，孤立代理项无法表示；照抄切点就只能
用 `from_utf16_lossy` 写出 U+FFFD（用户看到 `�`）。因此 Rust 侧在切点
落在代理对中间时把边界移动一个 UTF-16 单元，让代理对整体留在同一段，
其余切分规则（每段 `liveTextLimit()` = 3998 单元、超长 `post` 截断到
3988 单元后追加 `…（已截断）`）与 TS 逐单元一致。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/protocol/ImLiveReplyController.ts:332-360` 的
`append` 用 `text.slice(0, limit)` / `text.slice(limit)` 切段（按 UTF-16
单元，不避代理对）；`feishu-render.ts` 的 `renderFeishuLivePost` 用
`text.slice(0, max)` 截断。Node 实测（`node -e` 探针，基线同一运行时）：

本地实跑（Node v22.22.0，原始输出）：

```
$ node -e 'const s="a".repeat(3997)+"😀"; const a=s.slice(0,3998), b=s.slice(3998);
console.log(JSON.stringify({node:process.version, firstTail:a.slice(-1),
secondHead:b.slice(0,1), joined:a+b===s,
units:[a.slice(-1).charCodeAt(0).toString(16), b.charCodeAt(0).toString(16)]}))'
{"node":"v22.22.0","firstTail":"\ud83d","secondHead":"\ude00","joined":true,"units":["d83d","de00"]}
```

即 TS 的两段各持半个代理对（`d83d` / `de00`），拼回去才等于原文。

## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/render.rs`：
`live_chunks`（`append` 的移植）在 `units[end - 1]` 是高代理项时把 `end`
回退一个单元（`limit == 1` 的退化情形改为前进一个单元，保证每段至少含
一对完整代理项或一个完整字符）；`truncate_units`（`renderFeishuLivePost`
的截断）做同样的回退。两处都保证输出字符串不含 U+FFFD，且各段拼回等于
原文。切点不落在代理对中间时（金样与绝大多数真实回复），分段边界与 TS
逐单元相同。

## 范围

仅 feishu 出站文本的 UTF-16 分段/截断在**代理对跨界**这一种边界上的
切点位置：TS 产出两个孤立代理项，Rust 产出「整对留在后一段/前一段」。
不覆盖分段长度、段数（除该边界外一致）、`post` 载荷结构、纯文本回退、
`splitForTransport` 的换行/空格优先规则，也不覆盖入站解析。本条不构成
判分豁免。

## 机器判据

- `src/pilotdeck-gateway/src/channel/feishu/render.rs` 的
  `live_chunks_never_split_a_surrogate_pair`：`"a"*3997 + "😀" + "b"*10`
  按 3998 切分后，任一段都不含 U+FFFD、拼回等于原文、段数为 2（切点从
  3998 移到 3997）；同一用例钉住 `render_live_post` 在截断窗口正好落在
  高代理项之后时仍不带 U+FFFD 且保留 `…（已截断）` 后缀。
- 金样矩阵不覆盖该边界（生成器没有代理对跨界用例）；两侧的真实差异以
  上面的 Node 探针记录为准，负控矩阵不为本条新增变异（改动本身就是
  判据）。
