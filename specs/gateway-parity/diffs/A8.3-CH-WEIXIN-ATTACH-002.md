## 类别

不可避免（宿主运行时差异）。附件落盘失败时，基线把 Node `fs` 抛出的错误原样
交给 `formatWeixinError`，用户可见诊断里带着 Node 的错误码、syscall 与路径
（`EACCES: permission denied, mkdir '/…'`）。Rust 的 `std::io::Error` 只保留
errno 与描述，不携带 Node 拼出的 `code: description, syscall 'path'` 文本；
`Display` 形如 `Permission denied (os error 13)`。失败可见（同样进
`微信附件处理失败：…` 诊断、同样不落盘），只是错误文本不同。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/protocol/ImAttachmentStore.ts`：`:78` `await mkdir(dir,
{recursive:true, mode:0o700})`、`:85` `await writeFile(path, buffer,
{mode:0o600})`、`:86` `await stat(path)`——三处都直接把 `fs` 的 rejection 抛给
调用方。`src/adapters/channel/weixin/WeixinChannel.ts:620`（`extractIncomingMessage`

## Rust 行为

`src/pilotdeck-gateway/src/channel/im_attachment.rs:311-317` 的 `io_error`：

```rust
fn io_error(error: std::io::Error) -> AttachmentError {
    AttachmentError::error(error.to_string())
}
```

`create_private_dir`（`:319-328`）、`write_private_file`（`:331-341`）与
`metadata` 失败都经这一个函数包装，`AttachmentError::formatted()` 再加
`Error: ` 前缀，于是同一个失败在 Rust 侧的诊断是
`微信附件处理失败：Error: Permission denied (os error 13)`。

## 范围

只影响落盘阶段的失败诊断文本（`create_dir_all` / `write` / `metadata`），以及
以这些错误为 `cause` 的上层日志。成功路径（路径、文件名、0600/0700 权限、
metadata 展平顺序、`bytes`)不受影响；错误是否可见、是否中止该附件、是否继续
处理同一条消息的其余 item，两侧一致。空消息/回退文案与 `Attachment is … bytes
(limit …).` 两类诊断不受本条影响（它们由实现自己拼文案，逐字对齐基线）。

## 机器判据

- `src/pilotdeck-gateway/src/channel/im_attachment/tests.rs` 的
  `save_from_url_persists_with_the_baseline_metadata_spread`、
  `save_from_url_creates_private_paths` 钉成功路径；失败文本目前无逐字用例
  （失败注入需要只读目录/占用路径，跨平台不稳定）。
- 复算（人工）：`node _tmp/20261107-issue-1822/fs-probe/probe.mjs` 给出上表；
  Rust 侧 `std::io::Error::from_raw_os_error(13).to_string()` 为
  `Permission denied (os error 13)`。
- 未登记负控行：本条是诊断文本的宿主差异，不是可注入的判分行为，加负控只会
  产生无法 KILLED 的假锚点。

## 批准记录
