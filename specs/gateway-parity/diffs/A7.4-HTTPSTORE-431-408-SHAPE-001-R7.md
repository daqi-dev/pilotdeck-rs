## 类别

更正 R6 的三处事实性错误（#1576 双家四角色审查的边界 / sibling P1，评审人独立核验），不改变
任何已登记差异的类别，也不新增判分豁免：R6 把折叠续行残余的 Node 结局写反、把
`fields-max-16x` 的串行测量标成「16 路并发」、§范围 把 raw 上界的残余形状写成只剩折叠
续行而漏掉请求行分隔符。第三条同时补登一个此前未登记的 Node 200 / Rust 431 形状。

本条同时登记 #1555 fix-r2 引入的 **CR 族第三形状**（值内 CR + 越过 raw 上界的填充：
Rust 67 B 431 vs Node 47 B 400），并把本轮新增的 Rust 侧判据与负控写进 §机器判据——
fix-r2 前该形状被 guard 改写成合法空值（405），fix-r2 后它变成 431，两者都不等于 Node 的
400，但 431 落在已登记的「guard 自有 431 字节」口径内，故按残余登记而非新增豁免。
**未批准，非已接受差异。**

## 基线依据

Node v22.22.0（Darwin arm64 · raw socket 直接打 `node:http` 无选项 `createServer`；
折叠 / 请求行 / 短 CR 三组在 macmini-01 采集，fix-r3 补的 CR 长度跨档在本机同版本复查）。**十份文件**（五对探针 `.mjs` / 输出 `.out`、两份转录 `.txt`）随本条目入库，
目录 `src/pilotdeck-gateway/tests/fixtures/user-dialog-http-store-1555/node-1576/`，逐文件说明与
复算命令见同目录 `README.md`（此前写在 `_tmp/` 下、被 `.gitignore` 忽略，评审打回为「本仓不可复现」）：

- `node-obs-fold-probe.out`（探针 `node-obs-fold-probe.mjs`）：**短折叠 / 90,000 空格折叠 /
  16,400 B 折叠全部 47 B `400 Bad Request`**（`{"bytes":47,"why":"EOF"|"error:ECONNRESET"}`，
  hex `485454502f312e312034303020426164...`）；同文件 `leading-ows-90000` 对照格仍为
  200 / 141 B，说明拒绝发生在折叠本身而不是填充量。
- `node-reqline-probe.out`（探针 `node-reqline-probe.mjs`）：请求行 90,000 空格（target
  前 / target 后两种形状）、短双空格、plain 四格**全部 200 / 141 B**。
- `cr-ows-probe.out`（探针 `cr-ows-probe.mjs`）：`X: \r  \n` 与 `X:\r \r\n` 均 **47 B 400**；
  同文件 `X: ok` 与 `X:  ok`（冒号后真加一个前导空格）对照格 200 / 96 B，说明 400 来自 CR 本身。
- `cr-ows-length-probe.out`（探针 `cr-ows-length-probe.mjs`，fix-r3 补）：CR 族的**长度跨档**实测——
  `X: \r` + 90,000 空格 + `  \n`（与本 PR 的 Rust 判据同一字节形状）与值长 16,300 / 16,360 /
  16,380 / 16,400 空格四档（跨 Node 16 KiB `maxHeaderSize`）**全部 47 B 400**；90,000 空格
  前导 OWS 对照格 96 B 200。据此「Node 对该形状任意长度都是 47 B 400」不是外推：llhttp 在值内
  CR 处即停，长到 90 KB 也不会先撞 `HPE_HEADER_OVERFLOW`。
- `rss-16x-serialized.txt` 与 `tokio-test-current-thread.txt`：`#[tokio::test]`
  无 flavor 时 tokio-macros 2.6.1 `src/entry.rs:84-90,452-456` 选
  `Builder::new_current_thread()`；实测 `fields-max` 单连 14.1 ms、
  `fields-max-16x` 211.2 ms = **14.98×**。该比值**低于** 16×，因此不能写成「串行下界
  16×」：它说明 16 次解析的每次墙钟比单连格更便宜（连接复用与预热），仍是串行证据
  （真并发应 ≈1×），但不是 16× 的倍数关系。

## Rust 行为

`src/pilotdeck-gateway/src/user_dialog/http_store.rs`（#1576 审查链，head 见 PR 结果块，
fix-r2 在此基础上改 guard 的 CR 状态与峰值探针的树锁）：

- **折叠续行**仍由 `HeaderGuard` 计入 raw 上界，超过 `4 × max + 2 × 8 KiB` 时写 67 B
  431（`header_guard_raw_cap_uses_node_431_bytes`，形状 `X: a\r\n<90,000 SP>b\r\n`）。
  **Node 对同一形状是 47 B 400，不是 200**：真实残余是「Rust 431 vs Node 400」，两个实现
  都拒绝该畸形头，只是状态码与字节不同；R6 写成「Node 该形状 200」低估了 Node 侧的拒绝。
- **请求行分隔符**（target 前 / 后的空格）同样计入 raw 上界：单测
  `header_guard_replays_node_field_budget` 末段断言
  `GET <4×max+2×8 KiB SP> HTTP/1.1\r\n` 触发 431；而 **Node 对 90,000 空格请求行是 200**
  （`node-1576/node-reqline-probe.out`）。这是 R6 未登记的 Node 200 / Rust 431 形状，与折叠
  续行同属「guard 仍转发、但不计入 Node 计数字节」的 raw 上界族。
- **值内 CR**（fix-r2 的中心改动）：guard 在 CR 处关闭 after-colon 可丢窗口。上界以内 hyper
  自己拒（`Err(HeaderValue)`），两侧同为 400（`cr_in_value_is_rejected_like_node`
  断言 400 + 连接关闭，Node 47 B 400 见 `node-1576/cr-ows-probe.out`；400 的**字节形状**
  差异属 R3 / R4 已登记的「malformed 400 / 414 形状」，本条不重复登记）。**越过 raw 上界时
  guard 自己接管**：CR 之后的填充字节虽不计入 Node 计数字节（`discarding_leading_whitespace`
  仍为真），却**逐字节计入 `raw_bytes`**，达到 81,920 B 时 guard 写 67 B 431，而 Node 对该
  形状任意长度都是 47 B 400（llhttp 在 CR 处即停；短形状 / 90,000 空格 / 值长 16,300–16,400
  五档实测见 `node-1576/cr-ows-length-probe.out`）。这是本条新登记的第三族残余，判据
  `cr_in_value_past_the_raw_bound_keeps_the_registered_431`。
- **进程峰值 RSS 探针** `header_budget_peak_rss` 的 `fields-max-16x` 格不是并发：
  `#[tokio::test]` 默认 current-thread，16 个 client / 连接 task 严格串行；实测墙钟
  211.2 ms / 单连 14.1 ms = 14.98×。R6 的「16 路并发下没有线性叠加（+3.30 MiB）」只能读作
  同一线程上依次解析 16 次，不能证明多 worker 并发下的上界；receipt 行现在由
  `Handle::current().runtime_flavor()` 打印真实 flavor（`flavor=CurrentThread`）并有
  `assert_eq!`，把 `#[tokio::test]` 改成 multi-thread 会直接转红，而不是继续自称串行。

## 范围

只更正 R6 的三处表述并补登一条残余，作用面仅限本条：

1. **折叠续行残余的 Node 结局**：R6 §范围与 §机器判据称「Node 该形状 200」。实测 Node 对
   短折叠 / 90,000 空格折叠 / 16,400 B 折叠**一律 47 B 400**
   （`node-1576/node-obs-fold-probe.out`）。残余措辞改为「Rust 431 vs Node 400」：Node 是先
   拒绝该畸形头，不是接受后计数；R6 的「已消除」只覆盖前导 OWS，不覆盖折叠形状。
2. **`fields-max-16x` 的并发标签**：R6 峰值内存表「同上 16 路并发」不成立。该格是
   current-thread 运行时里的 16 次串行解析（`node-1576/rss-16x-serialized.txt`，比值
   14.98×，不是 16× 下界），`+3.30 MiB` 只能说明 16 次串行解析的进程峰值；多线程 worker
   下的叠加上界仍未实测，仍列为待实测。
3. **raw 上界的残余形状清单**：R6 §范围只列折叠续行；同一 PR 的
   `header_guard_replays_node_field_budget` 同时钉住请求行分隔符受 raw 上界约束，而 Node
   对 90,000 空格请求行是 200（`node-1576/node-reqline-probe.out`）。据此补登
   Node 200 / Rust 431 形状：**请求行 target 前 / 后的空格填充超过 raw 上界时 Rust 写
   67 B 431，Node 接受并 200**。
4. **新增 CR 族残余（fix-r2 引入）**：值内 CR 之后的大段填充使 `raw_bytes` 越过上界时，
   Rust 写 67 B 431，Node 写 47 B 400。fix-r2 之前该形状被 guard 改写为合法空值 `X:\r\n`
   交给 hyper（405），同样不等于 Node；fix-r2 之后它归入已经登记的「guard 自有 431 字节」
   口径，仍然**未获批准**，不据此新增任何豁免。

R6 的其余结论不变：前导 OWS 两格已消除、字段数按 Node 计数预算取值、trailer 16 KiB
原始字节上限待实测、每 parse 约 1 MiB 槽向量（`fields-max-16x` 一格按串行解读）。

## 机器判据

- Node 侧证据（入仓、可复算）：`node-1576/` 下五对 `.mjs`/`.out`（含 fix-r3 补的 CR 族长度跨档
  实测）+ 两份 `.txt` 转录，同一 Node v22.22.0 重跑即可复现；不引入新阈值，不改任何测试断言。
- Rust 侧判据（本 PR 内新增的用 ★ 标出）：
  - `header_guard_raw_cap_uses_node_431_bytes`：折叠续行 → 67 B 431。
  - `header_guard_replays_node_field_budget`：请求行分隔符 → raw 上界触发。
  - `header_budget_peak_rss`：`fields-max-16x`，**串行**；receipt 现在打印运行时读出的
    `flavor=CurrentThread` 并断言。
  - `cr_in_value_is_rejected_like_node`（基线已有，本 PR 只改了它旁边的注释）：
    `X: \r  \n` 与 `X:\r \r\n` → 400 + 连接关闭（与 `node-1576/cr-ows-probe.out`
    的 47 B 400 同状态）。
  - ★ `cr_in_value_past_the_raw_bound_keeps_the_registered_431`：CR + 90,000 空格 →
    67 B 431（本条 §范围 4 的残余，固定住而不假装两侧一致；Node 对同一字节形状实测
    47 B 400，见 `node-1576/cr-ows-length-probe.out`）。
- 负控（`tests/fixtures/user-dialog-http-store-1555/negative_controls_1555.py`）：本轮
  **八**变异，名单以该文件的 `cases` 表为准（`--check-anchors` 打印 `8 anchors: ok`）：
  `ows-still-raw-counted`、`ows-dropped-but-raw-counted`、`ows-not-dropped-from-stream`、
  `obs-fold-ows-also-dropped`、`max-headers-back-to-4096`、`open-run-not-finalized`、
  `cr-does-not-close-ows-window`（删掉 CR 处的 `droppable_ows = false` 后
  `cr_in_value_is_rejected_like_node` 必须转红）、
  `raw-cap-never-tripped`（把 `raw_limit` 抬到 `usize::MAX` 后
  `cr_in_value_past_the_raw_bound_keeps_the_registered_431` 必须转红）。★ 为 fix-r2 / fix-r3
  新增的两条；R6 §机器判据 的「六变异」是 fix-r1 轮次的分母快照，三处数字按各自轮次读。
- 装置：`dirty_tree_control_1555.py` 两条判据——`lock-held`（驱动先打印 `starting` 再取锁、
  取到锁才打印 `provenance`；控制持锁期间只允许出现前者，因此「没等到锁」是可判定的而不是
  靠安静窗口猜）与 `dirty-src`（同一次持锁内弄脏一个已跟踪产品源，探针必须在 build 前
  `status=INVALID`、rc=2、无 `build.log`）；还原只写回本进程写入的标记，且用临时文件 +
  `os.replace`，别人未提交的字节原样保留并记 INVALID。`rss_probe_1555.py` 用共享
  `_assert_workspace_sources` 判定干净树，`status` 跟随 minima 覆盖而非只看 failures 列表，
  receipt 的 `flavor` 由 `Handle::current().runtime_flavor()` 读出并有 `assert_eq!`。
