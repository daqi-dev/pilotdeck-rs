## 类别

登记（有意偏差，非判分更正）。#2487（PR #2397 rebase 合并轮 MM
boundary#3 单家 P2）发现：原生进程按 `Options::serves_project`（
`native_process.rs:369`）做单项目隔离——管理面 / 请求面 / 各方法的准入层
都以它拒绝非本进程 `projectKey`——但 always-on 后台运行时的构造不走这层
隔离：`AlwaysOnManager::new` 对全局 `alwaysOn.projects` 的每个 enabled
项目都建 `AlwaysOnRuntime`。本轮已核 TS 基线（见「基线依据」）：TS 同为
按全局配置铺开、全链路无「本进程项目」过滤——Rust 侧该行为是 TS 同构，
非移植漏改。按任务书处置口径（TS 同构 → 登记有意偏差），本件登记该偏差
为**有意**：跨项目铺开是 TS 语义的忠实移植，原生进程的单项目隔离模型
不作用于后台运行时构造这一层。本件不改基础条目与其 -R1/-R2 的任何字节，
不新增任何判分豁免，不改任何代码。

## 基线依据

同基础条目 `A7.8-ALWAYS-ON-BACKGROUND-001`（TS 基线 cc7c4e6，`resources/
PilotDeck`）。本轮对「按全局配置铺开还是按本进程项目收紧」的专项核对
（只读实读，2026-11-10，远端基线 `/home/clawbox-08/ws/pdrs-runner/resources/
PilotDeck`）：

- `src/cli/ProjectAutomationBundle.ts:287-302` `createAlwaysOn`：只要有
  任一 `project.enabled` 就把**整个** `config`（即 `config.alwaysOn`，
  含全部项目）交给 `makeAlwaysOn`，无逐项目过滤；
- `src/always-on/runtime/AlwaysOnManager.ts:110-133` 构造器：
  `for (const [projectKey, project] of Object.entries(options.config.projects))
  { if (!project.enabled) continue; this.runtimes.push(new AlwaysOnRuntime(
  {...})) }` —— 对全局配置的每个 enabled 项目各建一个 runtime；
- `src/cli/pilotdeck.ts:60`：`new ProjectAutomationBundle({ config:
  snapshot.config, ... })` —— bundle 拿到的是完整快照配置；
- 全链路（`pilotdeck.ts` → `ProjectAutomationBundle` → `createAlwaysOn` →
  `AlwaysOnManager` 构造器）无任何「本进程所服务项目」的过滤概念——TS
  CLI 是单进程服务全部项目，不存在进程级项目隔离，按全局配置铺开即 TS
  行为本身。

结论：**TS 同构**。Rust 侧按全局配置铺开不是对 TS 的偏离，是对原生进程
自身单项目隔离模型的偏离（见「Rust 行为」）。

## Rust 行为

按本轮树（基点 `d15ab7719`）实读，行号为现读行号：

- 装配链：`native_process/assembly.rs:1008-1017` 进程唯一的
  `ProjectAutomationBundle::new`，`AlwaysOnConfig::from_section`（`:1013`）
  把整个 `alwaysOn:` 段的 `projects` 名册原样交给 bundle，
  `make_always_on: always_on::native_factory()`（`:1017`）；
  `runtime/always_on/manager.rs:756-780` `AlwaysOnManager::new` 对
  `options.config.projects` 每个 enabled 项目建一个 `AlwaysOnRuntime`
  （`:759` 的循环），共享一个 run-context 注册表——TS
  `AlwaysOnManager.ts:110-133` 的逐项目循环同构。
- 隔离边界：`native_process.rs:369` `Options::serves_project` 只出现在
  管理面 / 请求面 / 各方法的准入层（`management.rs:114,215`、
  `requests.rs:224`、`methods/session_dir.rs:55,442`、`methods/config.rs:163`、
  `services.rs:1517`、`assembly/memory.rs:51` 一带）；always-on 构造链
  （assembly → bundle 工厂 → manager 构造器）零命中。
- 后果（#2487 问题场景）：全局配置 A、B 两项目都 enabled、本进程服务 A
  时，B 的 `AlwaysOnRuntime` 也在本进程构造——B 的 `state.json` / cycle
  index 在本进程 pilot home 下被写（tick 门控链按项目各自跑），B 的
  busy 钩子（`bind_agent_gateway` 的 `is_project_busy` 闭包）也被查询。
  三方法控制面不受此影响：入参带非本进程 `projectKey` 时仍在请求面被
  `serves_project` 拒（`r9_manager_project_not_found` 的信封保持）。

## 范围

- 本件登记的偏差：**always-on 后台运行时构造不按 `serves_project` 收紧**。
  处置为有意保留（TS 同构优先），不收紧、不补过滤。后续若人定要收紧
  （只建所服务项目的 runtime），属新决策，须新开 R 件登记，本件不动。
- 不影响 R1 登记的其余残差（fire 深管留缝、fallback 控制面偏差、无生产
  reload 触发、lease registry 惰性）；不影响 R2 登记的 cron 半口径订正。
- 用户感知：多项目 always-on 配置下，本进程会为非所服务项目跑后台 tick
  并写其状态文件（与 TS 单进程行为一致）；该写入不越过进程自身的
  pilot home 边界。
