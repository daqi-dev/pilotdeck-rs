## 类别

差异消除（连接生命周期）。原条目与 R1 登记的「未实现 keepAliveTimeout、
空闲连接由 60 s 请求头超时兜底」不再成立；Rust 现在按 Node v22.22.0 的
默认行为在 6 s（`keepAliveTimeout` 5 s + `keepAliveTimeoutBuffer` 1 s）
关闭空闲 keep-alive 连接。本轮（fix-r2）另把广告与 hyper 的实际复用决定
对齐：请求体未读的早退响应、HTTP/1.0 响应和 `close()` 中的在途响应不再
广告 keep-alive。

## Rust 行为

`src/pilotdeck-gateway/src/user_dialog/http_store.rs`：

- `:60,:65` 定义 `DEFAULT_KEEP_ALIVE_TIMEOUT = 5 s` 与
  `DEFAULT_KEEP_ALIVE_TIMEOUT_BUFFER = 1 s`；两者之和作为连接空闲期限。
- `KeepAliveTimer`（`:1793`）的状态机：`request_started`（`:1828`）在完整
  请求头到达时清除连接级期限，`response_finished`（`:1841`）在响应体结束
  时武装空闲期限，`read_activity`（`:1854`）重置空闲期限并在首个后续请求
  字节上起算新的 `headersTimeout`，`write_activity`（`:1876`）把响应刷写
  计为活动。
- `KeepAliveBody::drop`（`:1984`）在 hyper 不轮询 body 的路径上补
  `response_finished`：HEAD 响应按 `Encoder::length(0)` 写出后 hyper 直接
  丢弃 body，`is_end_stream()` 已为真的空 body 也不会被 `poll_frame`；
  `finished` 保证每条响应只触发一次。缺这条时连接停在 `Request` 相位、
  两个期限都为 `None`，permit 永不释放。
- `TimeoutStream`（`:1895`）在 `poll_read` 中把到期转成静默 EOF；
  `http1::Builder::header_read_timeout(None)` 关闭 hyper 自带计时，改由该
  状态机从首个请求头字节起算 `headersTimeout`。
- `keep_alive_advertisement`（`:2403`）与 `add_keep_alive_headers`
  （`:2450`）在持久 HTTP/1.1 响应上补齐 Node 的
  `Connection: keep-alive` / `Keep-Alive: timeout=<floor(ms/1000)>`；已有
  `Connection` 头的响应不被覆盖。
- `serve`（`:2277`）在 `:2286` 用 `Incoming::size_hint().exact() != Some(0)`
  判断请求是否还有未读 body。405/404/401 的 precheck（`:2339`）、
  Content-Length 预检 413（`:2350`）、`Limited` 截断 413（`:2362`）与 body
  读取失败 500 都经 `close_if_body_pending`（`:2440`）写显式
  `Connection: close`，不再广告 keep-alive。431/408 仍走
  `empty_response` 的既有 close 对。
- HTTP/1.0（`:2127`）：响应版本固定为 `HTTP/1.0` 并写
  `Connection: close`。这样 hyper 的 `fix_keep_alive` 走 1.0 分支
  `disable_keep_alive`，不会把解析器的 keep-alive 重新写成广告。
- `close()` 在途：service 读到 `shutdown` watch 已置位时跳过广告并写
  close；hyper 的 `graceful_shutdown` 本来就会关连接，跳过广告避免出现
  `connection: close` 与 `Keep-Alive: timeout=5` 并存的矛盾。
- 单请求进行中不运行空闲定时器；请求体仍由 `serve` 的 `requestTimeout`
  约束。

fix-r2 的原始 socket 前后对照：
`_tmp/20261025-issue-679/fix-r2/probe/rust-raw-before.log`（修前：
405/404/401/两种 413 都带 `Connection: keep-alive` + `Keep-Alive: timeout=5`
随后 EOF）与 `rust-raw-after.log`（修后：这些响应只带
`Connection: close`，无 `Keep-Alive`；HTTP/1.0 两种请求也 close）。shutdown
对照见 `rust-shutdown.log`（修前 `connection: close|keep-alive: timeout=5`）
与 `rust-shutdown-after.log`（修后只有 `connection: close`）。

## 范围

仅连接生命周期：空闲 keep-alive 连接、后续请求头的 `headersTimeout` 起点、
请求进行中的空闲定时器抑制，以及持久连接的 `Connection` / `Keep-Alive`
广告头。响应体、状态码、JSON 字节、请求体上限与连接数上限不变。Node 默认
`connectionsCheckingInterval = 30 s`，其 `headersTimeout` 实际在 60–90 s
间检查；本条不声称对齐该检查粒度（归 A7.4-HTTPSTORE-TIMEOUTS-001 的既有
范围），只对齐起点与空闲期限。

首个请求保留既有资源保护：连接建立后 60 s 内未发完头仍会关闭；Node 对
完全不发数据的连接不启动 `headersTimeout`（上条实测 3 s 内未关）。Rust
没有 Node 的无限连接模型，`DEFAULT_MAX_CONNECTIONS = 64` 下必须防止
silent 连接长期占用 permit，故不在本条取消该上限，也不把它算作 keep-alive
差异。

响应头范围补记：此前 Rust 只靠 hyper 默认行为（HTTP/1.1 不显式写
`Connection`），不发送 Node 的 `Keep-Alive: timeout=5`，而注释读起来像两边
已一致；本条一并对齐并登记。广告值只取 `keepAliveTimeout`（5），不是实际
关闭期限 6 s；没有任何 keep-alive 响应时不得覆盖 431/408 的
`Connection: close`。

早退关闭的偏差：Node 会先收完 body（或 `_dump` 掉未读部分）再保持连接；
Rust 为了不在未认证/超限请求上读 body（A7.4-HTTPSTORE-AUTH-BEFORE-BODY-001
的既有偏离），注定无法复用该连接，故回 `Connection: close`。这是既有
早退偏离在连接层的后果，不另立条目；它让线上字节从「广告 keep-alive 后
立刻关」变成一致的 close。

HTTP/1.0 的偏差：Rust 现在与 Node 实测的可观察行为一致（`Connection:
close`，不复用）；响应行仍是 `HTTP/1.0` 而 Node 回 `HTTP/1.1`，这是既有的
hyper 版本回写差异，本条不改也不新登。

shutdown 的偏差：Node 在 `server.close()` 中的在途响应仍广告 keep-alive
且连接可继续复用；Rust 的 hyper `graceful_shutdown` 在本响应后关闭连接，
故只写 `Connection: close`、不广告。两者都保住「广告什么就做什么」，差别
在于关闭时机；要逐字节对齐 Node 需要换掉 hyper 的 graceful 关闭模型，超出
本条（keep-alive 广告）范围，已在 fix-r2 证据中留档。

机制旁及：hyper 的 `header_read_timeout` 不再启用，头部超时统一由
`TimeoutStream` 关闭。A7.4-HTTPSTORE-TIMEOUTS-001 的「头 60 s + 体 300 s」
数值与 A7.4-HTTPSTORE-431-408-SHAPE-001-R1 的「头部超时没有 408」可观察
结论都不变，只是前者不再由 hyper 计时；本条不重登那两条。
