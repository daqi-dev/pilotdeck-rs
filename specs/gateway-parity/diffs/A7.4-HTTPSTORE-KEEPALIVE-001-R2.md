## 类别

差异消除（连接生命周期）。原条目与 R1 登记的「未实现 keepAliveTimeout、
空闲连接由 60 s 请求头超时兜底」不再成立；Rust 现在按 Node v22.22.0 的
默认行为在 6 s（`keepAliveTimeout` 5 s + `keepAliveTimeoutBuffer` 1 s）
关闭空闲 keep-alive 连接。

## TS 依据

cc7c4e6 的 `src/gateway/user-dialog/HttpGatewayUserDialogStore.ts:232,236`
用无选项的 `createServer(...)`，`:243` 只 `listen`，因此全部采用 Node
默认超时。Node v22.22.0 实测（macOS，`_tmp/20261025-issue-679/probe/`）：

- `server.keepAliveTimeout = 5000`、`server.keepAliveTimeoutBuffer = 1000`、
  `server.headersTimeout = 60000`、`server.requestTimeout = 300000`；
- 默认配置下空闲 keep-alive 连接在响应后 **6,003 ms** 被关闭（不是 5,000）；
- 短配置 `keepAliveTimeout=300, buffer=0` 时 303 ms 关闭；
  `keepAliveTimeout=500, buffer=0` 时，部分第二个请求头在响应后 100 ms
  到达，连接在 602 ms 关闭（即最后一个字节后 501 ms），证明该定时器被
  socket 活动重置；
- `headersTimeout=2000`、`keepAliveTimeout=500` 时，响应后 302 ms 开始
  持续发送第二个请求头，连接在开始后 2,015 ms 关闭：`headersTimeout` 从
  第二个请求头的第一个字节重新起算；
- 第二个完整请求在窗口内到达时重新计时（响应后 501 ms 关闭）；
- 完全不发字节的连接在 `headersTimeout=1500 ms` 下 3 s 内没有关闭；连接后
  先空闲 1 s 再发部分头并 trickle 时，关闭发生在首字节后约 1,720 ms，即
  Node 的 `headersTimeout` 从首字节起算（`probe3.mjs`，输出见
  `probe3.out.txt`）；
- 默认持久连接的响应头带 `Connection: keep-alive` 与
  `Keep-Alive: timeout=5`；`Connection: close` 的请求只回
  `Connection: close`，不带 `Keep-Alive`；`keepAliveTimeout=1500` 时广告
  `timeout=1`、`200` 时 `timeout=0`、`0` 时只保留 `Connection:
  keep-alive` 并省略 `Keep-Alive`；HTTP/1.0 请求被回成
  `Connection: close`。

原始输出：`out2.json`、`stderr2.txt`；脚本 `probe2.mjs`。Node 内部实现
（`process.binding('natives')['_http_server']` 导出的 `_http_server.js`
同目录）在 `:486`、`:494`、`:1050` 印证 5 s + 1 s 的 `socket.setTimeout`。
响应头实测在 `_tmp/20261025-issue-679/fix-r1/node-keepalive/probe.mjs`、
`probe.out.txt` 与 `probe-timeout-values.mjs`、`probe-timeout-values.out.txt`
（Node v22.22.0，原始响应字节）。

## Rust 行为

`src/pilotdeck-gateway/src/user_dialog/http_store.rs`：

- `:60,:65` 定义 `DEFAULT_KEEP_ALIVE_TIMEOUT = 5 s` 与
  `DEFAULT_KEEP_ALIVE_TIMEOUT_BUFFER = 1 s`；`:2079` 以两者之和作为连接
  空闲期限。
- `KeepAliveTimer`（`:1793`）的状态机：`request_started`（`:1828`）在完整
  请求头到达时清除连接级期限，`response_finished`（`:1841`）在响应体结束
  时武装空闲期限，`read_activity`（`:1854`）重置空闲期限并在首个后续请求
  字节上起算新的 `headersTimeout`，`write_activity`（`:1876`）把响应刷写
  计为活动。
- `KeepAliveBody::drop`（`:2029`）在 hyper 不轮询 body 的路径上补
  `response_finished`：HEAD 响应按 `Encoder::length(0)` 写出后 hyper 直接
  丢弃 body，`is_end_stream()` 已为真的空 body 也不会被 `poll_frame`；
  `finished` 保证每条响应只触发一次。缺这条时连接停在 `Request` 相位、
  两个期限都为 `None`，permit 永不释放。
- `TimeoutStream`（`:1895`）在 `poll_read` 中把到期转成静默 EOF；`:2139`
  关闭 hyper 自带的 `header_read_timeout`，改由该状态机从首个请求头字节
  起算 `headersTimeout`，避免空闲等待消耗后续请求的 60 s 预算。
- `keep_alive_advertisement`（`:2364`）与 `add_keep_alive_headers`
  （`:2387`）在持久 HTTP/1.1 响应上补齐 Node 的
  `Connection: keep-alive` / `Keep-Alive: timeout=<floor(ms/1000)>`；已有
  `Connection: close` 的 431/408 响应不被覆盖。
- 单请求进行中不运行空闲定时器；请求体仍由 `serve` 的 `requestTimeout`
  约束。

## 范围

仅连接生命周期：空闲 keep-alive 连接、后续请求头的 `headersTimeout` 起点、
请求进行中的空闲定时器抑制，以及持久连接的 `Connection` / `Keep-Alive`
广告头。响应体、状态码、JSON 字节、请求体上限与连接数上限不变。Node 默认
`connectionsCheckingInterval = 30 s`，其 `headersTimeout` 实际在 60–90 s
间检查；本条不声称对齐该检查粒度（归 A7.4-HTTPSTORE-TIMEOUTS-001 的既有
范围），只对齐起点与空闲期限。

首个请求保留既有资源保护：连接建立后 60 s 内未发完头仍会关闭；Node 对
完全不发数据的连接不启动 `headersTimeout`（上条实测 3 s 内未关）。Rust
没有 Node 的无限连接模型，`DEFAULT_MAX_CONNECTIONS = 64` 下必须防止
silent 连接长期占用 permit，故不在本条取消该上限，也不把它算作 keep-alive
差异。

响应头范围补记：此前 Rust 只靠 hyper 默认行为（HTTP/1.1 不显式写
`Connection`），不发送 Node 的 `Keep-Alive: timeout=5`，而注释读起来像两边
已一致；本条一并对齐并登记。广告值只取 `keepAliveTimeout`（5），不是实际
关闭期限 6 s；没有任何 keep-alive 响应时不得覆盖 431/408 的
`Connection: close`。

机制旁及：hyper 的 `header_read_timeout` 不再启用，头部超时统一由
`TimeoutStream` 关闭。A7.4-HTTPSTORE-TIMEOUTS-001 的「头 60 s + 体 300 s」
数值与 A7.4-HTTPSTORE-431-408-SHAPE-001-R1 的「头部超时没有 408」可观察
结论都不变，只是前者不再由 hyper 计时；本条不重登那两条。

## 机器判据

`src/pilotdeck-gateway/src/user_dialog/http_store_tests.rs`：

- `:544 idle_keep_alive_connections_close_at_keep_alive_timeout`：200 ms
  空闲期限，2 s 内必须 EOF。
- `:578 default_idle_keep_alive_connection_closes_after_six_seconds`：真实
  默认值，响应后 5.5–8 s 内关闭（实测约 6.0 s）。
- `:607 partial_next_request_resets_keep_alive_inactivity_timer`：部分第二个
  请求头重置空闲期限（旧期限后仍存活，新期限后关闭）。
- `:645 next_request_headers_timeout_starts_at_first_byte`：部分第二个请求头
  必须由从首字节起算的 300 ms `headersTimeout` 关闭，而不是等 2 s 空闲期。
- `:683 keep_alive_timeout_does_not_close_active_request`：150 ms 空闲期限下
  慢请求体（300 ms 后继续）仍返回 200。
- `:723 keep_alive_advertisement_matches_node_v22`：广告值取
  `floor(keepAliveTimeout/1000)`，0 时省略 `Keep-Alive`，HTTP/1.0 与
  `Connection: close` 不广告，431/408 的 `Connection: close` 不被覆盖。
- `:784 persistent_responses_advertise_keep_alive_like_node`：线级断言持久
  405 与 HEAD 响应带 `Connection: keep-alive` / `Keep-Alive: timeout=5`，
  close 请求不带。
- `:822 head_requests_arm_idle_timer_and_release_permits`：两个 HEAD 连接
  占满 2 个 permit，200 ms 空闲后均 EOF，随后新请求得到 405（permit 已
  释放）。
- `:885 empty_response_body_arms_idle_timer_without_a_body_poll`：204 空 body
  经生产 `TimeoutStream`，200 ms 后 EOF 且 semaphore permit 归还。
- `:950 client_read_shutdown_still_releases_head_connection_permit`：客户端
  提前 `shutdown(Read)` 后无法观察 EOF，仍必须在空闲期限后释放唯一 permit。
- `:996 dropping_a_fully_polled_body_does_not_rearm_the_idle_deadline`：
  已轮询完的 body 再 Drop 不得重置期限（`finished` 只触发一次）。
- `:1023 default_connection_timeouts_match_node_v22` 固定四个默认常量与
  6 s 有效期限。
