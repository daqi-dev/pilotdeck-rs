## 类别

差异消除（连接生命周期）。原条目与 R1 登记的「未实现 keepAliveTimeout、
空闲连接由 60 s 请求头超时兜底」不再成立；Rust 现在按 Node v22.22.0 的
默认行为在 6 s（`keepAliveTimeout` 5 s + `keepAliveTimeoutBuffer` 1 s）
关闭空闲 keep-alive 连接。

## TS 依据

cc7c4e6 的 `src/gateway/user-dialog/HttpGatewayUserDialogStore.ts:232,236`
用无选项的 `createServer(...)`，`:243` 只 `listen`，因此全部采用 Node
默认超时。Node v22.22.0 实测（macOS，`_tmp/20261025-issue-679/probe/`）：

- `server.keepAliveTimeout = 5000`、`server.keepAliveTimeoutBuffer = 1000`、
  `server.headersTimeout = 60000`、`server.requestTimeout = 300000`；
- 默认配置下空闲 keep-alive 连接在响应后 **6,003 ms** 被关闭（不是 5,000）；
- 短配置 `keepAliveTimeout=300, buffer=0` 时 303 ms 关闭；
  `keepAliveTimeout=500, buffer=0` 时，部分第二个请求头在响应后 100 ms
  到达，连接在 602 ms 关闭（即最后一个字节后 501 ms），证明该定时器被
  socket 活动重置；
- `headersTimeout=2000`、`keepAliveTimeout=500` 时，响应后 302 ms 开始
  持续发送第二个请求头，连接在开始后 2,015 ms 关闭：`headersTimeout` 从
  第二个请求头的第一个字节重新起算；
- 第二个完整请求在窗口内到达时重新计时（响应后 501 ms 关闭）；
- 完全不发字节的连接在 `headersTimeout=1500 ms` 下 3 s 内没有关闭；连接后
  先空闲 1 s 再发部分头并 trickle 时，关闭发生在首字节后约 1,720 ms，即
  Node 的 `headersTimeout` 从首字节起算（`probe3.mjs`，输出见
  `probe3.out.txt`）。

原始输出：`out2.json`、`stderr2.txt`；脚本 `probe2.mjs`。Node 内部实现
（`process.binding('natives')['_http_server']` 导出的 `_http_server.js`
同目录）在 `:486`、`:494`、`:1050` 印证 5 s + 1 s 的 `socket.setTimeout`。

## Rust 行为

`src/pilotdeck-gateway/src/user_dialog/http_store.rs`：

- `:60,:65` 定义 `DEFAULT_KEEP_ALIVE_TIMEOUT = 5 s` 与
  `DEFAULT_KEEP_ALIVE_TIMEOUT_BUFFER = 1 s`；`:2056` 以两者之和作为连接
  空闲期限。
- `KeepAliveTimer`（`:1786`）的状态机：`request_started`（`:1821`）在完整
  请求头到达时清除连接级期限，`response_finished`（`:1834`）在响应体结束
  时武装空闲期限，`read_activity`（`:1847`）重置空闲期限并在首个后续请求
  字节上起算新的 `headersTimeout`，`write_activity`（`:1869`）把响应刷写
  计为活动。
- `TimeoutStream`（`:1888`）在 `poll_read` 中把到期转成静默 EOF；`:2110`
  关闭 hyper 自带的 `header_read_timeout`，改由该状态机从首个请求头字节
  起算 `headersTimeout`，避免空闲等待消耗后续请求的 60 s 预算。
- 单请求进行中不运行空闲定时器；请求体仍由 `serve` 的 `requestTimeout`
  约束。

## 范围

仅连接生命周期：空闲 keep-alive 连接、后续请求头的 `headersTimeout` 起点、
请求进行中的空闲定时器抑制。响应内容、状态码、JSON 字节、请求体上限与
连接数上限不变。Node 默认 `connectionsCheckingInterval = 30 s`，其
`headersTimeout` 实际在 60–90 s 间检查；本条不声称对齐该检查粒度（归
A7.4-HTTPSTORE-TIMEOUTS-001 的既有范围），只对齐起点与空闲期限。

首个请求保留既有资源保护：连接建立后 60 s 内未发完头仍会关闭；Node 对
完全不发数据的连接不启动 `headersTimeout`（上条实测 3 s 内未关）。Rust
没有 Node 的无限连接模型，`DEFAULT_MAX_CONNECTIONS = 64` 下必须防止
silent 连接长期占用 permit，故不在本条取消该上限，也不把它算作 keep-alive
差异。

机制旁及：hyper 的 `header_read_timeout` 不再启用，头部超时统一由
`TimeoutStream` 关闭。A7.4-HTTPSTORE-TIMEOUTS-001 的「头 60 s + 体 300 s」
数值与 A7.4-HTTPSTORE-431-408-SHAPE-001-R1 的「头部超时没有 408」可观察
结论都不变，只是前者不再由 hyper 计时；本条不重登那两条。
