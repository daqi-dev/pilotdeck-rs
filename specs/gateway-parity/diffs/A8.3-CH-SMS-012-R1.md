## 类别

更正（陈述与实测相反，非差异变化）：`A8.3-CH-SMS-012.md:95-96` 的结论句
「所以两侧都不在 `stop()` 里等连接」写反了 Node 侧。同一条残差的前两句
（`A8.3-CH-SMS-012.md:92-95`）已经写明「`SmsHandle::stop()` 只 await accept
循环、**不等** detach 的连接任务，而 Node 的 `server.close()` 会等」，紧接着的
结论句却把两侧并列成「都不等」，与前两句自相矛盾。

正确表述：**两侧不等价**——Rust 的 `stop()` 立即返回、在途连接任务 detach；
Node/TS 的 `stop()` **阻塞在 `server.close()` 回调**上，且 close 时
`httpServerPreClose` 清掉 connections checker，半截头连接从此不再收到 408，
`stop()` 在 200 s 观察窗内**始终未 resolve**（实测 `stopWaitedMs=199001`）；
观察窗到点由探针自己 `socket.destroy()`，close 回调才与 destroy 同一刻
resolve——「不销毁还会等多久」未测，199,001 ms 是**下界不是上界**。紧随其后的
「关闭方向相反」结论仍然成立，但它不能由「都不等」推出——恰恰是「一方不等就
返回、另一方一直等到客户端离开」。

## Rust 行为

`src/pilotdeck-gateway/src/channel/sms/mod.rs:307-328` 的 `SmsHandle::stop()`
只 `server.shutdown.send(true)`（`:322`）后 `server.task.await`（`:323`）；
`server.task` 是 **accept 循环**的 JoinHandle（`:587`），循环命中
`shutdown_rx.changed()` 即 `break`（`:590`）。每条连接的 `serve_connection`
由 accept 分支 `tokio::spawn` 后直接丢弃 JoinHandle（`:594`），`SmsShared`
（`:238-252`）没有 JoinSet、没有连接表，`stop()` 结构上无从等它们，也不 abort。
因此 `stop()` 立即返回，在途连接 detach，各自跑到自己的期限才结束：**头读
60 s、体读 300 s** 的依据见 `:614-620`（只装 `header_read_timeout`）；响应**写**
阶段是否受这两条期限覆盖未实测，因此不排除 detach 连接活得更久——**与 TS 相反**。
