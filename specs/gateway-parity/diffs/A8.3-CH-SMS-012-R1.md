## 类别

更正（陈述与实测相反，非差异变化）：`A8.3-CH-SMS-012.md:95-96` 的结论句
「所以两侧都不在 `stop()` 里等连接」写反了 Node 侧。同一条残差的前两句
（`A8.3-CH-SMS-012.md:92-95`）已经写明「`SmsHandle::stop()` 只 await accept
循环、**不等** detach 的连接任务，而 Node 的 `server.close()` 会等」，紧接着的
结论句却把两侧并列成「都不等」，与前两句自相矛盾。

正确表述：**两侧不等价**——Rust 的 `stop()` 立即返回、在途连接任务 detach；
Node/TS 的 `stop()` **阻塞在 `server.close()` 回调**上，且 close 时
`httpServerPreClose` 清掉 connections checker，半截头连接从此不再收到 408
（零字节连接同理由 `clearInterval` 结构推出，未单独实测 408），
`stop()` 在 200 s 观察窗内**始终未 resolve**（实测 `stopWaitedMs=199001`）；
观察窗到点由探针自己 `socket.destroy()`，close 回调与 destroy 实测落在同一
毫秒（单次观测；跨毫秒不影响结论）——「不销毁还会等多久」未测，199,001 ms 是
**下界不是上界**。紧随其后的
「关闭方向相反」结论仍然成立，但它不能由「都不等」推出——恰恰是「一方不等就
返回、另一方一直等到客户端离开」。

## Rust 行为

`src/pilotdeck-gateway/src/channel/sms/mod.rs:307-328` 的 `SmsHandle::stop()`
只 `server.shutdown.send(true)`（`:322`）后 `server.task.await`（`:323`）；
`server.task` 是 **accept 循环**的 JoinHandle（`:587`），循环命中
`shutdown_rx.changed()` 即 `break`（`:590`）。每条连接的 `serve_connection`
由 accept 分支 `tokio::spawn` 后直接丢弃 JoinHandle（`:594`），`SmsShared`
（`:238-252`）没有 JoinSet、没有连接表，`stop()` 结构上无从等它们，也不 abort。
因此 `stop()` 立即返回，在途连接 detach，各自跑到自己的期限才结束：**头读
60 s** 的依据见 `:614-620`（只装 `header_read_timeout`）；**体读 300 s** 的依据
见 `:66` 的 `DEFAULT_REQUEST_TIMEOUT = 300 s`、`:389` 的取值与 `:900` 的
`tokio::time::timeout(shared.request_timeout, body_read)`。**读**阶段受这两条期限
覆盖；handler 内的出站调用与响应**写**不在其内（未实测），因此不排除 detach
任务活得更久——**与 TS 相反**。

## 机器判据

本条不新增也不修改机器判据（原条与更正条都是未批准登记；判据覆盖缺口由
#1955 的 `head_timeout` 用例与账本状态共同承受）。更正所依赖的「`stop()` 不等
连接」这一事实目前只有代码结构为据、没有配对用例，该测试缺口登记在 #2035。

- 更正依据可重跑：`node _tmp/20261107-issue-1955/smoke/ts-stop-drain.mjs`
  （Node v22.22.0）。重跑前置：主仓 `resources/`（脚本按绝对路径加载真实
  `SmsChannel`）、端口 18781 空闲、**同一时刻只跑一个探针**（端口与输出名共用），
  输出写到按 run 唯一化的新文件名（如 `ts-stop-drain-<runid>.out`），
  `ts-stop-drain.out` / `ts-stop-drain-zero.out` 是已封存原件，不覆盖。
  首行 JSON 的 `headersTimeout` 字段为 60000，是本轮确实连到真实 `SmsChannel`
  监听器的证据。
- **观察窗下限**：`PROBE_DEADLINE_MS` 默认 200,000，且必须明显大于
  `STOP_AFTER_MS`（脚本内 1,000 ms）——至少 `> STOP_AFTER_MS + 建连余量`。
  要复现「0 字节 / 没有任何 408」这一半结论，窗口必须**严格大于** accept +
  90 s（60 s `headersTimeout` + 一个 30 s checker 网格，见 `A8.3-CH-SMS-011`
  残差 1）**再加过冲**：零字节连接的 408 实测落在 90,004 ms，所以下限取
  **≥ 95 s**（保守取 ≥ 120 s，即两个网格）。窗口 ≤ 90 s 只能复现「`stop()` 在
  窗口内未 resolve」，**不能**用来支持「无 408」——短窗下的 0 字节是必然而非证据。
- **判废条件**（任一命中即作废重跑）：首行 JSON 的 `headersTimeout` 字段不是
  60000；`stopResolvedMs` / `stopWaitedMs` / `connectionEndedMs` 任一为 `null`
  （探针在 deadline 处先 resolve 再打日志，`null` 说明观测未走完）；
  `stopResolvedMs < stopCalledMs` 或 `connectionEndedMs < stopCalledMs`
  （窗口短于 stop 调用时刻，连接在 `stop()` 前就没了）；或
  `stopWaitedMs < (PROBE_DEADLINE_MS − stopCalledMs) − 10 ms`（有效运行不会
  早于 deadline 到期，提前 resolve 说明连接被提前关闭或端口被别人占了、走到的
  不是真实 `SmsChannel`）。`.out` 首行不记录窗口值，但窗口可由
  `stopCalledMs + stopWaitedMs` 反推（±数毫秒过冲）；重跑仍建议把本次
  `PROBE_DEADLINE_MS` 与输出一并留档，输出用 `>` 独占创建重定向（不要 `tee`），
  有效性只看首行与上述判废条件、不看退出码。`stop()` 未 resolve 时探针的
  `portProbe` 会一直轮询，重跑须给进程加外部超时兜底。
- 本条不点名可判分用例：现状 sms 用例（如
  `channel::sms::head_timeout_tests::half_sent_head_is_closed_at_the_deadline_and_leaves_no_task`）
  只覆盖「连接自己能到期」，**不覆盖**「`stop()` 返回后连接仍 detach 在跑」；
  该缺口已登记 #2035。
- Rust 侧为现有代码结构，直接可核：
  `src/pilotdeck-gateway/src/channel/sms/mod.rs:307-328`、`:587`、`:590`、
  `:594`、`:238-252`；本条不改变任何实现行为。
- `python3 -I scripts/gateway-parity/check_frozen.py --base origin/main` 通过
  （只新增文件，不改既有字节）。
