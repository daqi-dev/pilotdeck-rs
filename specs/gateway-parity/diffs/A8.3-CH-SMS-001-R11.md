## 类别

更正（覆盖形状被后续轮次改变，非差异变化）：`A8.3-CH-SMS-001-R10.md` 把
`sms-oracle-null-sentinel` 登记为「绑 `null_sentinels_are_absence_for_every_sentinel_field`
一条测试」，并把 `recorded_present` 的覆盖写成 `#1813` 的六个字段。`#1879`
把同一个开关改为**逐字段列表绑定**（12 条测试、12 条锚点）、把
`sms-oracle-recorded-log-level` / `sms-oracle-recorded-log-text` 从单测试改为
「错型 + 缺席」双测试列表绑定、把 `recorded_present` 扩到 17 个读取点
（`OLD_NULL_REJECTING_FIELDS` 11 个字段，含同签名的 `extra`）。开关总数仍 66，`--check` 仍打印
`66 switch anchors and bindings checked`；按 `-R10` 的绑定形状字面核对会判红
（`check_frozen.py` 只校 ledger 字节 append-only，不校判据正文），故本条登记
新形状。`-R10` 原字节不动，本目录只新增本文件。

**本件不登记任何 Rust↔TS 偏离；本单改动全在测试侧，产品代码零改动，金样读值不变。**

三列依据（改前 Rust / TS 侧 / 改后 Rust）：

| | |
|---|---|
| 改前 Rust | `sms/tests.rs` 的 `recorded_header_map_checked` / `recorded_stop_reason_checked` 直接用 `value.get("headers")` / `value.get("reason")`；显式 `null` 进 `recorded_checked` 后按 `is_object` / `as_str` 判错型 |
| TS 侧 | `generate.mts:335` `effectiveHeaders` 写 `{ ...(step.headers ?? {}) }`（与 `env: definition.env ?? {}` 同签名）；录制端在 `generate.mts:350` 把 `headers` 换成 `effectiveHeaders` 的结果再写进 step，`generate.mts:887` 的 `REQUEST(step.body, step.headers, …)` 直接消费这个归一化对象、自己不再做 `??`，所以手改成 `null` 的 step 与缺席同义；`generate.mts:264` 的 `stop = (reason?) => …(reason === undefined ? {} : {reason})` 允许录出 `{reason: null}`，处理器读 `reason ?? "no reason"` |
| 改后 Rust | 两者都走 `recorded_present(value, "headers" / "reason")`，显式 `null` 读成缺席并与 TS 默认同结论；`OLD_NULL_REJECTING_FIELDS` 含这两个字段，`sms-oracle-null-sentinel` 变异时恢复旧的 fail-closed 读法 |

同一判据还覆盖 `extra`：`generate.mts:323` / `:337` 的 `definition.extra ?? {}` 与
`env: definition.env ?? {}` 同签名，但 `recorded_extra_checked` 仍直接
`value.get("extra")`，手改 `"extra": null` 会报 `#1339 extra must be an object, got null`
——与 `env: null` 读成缺席自相矛盾。改走 `recorded_present` 后两者一致。

签名场景的边界：`sign: true` 的 request 步由 `effectiveHeaders`（`generate.mts:336`）
把 `X-Twilio-Signature` 烘进录制后的 headers，Rust 侧重放录制字节、不重新签名；因此
「录制产物里的 `headers: null`」只能来自手改，且会丢掉已录签名、让该例以响应不符失败，
不会假通过。本次只改这种手改场景的失败形态（类型错 → 缺 header），现有 55 例读值不变。
