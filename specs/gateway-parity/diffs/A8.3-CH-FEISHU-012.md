## 类别

竞态/时序差异（未批准）：`/new` 重置与**已在跑的**入站 drainer 交错时，批次条目的
收尾归属不同。TS 按 `chatId` 无条件删除条目，可能删掉重置之后新建的批次，导致该批次里的
消息丢失；Rust 按批次 `id` 只删自己那一个，替代批次继续由它自己的定时器排空。

本条目**不涉及**定时器作废语义：先前一版草稿按「Node 的 `clearTimeout` 对已到期、尚未
执行的回调无效」登记差异，该前提已被实测否证（Node v22.22.0 / ICU 78.2，
`_tmp/20261107-issue-1329/node-cleartimeout-probe.txt`：Case C 输出 `C: c1-start`，
后插入的同到期定时器未执行；Case B 微任务里清除同样生效），那一版已整条撤回，不是本条的更正。

## 基线依据

固定基线 `cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85`，Node v22.22.0，
`src/adapters/channel/feishu/FeishuChannel.ts`：

- `:335-349` `enqueueInboundMessage`：按 `chatId` 取批次对象（没有就新建），
  `push` 消息，`clearTimeout` 旧定时器后重设。

  ```ts
  const batch = this.inboundBatches.get(input.chatId) ?? { messages: [], draining: false };
  batch.messages.push(input);
  if (batch.timer) clearTimeout(batch.timer);
  batch.timer = setTimeout(() => {
    batch.timer = undefined;
    void this.drainInboundBatch(input.chatId).catch(...);
  }, shouldBatchFeishuMessage(input) ? FEISHU_MULTI_ATTACHMENT_BATCH_MS : 0);
  batch.timer.unref?.();
  this.inboundBatches.set(input.chatId, batch);
  ```

- `:411-434` `drainInboundBatch(chatId)`（`finally` 在 `:423-433`）：先按 `chatId` 取批次对象并置 `draining`，
  `while (batch.messages.length > 0)` 循环 `splice(0)` 取走并处理；`finally` 里

  ```ts
  batch.draining = false;
  if (batch.messages.length === 0) {
    this.inboundBatches.delete(chatId);
  } else {
    this.inboundBatches.set(chatId, batch);
    void this.drainInboundBatch(chatId).catch(...);
  }
  ```

  关键点：`finally` 里判断的是**自己持有的那个** `batch` 对象的消息数，删除时用的却是
  **`chatId` 这个键**。两者在重置/新建交错时不再指向同一个对象。

- `:528-537` `resetChatInteractionState`：`clearTimeout(batch?.timer)` 后
  `this.inboundBatches.delete(chatId)`。

交错场景（全部落在源码控制流内，无需额外交互）：

1. drainer `D` 取走批次 `B` 的消息，`await this.processInboundMessages(group)`。
2. 该 chat 进来 `/new` → `resetChatInteractionState` → `clearTimeout(B.timer)` +
   `delete(chatId)`（`B` 已不在表里）。
3. 同一 await 窗口里再来一条普通消息 `m2` → `enqueueInboundMessage` 取不到条目，
   新建批次 `B2 = { messages: [m2] }`，`set(chatId, B2)` 并装定时器。
4. `D` 处理完回到 `while`，`B.messages` 为空 → 退出循环 → `finally`：
   `B.messages.length === 0` → `this.inboundBatches.delete(chatId)` —— 删掉的是 **`B2`**。
5. `B2` 的定时器到期 → `drainInboundBatch(chatId)` → `get(chatId)` 为空 → 直接返回。

结果：`m2` 既不在表里、也没有 drainer 认领，TS 上永久丢失（直到下一条消息创建一个空批次时
才会被顺带创建，但 `m2` 不会回来）。

**用户可感知后果**：用户在 `/new` 之后、旧一轮尚未收尾时紧接着发的那条消息，在 TS 基线里
**被静默吞掉**（不回复、不报错，日志里也没有痕迹）；同一交错在 Rust 侧正常回复。

## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/mod.rs`（符号锚点，用 `grep -n` 复算）：

- `async fn drain_inbound_batch`：入队处取到 `batch.id` 与 `timer_seq` 后才认领批次；
  循环体每次 `state.batches.get_mut(chat_id)`，只有 `batch.id == batch_id` 且非空才取走消息，
  否则 `break`（注释写明「A batch replaced under us (`/new` removed the entry, then a new
  message created a fresh one) belongs to another drainer: stop, never take its messages.」）。
- 收尾：`let done = state.batches.get(chat_id).is_none_or(|batch| batch.id != batch_id || batch.messages.is_empty());`
  然后在 `state.batches.get(chat_id).is_some_and(|batch| batch.id == batch_id)` 为真时才
  `remove(chat_id)` —— **只删自己启动时那一个批次**，替代批次留给它自己的定时器/drainer。
- `fn reset_chat_interaction_state`：`state.batches.remove(chat_id)`，与 TS `:534-536` 同形。

因此上述交错在 Rust 侧的结果是：`D` 收尾时发现 `id` 不符，不动 `B2`；`B2` 的定时器
按 `(id, timer_seq)` 通过守卫、取走 `m2` 并处理 —— **消息不丢**。

方向：这一处 Rust 比 TS 更严格（TS 会丢一条消息）。按「旧实践迁就新理念」，不复刻该缺陷，
登记为差异并保持未批准状态。

## 范围

仅覆盖「`/new` 重置发生在 drainer 的某个 `await` 期间，且重置后、drainer 收尾前该 chat
又有新消息入队」这一种交错。不含：

- 定时器作废（两侧等价，见上）；
- 同一批次的正常重排空（TS `else` 分支的 `set` + 递归 re-drain 与 Rust 的原地循环等价，
  `A8.3-CH-FEISHU-012` 不覆盖也不否认这一等价性）；
- `/new` 之外的任何路径（`reset_chat_interaction_state` 只有 `/new` 一个调用点）。

## 机器判据

- **当前无用例钉住**：13 场景金样（`tests/fixtures/channel-feishu/oracle.json`）不含
  「drain 在飞 + `/new` + 新消息」的交错；`negative_controls.py` 的 10 条变异也没有一条
  触及该收尾判断。缺口见 #2055（P2-跟进，前置于 #1329 后续节点）。
- 本条目**不得**被当作「两侧等价」的依据；摘掉 Rust 收尾的 `id` 检查不会让任何现有用例转红，
  所以不能据此验收。要钉住需要可控时序的组件用例（在 `process_inbound_messages` 的
  await 点插入 `/new` 与第二条入队，断言第二条消息仍被处理）。
- 复核用命令（在 `src/pilotdeck-gateway/src/channel/feishu` 下）：

  ```

  ```
