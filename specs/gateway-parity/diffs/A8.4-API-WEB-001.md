## 类别

传输层差异（待批）：#1348 的 api-web 组件（`/api/web/projects`、
`/api/web/projects/:key`、`/api/web/projects/:key/files/*`）挂在 #1209
原生监听器的同一 hyper 1.7.0 编解码后面，继承 A8.4-NATIVE-HTTP-001 已登记
的全部帧级/头级呈现差异（头名大小写、chunk 大小十六进制、HTTP/1.0 状态行、
空体 `content-length: 0`），回放按同一组归一化规则折叠后 78 个 cell 字节
一致，`http10` 钉死为继承的状态行差异。本条新增登记 2 项该组件路径上的
残余：

1. files 分支上项目 key 的坏百分号（`decodeURIComponent` 在 describe 的
   try 之外）；
2. `GET /api/web/projects` 对 `listProjects` 拒绝的处理（TS 裸 await，无
   try/catch）。

两项在 TS 侧同为「unhandled rejection、一个响应字节都不写」的表现，Rust
侧都答 500 `internal_error`。组件未接线（W0 #1305 拆分发、接线另单），差异
只影响金样矩阵外被独立测试钉死的格，不构成对拍豁免。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0 / ICU
78.2。TS 侧 `adapters/web/httpRouter.ts`：

- describe 分支的 `decodeURIComponent(key)` 在 try 内，坏百分号落 404
  `project_not_found` "URI malformed"（金样 cell `project-describe-badpct`
  实测）；
- files 分支的同一调用在 try 外，`URIError` 逃出 route handler（残余 1）；
- projects 分支 `httpRouter.ts:39-43` 是裸 await
  `const result = await options.gateway.listProjects();`，没有 try/catch；
  上游 `GatewayServer.ts:64-65` 以 `void handleHttpRequest(...)` 丢弃
  handler 的 promise（残余 2）。

两处逃出的拒绝都没有任何代码写响应，金样里因此没有对应 cell（README
「不在金样里的一格」）；projects 分支这一格即使想录也录不了——金样生成器
以独立 `startGatewayServer` 起服务、不装全局监听器，拒绝会直接终止生成
进程（见下方实测 default 行）。HTTP/1.0 一格：Node 对 HTTP/1.0 请求始终
写 `HTTP/1.1` 状态行 + `Connection: close` + 无 framing 的 close 定界体，
金样 cell `http10` 实测；先例 A8.4-NATIVE-HTTP-001 与
A8.4-MODULE-HOST-001 的同名继承项。

### 残余 1 / 残余 2 的 TS 症状实测（node v22.22.0）

探针 `_tmp/20261106-issue-1348/ts-probe3/`（`list-reject-server.mjs` +
`list-reject-client.mjs`，服务端与客户端分进程，客户端才能读到崩进程后的
连接结局；原始日志 `run.log`、`client-<mode>.log`、`server-<mode>.log`）。
同一 handler 形状下三种宿主配置，客户端看到的都是**零响应字节**：

```
mode=default（无监听器——独立 startGatewayServer，金样生成器/probe2.mts 的形态）
  client  elapsed=7ms bytes=0 closed=true
  server  rc=1  Uncaught Error: catalog exploded
          （Node 默认 --unhandled-rejections=throw，进程终止）
mode=swallow（probe2.mts 自装的监听器，只打印）
  client  elapsed=1205ms bytes=0 closed=false
  server  UNHANDLED-REJECTION Error: catalog exploded（进程存活，连接一直开着）
mode=exit（CLI `src/cli/pilotdeck.ts:271-274`：trackError + shutdownAndExit(1)）
  client  elapsed=5ms bytes=0 closed=true
  server  rc=1  UNHANDLED-REJECTION … / SHUTDOWN-EXIT-1
```

结论：**任何配置下 TS 都不写响应**；连接是「挂着等」还是「立刻关」取决于
该进程有没有全局 `unhandledRejection` 监听器、监听器做什么。残余 1 与残余
2 共用这一条实测，不再各自外推。

## Rust 行为

`src/pilotdeck-gateway/src/api_web.rs`：

- 残余 1：files 分支上 key 的坏百分号是 `decode_uri_component` 的 `Err`，
  不复制 Node 的挂起——映射成 500 `internal_error` "URI malformed"
  （`project_key_malformed_percent_is_500` 钉死）；
- 残余 2：`list_projects()` 的 `Err` 映射成 500
  `internal_error` + 错误的 `to_string()`
  （`catalog_list_failure_is_500` 钉死）。

理由是零字节挂起不可复用 `serve` 的应答通道，且会占住连接直到超时；两条
都在钉死测试里注明 TS 侧为 unhandled rejection 残余。

HTTP/1.0 一格：hyper 1.7.0 对 `Version::HTTP_10` 写 `HTTP/1.0` 状态行，
其余（`Connection: close`、无 framing 的 close 定界体）与 Node 一致
（`http10_close_delimited_response` 钉死）。

## 范围

与状态行呈现（组件范围，未接线，`native_process/{requests,services,
assembly}.rs` 不受影响）。`/api/web`（无尾斜杠）落 native 纯文本 404 属

拒绝对 500），一项是状态行差异。
