## 类别

有意改进（安全加固），对 TS 基线的可观测偏离。TS 的 `readBody` 无上限；Rust 侧在
验签之前给 `POST *` 的请求体加 1 MiB 上限，超限的连接以**零响应字节**结束（不是
413）。人拍板 #1837「A」要求装配该渠道前必须解决无上限问题；本条是提前落地的
**候选**，批准状态见「批准记录」段末的加粗声明行（当前为**待批**），不得当作已批准
或已接受差异引用。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。

`src/adapters/channel/wecom-callback/WeComCallbackChannel.ts:59-65`
`readBody` 用 `req.on("data", (c) => chunks.push(...))` 累积、`Buffer.concat`
拼接，**没有任何字节上限**；`:176` 的 `POST` 分支 `const body = await readBody(req)`
在 `:181` 取 `<Encrypt>`、`:185` 验签之前就把整个 body 读进内存。未认证方 POST
1 GB 时进程先涨 1 GB RSS，再走进验签失败（或在无 `<Encrypt>` 时 400）。

真实行为口径来自同族先例的实测（`src/pilotdeck-gateway/src/channel/webhook/mod.rs`
的超限格）：超限后 TS 销毁 socket，**catch 分支的 413 从不落到线上**，可观测结果
是零响应字节的连接结束（代码注释原文：`The catch arm's 413 never reaches the
wire: TS destroyed the socket before the rejection continuation runs`）。本渠道取
同一落线行为，而不是新增 413。

## Rust 行为

- 上限常量：`src/pilotdeck-gateway/src/channel/wecom_callback/mod.rs:71`
  `const MAX_BODY_BYTES: f64 = super::webhook::DEFAULT_MAX_BODY_BYTES;` —— 别名到
  `src/pilotdeck-gateway/src/channel/webhook/mod.rs:86` 的 `1_048_576.0`，两处不
  复制数值。webhook 那个常量只为共享加了 `pub(crate)`，其读体逻辑与测试未改。
- 读体：`wecom_callback/mod.rs:352-361` 用
  `http_body_util::Limited::new(request.into_body(), MAX_BODY_BYTES as usize)`，
  `LengthLimitError` → `RouteError::PayloadTooLarge`；恰好 1 MiB 的 body 仍通过
  （与 `webhook/mod.rs:694` 的 `read_request_body` 的 `total > max` 同一边界），
  其它读错误仍走原来的 `Error: <e>` → 日志 + `500 "error"`。
- 落线：`wecom_callback/mod.rs:278-296` 的 `handle_request` 把 `PayloadTooLarge`
  映射成 `Err(io::Error)`，从 `http.rs` 的 `service_fn` 冒出去，hyper 直接丢弃
  连接、不写任何字节；`wecom_callback/http.rs` 的 service 返回类型随之从
  `Infallible` 改为 `std::io::Error`。这与 `webhook/mod.rs:789` 的
  `Err(io::Error::other("webhook payload too large"))` 完全同构；413 只存在于
  webhook 的负控变异 `webhook-oversize-answers`（`:779`）。
- 验签顺序不变：签名材料 `<Encrypt>` 在 body 里（`crypto.rs` 的
  `verify_msg_signature(token, timestamp, nonce, msgEncrypt, sig)`），query 只带
  `msg_signature` 摘要，因此「先验签再读体」不可行；上限只是让读体阶段有界，不改
  任何 under-limit 请求的 400 `no Encrypt` / 403 `signature` 次序。
- 并发上限：未做。`channel/webhook/mod.rs` 无并发/信号量先例（其速率限制是另一
  机制），本渠道 TS 也无此概念；按任务书在 PR 写明另开单。

## 范围

仅 `wecomCallback` 车道 `POST *` 请求体的**大小上限**：

- 超限（> 1 MiB）：连接零响应字节结束；不再把整个 body 读进内存。
- 恰好 1 MiB：仍读完并走原解析路径。
- 不覆盖：并发上限（无先例，另开单）；阈值本身的业务依据（1 MiB 是仓内先例值，
  企业微信回调的真实大小分布尚无线上数据）；`GET *` 分支（不读 body）。

用户可感知差异：合法但 > 1 MiB 的回调会被拒（TS 会处理）；现实中企业微信加密
回调远小于 1 MiB，故正常流量无差异。该渠道当前**未装配**（`wecom_callback/mod.rs`
头部注释），所以今天零用户影响，差异在装配后生效。

本条不构成判分豁免：22 例金样全部是小于上限的正常回调，判分面不变。

## 机器判据

- `src/pilotdeck-gateway/src/channel/wecom_callback/tests.rs:1289`
  `oversize_post_closes_at_the_cap_with_zero_bytes`：声明 `1 MiB + 64 MiB` 但只发
  `1 MiB + 1` 字节并保持连接。断言连接在 3 s 内**结束**（EOF 或 reset，而不是
  等未发的 64 MiB），且客户端收到 **0 字节**。若上限被去掉，服务端会继续等声明的
  剩余 body，读取必然超过 3 s 期限 → 转红。
- 同文件 `:1342` `post_up_to_the_cap_is_still_read`：恰好 1 MiB 与一个小组都仍被
  读完并返回 400 `no Encrypt` —— 钉住 off-by-one 与正常读取路径。
- 22 例金样 `channel_matches_real_ts`（`tests.rs` 的 `channel_matches_real_ts`）
  继续钉正常 POST 全路径（200 `success`、派发、签名拒绝等），证明上限没有改坏
  功能。
- 负控 `src/pilotdeck-gateway/tests/fixtures/wecom-callback/negative_controls.py`：
  - `wecom-body-cap-disabled`（读体上限的使用点 `MAX_BODY_BYTES as usize` →
    `usize::MAX`）必须让 `oversize_post_closes_at_the_cap_with_zero_bytes` 转红。
    变异打的是使用点而不是常量：该测试的客户端尺寸也从同一个常量派生，改常量会让
    测试自己在断言之前溢出，矩阵只会判 INVALID 而不是 KILLED。
  - `wecom-body-cap-off-by-one`（`MAX_BODY_BYTES as usize` → `as usize - 1`）必须让
    `post_up_to_the_cap_is_still_read` 转红。转红点落在该用例共享客户端
    `parse_raw_response` 的案例标记 `#1336 #1941 at-cap matches the TS oracle` 上：
    上限低一字节时，恰好 1 MiB 的请求被零字节关闭，`http_request` 解析不到响应头就
    在那里失败，行内 `negative_assert_eq!` 根本执行不到；负控按（测试, 断言）精确
    匹配收据，声明一条不可达的断言只会让该行判 INVALID 而不是 KILLED。
  - `wecom-oversize-answers-413`（把 `Err(...)` 换成 413 响应）必须让首发那条的
    「零响应字节」断言转红 —— 即本条钉的落线行为，不是「只要拒绝就行」。
- 复算：`python3 -I src/pilotdeck-gateway/tests/fixtures/wecom-callback/
  negative_controls.py --check` 锚点自检；矩阵本体在落地树上由共享 runner 执行
  （见该文件头注释）。
