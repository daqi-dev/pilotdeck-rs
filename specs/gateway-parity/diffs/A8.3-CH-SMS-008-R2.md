## 类别

更正（探测的错误分类与触发条件措辞，非差异变化）：`A8.3-CH-SMS-008-R1`
登记了「探测成功 ⇒ 回退 IPv4」与「探测被第三方占用骗过 ⇒ 保留 v6-only
listener」两半，但没登记探测**自身失败**这一条，也没说清第三方那半在什么
条件下才可达。fix-r6 补齐两处。

1. 探测错误分类（#1339 fix-r6，Codex P1 #1）。fix-r5 的探测把「建 v4 socket
   失败」与「v4 空闲」当成同一件事：`TcpSocket::new_v4()` 返回 `Err`（IPv4
   栈关闭、fd 耗尽、沙箱拦 `socket(2)`）时读作「v4 没被占」，于是把一个本来
   工作正常的双栈 `::` listener 降级成 `0.0.0.0`，**静默丢掉 IPv6 服务**——
   与 `-R1`「只在 v6only 宿主上回退」的登记相反。现改为三态，只有
   `AddrInUse` 判 `Unshared`（确证 v4 无人服务），其余错误一律 `Unknown`
   并保留原 listener。
2. 第 2 条误判的触发条件写清（minimax boundary #4 要求）。`-R1` 第 2 条可达
   的前提是「第三方占住了 `127.0.0.1:<port>`，使无选项的 v4 探测真的撞上
   `EADDRINUSE`」。**第三方是否设 `SO_REUSEADDR` 不影响该判定**（本机实测，
   见「机器判据」）：无选项探测对第三方具体地址占用一律报 `AddrInUse`。
   `SO_REUSEADDR` 只会让「`::` 通配自己占住的端口」被误判成空闲，那是 fix-r5
   换建 socket 方式已经消掉的那条。

## 基线依据

固定基线 `cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85`，Node v22.22.0 / ICU 78.2，
与 `-008` / `-R1` 一致。本条不改任何 oracle 期望字节；55 个 cell 的探针全走

## Rust 行为

`src/pilotdeck-gateway/src/channel/sms/mod.rs`：

```rust
enum V4Port { Shared, Unshared, Unknown }

fn v4_port_state(port: u16) -> V4Port {
    let address = std::net::SocketAddr::from(([127, 0, 0, 1], port));
    let Ok(socket) = tokio::net::TcpSocket::new_v4() else {
        return V4Port::Unknown;
    };
    match socket.bind(address) {
        Ok(()) => V4Port::Unshared,
        Err(error) if error.kind() == std::io::ErrorKind::AddrInUse => V4Port::Shared,
        Err(_) => V4Port::Unknown,
    }
}
```

`bind_dual_stack` 对 `Shared | Unknown` 返回原 listener，只有 `Unshared`
才返回一条 `AddrInUse`（文案「#1339 `::` is IPv6-only on this host」）让
`bind_listener` 回退 `0.0.0.0`。

测试侧 `ensure_replay_port_free` 同时换掉不可靠的 `TcpListener::bind` 探测，
但**不能**照抄实现里的无选项 bind：第一次这么改，22 条负控里 16 条变 INVALID
——同机上一个用例跑完留下的 `TIME_WAIT` 让无选项 bind 报 `AddrInUse`，后续
每次重放都误判端口被占（原始输出：`_tmp/20261106-issue-1339-fix-r6/
negctl/sms-active-dedupe-off-restored.log` 的
`#1339 port 18826 already in use`）。改为 **connect 探测**：有活 listener 则
连接成功，`TIME_WAIT` 则被拒，两个方向都不误判。

## 机器判据

- 三态与保留语义：`cargo test -p pilotdeck-gateway --lib channel::sms`
  全绿（62 passed / 0 failed / 1 ignored），其中
  `dual_stack_probe_uses_the_assigned_port` 在双栈宿主上断言
  `address.ip().is_unspecified()`（不是「某个 v6 地址」）、端口非 0，并实际
  连 `127.0.0.1:<port>` 与 `::1:<port>` 两侧；无 IPv6 的宿主走 `Err` 分支时
  先证明 `0.0.0.0` 仍可绑，再显式打印 `#1339 skipped: host has no IPv6` 跳过，
  不再 `.expect("control :: bind")` 直接判红（Codex P1 #2）。
- 第三方占用判定与 `SO_REUSEADDR` 无关（本机 macOS，Python `-I`）：

```
third-party v4 listener on 59030 SO_REUSEADDR=1
probe no-option bind -> 48 Address already in use
probe SO_REUSEADDR bind -> 48 Address already in use
```

- 测试侧端口预检：`ensure_replay_port_free` 用 connect 探测，判据是
  `port_busy_preflight_fails_fast` 仍红、同机连续两次重放同一用例仍绿。
  反证（第一次改成无选项 bind 的版本，同一台机器上连跑）：

```
summary: KILLED=6, SURVIVED=0, INVALID=16
sms-active-dedupe-off-restored.log:
  #1339 port 18826 already in use; a concurrent channel-sms replay would corrupt the oracle
```

- 未覆盖：v6only 宿主 + 第三方占 `127.0.0.1:<port>` 的端到端复现（需要
  可控第三方监听器与 v6only 宿主，本机不可复现），仅由上面的 bind 级实测
  支撑判定可达性。
