## 类别

有意改进的已知边界扩展。#1739 的 metadata 优先短路把既有登记 A6.3-CONFIG-POLL-001 的「净零遗漏（内容与 metadata 均相同）」扩成「内容变了、metadata 未变也会漏」，多出一格同族豁免。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0（`resources/PilotDeck/package.json` engines `>=22.13.0 <23`）。

`src/pilot/config/PilotConfigStore.ts:123-126` 对每个被监听路径调 `watch(watchedPath, scheduleReload)`。`fs.watch` 是事件驱动：任何一次写入都产生事件，`scheduleReload`（`:109-122`）无条件排 debounce，与文件内容、长度、mtime、ctime 是否变化无关。基线的变更判定只有 `reload` 里的快照 diff（`:60-94`），没有「先比 metadata、相同就不读内容」这一步。

实测：`_tmp/20261106-issue-1736/r2/evidence/ts-baseline-restored-mtime-rewrite-probe.mjs`（原始输出同目录 `.log`）直接加载基线 dist 的 `PilotConfigStore`，对真实 store 调 `startWatching({debounceMs: 50})`，再对同一路径做「等长改写 + mtime 精确还原」：

```
length before/after: 224/224 equal=true
content differs: true
mtime before/after (ns): 1700000000000000000/1700000000000000000 equal=true
ctime before/after (ns): 1793944277099547546/1793944277541334247 equal=false
```

TS 检出该改动（version 1→2，`changedPaths` 命中 `agent.maxContextTokens`）。

## Rust 行为

`src/pilotdeck-gateway/src/config/store.rs:737-752`（`WatchedPath::changed`）先取 metadata-only 指纹，与上次的 `metadata_fingerprint` 相同就 `return false`，不读内容。metadata-only 指纹见 `hash_entry`（`:755-790`）：`len` / `is_dir` / `modified()` / `ctime` / `ctime_nsec` / `ino` / `dev`，不含内容。预 #1739 的实现每 tick 都算含内容的指纹（`hash_entry(..., true)`），**但同样只对被监视的配置文件本体、且是普通文件、长度 ≤ `CONTENT_SAMPLE_LIMIT` 时读内容**（`:769`）；目录里的其它项与超限文件在 #1739 前后都只按 metadata 采样，因此这一格**只在被读内容的那一项上**是 #1739 新引入的。两种实现都把读取失败哈希成「无内容」而不重试（#1792），所以「#1739 前能检出」还隐含**两次内容读都成功**。

漏检的精确条件：ctime 只是一个 tick 编号，指纹里存的是上次采样读到的那个值 `C`；ctime 这一条只让**一个字段**分不出改写，只有当指纹里**其余每个字段**也都没变时两份指纹才逐字节相同、内容改动才被漏掉（len / mtime / inode / dev 均不变，经父目录监视时同目录其它参与指纹的目录项也不变）。因此窗口从「记下 `C` 的那次采样」算到「tick `C` 结束」，最宽只有一个文件系统粒度（HFS+ 1 s，APFS / ext4 ns 级），**与采样间隔无关**。

这不是「采样时刻所在的 tick」——采样时刻本身没有 ctime，能比的是文件 ctime 的 tick 编号。粒度 10 ms、采样间隔 20 ms 时：采样在 15 ms、指纹里的 ctime 是 0（上次写入在 [0,10)），16 ms 的改写其 ctime 变成 10，metadata 不同、照常读内容；只有指纹里的 ctime 已是 10 时，16 ms 的改写才落进同一 tick。这仍然说明「粒度细于采样间隔」不能排除漏检。

实测：同一 evidence 目录的 `hfs-ctime-vs-apfs-probe.log`（脚本 `hfs-ctime-probe.mjs`，对同一段「等长改写 + 还原 mtime」取 metadata 元组）：

HFS+ 上这一格里，`hash_entry` 哈希的字段中探针实测的四个（`len` / `mtime` / `ctime` / `ino`）逐字节相同，`is_dir` 与 `dev` 也不随原地改写变化（同路径、同文件系统、仍是普通文件）——正是短路判定「没有变化」的那个元组，《范围》一节列的是完整条件。

## 范围

只影响 watcher 触发的 reload；手动 `reload()` 不受影响。下列四条同时成立才触发（被监视目标经父目录监视时，同目录其它参与指纹的目录项也须不变）：

1. 改写后的 ctime 仍等于指纹里记下的 tick 编号 `C`（窗口 = 从记下 `C` 的那次采样到 tick `C` 结束，采样时 tick 已结束则窗口为空；最宽一个粒度：HFS+ 1 s 可命中，APFS / ext4 ns 级实际不可命中；与采样间隔无关）——注意这只让 ctime 一个字段分不出改写，还要第 2、3、4 条同时成立；
2. 改写后长度与原样一致（长度参与指纹）；
3. 改写方把 mtime 精确还原（`rsync -t` / `cp -p` / `touch -r` 一类保留时间的工具）；
4. 改写不换 inode（原地写文件；「写临时文件再 rename 替换」会换 inode，因此不会漏检）。

| 场景 | TS 表现 | Rust 表现 | 用户感知 |
|---|---|---|---|
| APFS / ext4 上等长改写 + 还原 mtime | 触发 reload，新配置生效 | 同（ctime 变了） | 无差别 |
| HFS+ 上、改写后的 ctime 仍落在指纹记下的 tick 内，且《范围》第 2–4 条也同时成立（等长原地改写 + 还原 mtime + 不换 inode；目录监听时同目录其它参与项也不变），目标是会被读内容的那一项 | 触发 reload | 不触发，直到下一次任意 metadata 变化 | 改了配置但热重载没发生，进程内仍是旧配置；重启或再改一次才生效 |
| 手动 `reload()` | 生效 | 生效 | 无差别 |

不改变：变更后的 diff / classify / publish 语义；大文件（> `CONTENT_SAMPLE_LIMIT`）只按 metadata 采样的既有登记；目录型监听目标只对 target 读内容的既有登记。

收敛路径（未实施，供人定）：给短路加有界周期内容复核（例如每 30 s 强制一次含内容样本，成本约降到 1/1500），把「永不检出」变成「≤ 30 s 检出」；或按 Node 的 ctime 语义把该格并入 A6.3-CONFIG-POLL-001 的既有豁免。两条都需重新登记。

## 机器判据

细粒度 ctime 上的检出分两条用例，钉的是不同的东西：

- 单元级 `config::store::tests::restored_mtime_rewrite_still_reads_the_content`：把 `deterministic` 改成等长的 `deterministix`、mtime 还原后，`changed()` 必须为真，且内容样本恰好读一次（`content_reads == before + 1`）。
- watcher 级 `restored_mtime_rewrite_between_samples_is_seen`：改一次再改回原内容（A→B→A 的净零突发）、mtime 还原，直接断言的是**最终**加载计数 `loads == 2`（启动加载一次 + 这次变更一次）与最终 `version == 2`；测试没有单独断言起点值，也没有断言内容读取次数。它证明的是「净零突发也能被 ctime 看出」，内容最终改变的那条路径由上面那条单元用例覆盖。

短路的成本行为由 `config::store::tests::unchanged_metadata_skips_the_content_read` 钉住：50 次 metadata 相同的采样 `content_reads` 不增加，一次真实变更恰好 +1。删掉短路（改回每 tick 读内容）该断言即红，因此「删掉该行为」会被测出。

粗粒度 ctime 的漏检没有单元用例：ctime 粒度是文件系统属性，CI 无法控制。复现与原始输出见 `_tmp/20261106-issue-1736/r2/evidence/`（`hfs-ctime-vs-apfs-probe.log`、`hfs-plus-port-tests.log`）。复算命令：

```sh

hdiutil attach /tmp/pdrs-1794-ctime.dmg -nobrowse -mountpoint /tmp/pdrs-1794-mnt
cd src
# APFS (default TMPDIR): both pass
cargo test -p pilotdeck-gateway --lib -- --exact \
  config::store::tests::restored_mtime_rewrite_still_reads_the_content \
  config::store::tests::restored_mtime_rewrite_between_samples_is_seen
# HFS+: both fail at the #1739 marker, which is this entry's gap

  config::store::tests::restored_mtime_rewrite_still_reads_the_content \
  config::store::tests::restored_mtime_rewrite_between_samples_is_seen
```

两端原始输出见同目录 `hfs-plus-port-tests.log`（HFS+ 端）与 `apfs-port-tests.log`（APFS 端）。APFS 上 25/25 通过；HFS+ 上同一命令连续 16 轮，逐轮原始 cargo 输出在 `hfs-runs/run-01.log` … `run-16.log`，汇总行也印在 `hfs-plus-port-tests.log` 末尾：单元级 `restored_mtime_rewrite_still_reads_the_content` 失败 16/16（`#1739 the ctime bump is seen through the metadata short-circuit`），watcher 级 `restored_mtime_rewrite_between_samples_is_seen` 失败 15/16（`left: 1, right: 2`——加载计数停在 1、期望 2）。唯一通过的 run-06 日志里没有 ctime 时间戳，成因未取证（按 tick 对齐推断，不作为结论）；即便按推断，也只是说明这一格依赖 tick 边界，不改变上表。
