## 类别

有意改进（可选语义上界）。基线的 `debounceMs` 没有上界，Rust 侧加 1 h 上界，属于自定的产品判断，不是算术必需。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0（`resources/PilotDeck/package.json` engines `>=22.13.0 <23`）。

`src/pilot/config/PilotConfigStore.ts:107-108` 取 `debounceMs = options.debounceMs ?? 250`，`:116` 把它原样交给 `setTimeout`。基线不做任何夹取。

实测两段（原始输出在 `_tmp/20261106-issue-1736/r2/evidence/`）：

1. 定时器本身（`settimeout-2h-probe.mjs` / `.log`）：

```
setTimeout(7200000)  armed: _idleTimeout=7200000 hasRef=true
setTimeout(2**31-1)  armed: _idleTimeout=2147483647
setTimeout(2**31)    armed: _idleTimeout=1
evidence: 7200000 accepted verbatim = true
evidence: 2**31-1 accepted verbatim = true
evidence: overflow clamp only at 2**31 = true
WARNING: TimeoutOverflowWarning - 2147483648 does not fit into a 32-bit signed integer.
```

2. 真实 store（`ts-baseline-debounce-2h-probe.mjs` / `.log`）加载基线 dist 的 `PilotConfigStore`，`startWatching({debounceMs: 7200000})` 后改一次配置文件，拦截 `globalThis.setTimeout` 记录实际延迟：

```
setTimeout delays recorded around one change: [7200000]
evidence: baseline hands 7200000 to setTimeout verbatim = true
```

即 2 h（7200000 ms）在 Node 的可表示范围内，会被当成真实定时器（不是 1 ms 兜底），TS 侧就等 2 h 才 reload。

## Rust 行为

`src/pilotdeck-gateway/src/config/store.rs:212` 的 `MAX_DEBOUNCE = 60 * 60 s`；`effective_debounce`（`:251-253`）做 `options.debounce.min(MAX_DEBOUNCE)`，`watch_loop` 用它算 debounce 截止（`:845`、`:856`）。`WatchOptions::debounce` 的公开文档（`:152-154`）已写明「Over-ceiling values are clamped to a one-hour ceiling」。

因此 `debounce = 7200000 ms` 在 Rust 侧实际是 3600 s。`config::store::tests::two_hour_debounce_is_clamped_to_the_one_hour_ceiling` 直接钉住这条（见「机器判据」）。

`deadline_after`（`:260-263`）的 `checked_add` 才是真正的溢岱乐防线；1 h 上界不是它必需的，删掉夹取也不会 panic（`Duration::MAX` 才会）。

## 范围

只影响 watcher 的 debounce 长度，也就是「最后一次采到的变化之后，隔多久 reload」。

| 场景 | TS 表现 | Rust 表现 | 用户感知 |
|---|---|---|---|
| `debounceMs` ∈ [0, 3600000] | 原值生效 | 原值生效 | 无差别 |
| `debounceMs` = 7200000（2 h） | 等 2 h 再 reload | 等 1 h 就 reload | 请求了 2 h 的静默窗口，实际 1 h 后就热重载；改配置更容易「提前」生效 |
| `debounceMs` > 2^31-1 ms（≈24.85 天） | 打 `TimeoutOverflowWarning`，静默按 1 ms 跑（实际是立刻 reload） | 等 1 h | 两侧都偏离请求值，但方向相反：TS 提前到 1 ms，Rust 提前到 1 h |
| `poll_interval` | 无对应概念（`fs.watch` 无轮询节奏） | 10 ms – 60 s 夹取 | 纯实现细节：TS 侧根本不存在这个旋钮，「Rust 轮询替代 `fs.watch`」已由 A6.3-CONFIG-POLL-001 登记，60 s 上限只是把该实现细节收窄，不产生新的可观测分歧。与 debounce 上界的区别正在于此：debounce 两侧都有、取值一致时行为也应一致，所以 1 h 上限必须单独登记 |

不改变：默认 250 ms 路径、零 debounce（合法，立即触发）、`deadline_after` 的溢出兜底、reload 之后的 diff / classify / publish 语义。

收敛路径（未实施，供人定）：把 `MAX_DEBOUNCE` 抬到 Node 自己的可表示上界 `2^31 - 1 ms`，则「TS 会原样执行的值 Rust 也原样执行」，只剩 `> 2^31-1` 这一段仍偏离（且那一段 TS 自身行为病态）。这会同时改掉 `deadline_after` 的兜底常量与既有用例，需要重新登记。

## 机器判据

`config::store::tests::two_hour_debounce_is_clamped_to_the_one_hour_ceiling`：`effective_debounce(7200000 ms) == MAX_DEBOUNCE == 3600 s`。钉的是账本实际协商的那个字面值（7200000 ms），不是 `2 * MAX_DEBOUNCE`，所以把上界抬到 Node 上界这条收敛路径会被当成语义变更抓出来，而不是静默通过。

同族既有用例：`overlong_debounce_is_clamped_and_reloads_within_the_bound`（watcher 级：超过上界的 debounce 仍在上界内 reload）、`overflowing_debounce_does_not_kill_the_watcher`（`Duration::MAX` 不 panic）。

负控：`tests/fixtures/config-store/negative_controls.py` 的 `two-hour-debounce-ceiling-removed` 行删掉 `effective_debounce` 里的 `.min(MAX_DEBOUNCE)`，`two_hour_debounce_is_clamped_to_the_one_hour_ceiling` 必须红（`left: 7200s, right: 3600s`）；同族 `debounce-ceiling-removed` 行覆盖 watcher 级用例。原始输出与 `KILLED / SURVIVED / INVALID` 行见 `_tmp/20261106-issue-1736/r2/evidence/negctl/`（六行全跑，`summary: KILLED=6, SURVIVED=0, INVALID=0`）。
