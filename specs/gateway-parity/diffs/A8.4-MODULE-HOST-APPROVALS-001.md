## 类别

JS 语义差异（待批）：`requestId` 命中 Object 原型链键（`constructor`、
`toString`、`valueOf`、`hasOwnProperty` 等）时 resume 的去重分支走向。
TS `SopStateStore.resume` 的第一步查重写的是
`current.resumeRequests[input.requestId]`——普通对象上的属性读取走
原型链，`requestId: "constructor"` 会命中 `Object.prototype.constructor`
（一个函数，真值、`authorization` 字段缺失）；
Rust `PendingSopStore` 的 `get_key` 只查自有键，原型链键落空、直接
按新请求受理。组件未接线（#1305 前拆分发），差异只影响金样矩阵内
被钉死的 1 个 cell，不构成对拍豁免。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0 / ICU 78.2。
真实金样 `src/pilotdeck-gateway/tests/fixtures/module-host-approvals/oracle.json`
cell `resume-requestid-proto`（session `sess-handoff4` 处于 handoff wait，
`POST /api/public-approvals/resume`，`requestId: "constructor"`）实测：
TS 侧 `resumeRequests["constructor"]` 命中 Object 构造器函数，
`!duplicate.authorization` 成立，应答
`HTTP/1.1 502 Bad Gateway` + `{"code":"SOP_APPROVAL_LEGACY_RECEIPT"}`。
该值是 generate.mts 两次独立录制（字节一致）落盘的金样，非评审推断。

## Rust 行为

`src/pilotdeck-gateway/src/module_host/approvals/pending.rs`：`resume` 的
查重用自有键查找，`"constructor"` 不是任何已播种 receipt 的键，走
全新受理路径：校验通过、写入 receipt，应答
`HTTP/1.1 200 OK` + `{"accepted":true,"duplicate":false,…}`。两侧
store 其余分支（SOP_NOT_WAITING / SOP_REVISION_REQUIRED /
SOP_APPROVAL_AUTH_REQUIRED 等）不受影响。

## 范围

仅 approvals transport 的 resume 查重分支上「requestId 恰为原型链
键名」的病态输入；正常 UUID 形 requestId 两侧行为一致（回放矩阵内
既有 resume cell 全部字节一致）。Rust 不模拟 JS 原型链（语义体对齐
而非对象模型对齐），按冻结程序登记为残余差异。

## 机器判据

`src/pilotdeck-gateway/src/module_host/approvals/tests.rs`：
`requestid_on_the_prototype_chain_diverges` 先断言金样 cell 的 TS 字节
（502 + `{"code":"SOP_APPROVAL_LEGACY_RECEIPT"}`），再把同一请求打到
Rust 侧断言 200 + `accepted:true` + `duplicate:false`，两端钉死；
`resume-requestid-proto` 入 `PINNED_CELL_IDS`，不进归一化比对，
`replay_cells_cover_exactly_the_oracle` 断言集合守恒。ignored
`regenerates_identically("module-host-approvals")` 重生成完整金样。

## 批准记录

未批准，不增加判分豁免；登记于 #1350 fix-r1 交付，由协调者按冻结
程序登记（`check_frozen.py --write`）并确定接受为 JS 对象模型残余
或另定修复方案；组件接线（#1305）前须收敛结论。

用户感知：以 `constructor` 等 Object 原型键名为 requestId 重放 resume
的客户端，TS 基线返回 502 `SOP_APPROVAL_LEGACY_RECEIPT`，Rust 返回
200 受理成功——仅影响病态 requestId（正常 UUID 不受影响），且该
requestId 在 TS 侧本就永远无法完成正常回放。
