## 基线依据

Node v22.22.0、cc7c4e6，`tests/fixtures/edgeclaw-same-root-generation/observe.mts` 直接 import 基线
`core/storage/sqlite.ts` 的 `MemoryRepository`，同一 dbPath 上开两代：

- `serial`（TS 生产语义，单事件循环）：两代同时打开成功；互相读到对方提交的写；旧代 close
  后新代继续写；重开读到全部数据。`DatabaseSync` 调用是同步块，同进程内不可能交叠，因此
  同根两代不会出现 SQLITE_BUSY。
- `threaded`（确定性对照，不是生产 TS）：worker 线程用同一个 `node:sqlite` 持
  `BEGIN IMMEDIATE`，主线程操作。已初始化库上构造/读成功，首个写立即
  `database is locked` / `ERR_SQLITE_ERROR`；legacy `pipeline_state` 需要 migration 时，
  构造本身立即同样报错，释放后成功迁移并读到 `workspaceId` 旧值。

原始探针输出、逐格矩阵与 Node 版本见 `_tmp/20261026-issue-1082/RESULT.md` 与
`.../ts-probe/`；oracle 为 `tests/fixtures/edgeclaw-same-root-generation/oracle.json`，
由 ignored `same_root_generates_identically` 重生成守卫逐字节核对。

## Rust 行为

TS 的事件循环把「同一进程内对同一 SQLite 文件的每次调用」串行化。Rust 多线程可以让旧代
在途写与新代 stage/首次写真正交错；`busy_timeout = 0`（Node `DatabaseSync` 的契约）下后者
得到 `SQLITE_BUSY`，这不是 TS 生产语义。修复在 `EdgeClawStorage` 增加按 canonical db 路径
在进程内共享的锁：`conn()` 先取共享锁再取连接锁（锁序固定 process → connection），
`ConnectionGuard` 在整段 SQLite 调用期间持有；`close()` 同序。写者 panic 时锁随 guard drop
释放，poison 被容忍（`into_inner`），不毒化后续代。

不改 `busy_timeout`，因此跨进程/外部连接持锁仍立即 `database is locked`（Node 契约不变）；
不改租约、取消、stage/dispose 顺序，也不新增 sleep/重试。文本 `FileMemoryStore` 的并发写不在
本单范围（未实测，不宣称对齐）。

## 范围

只覆盖同一 `rootDir` 下两代 bundle 的 SQLite 连接与写路径。矩阵格：旧代 staged-idle /
staged-writing / disposing × 新代 stage / 首次写 / 在途 flush / retrieve；写者 panic 与
外部进程持锁作为终止条件格。M21 的 `generation-*` 仍使用相同 projectRoot 但不同 rootDir，
两者互补。同根热重载实效验收仍需 D-4 / A8 的人工签字；本单清 C-P2-2 的 SQLite 写竞争矩阵
部分，不宣称阶段完成。

## 机器判据

lib 用例（`runtime::memory::edgeclaw::factory::tests::`）：

- `same_root_stage_serializes_with_in_flight_write`：#1082 旧代在途写提交前，新代 stage 不得完成；
  完成后读到旧代提交行。
- `same_root_first_write_serializes_with_old_generation_write`：新代首写与旧代在途写串行，均落盘。
- `same_root_read_during_in_flight_write_does_not_error`：WAL 读不因写锁报错，可见值只可能是
  提交前无行或提交后新值。
- `same_root_stage_after_old_generation_close`：旧代 close 后新代可 stage/写，数据保留。
- `same_root_stage_needing_migration_fails_immediately_against_external_writer`：legacy 库
  migration 遇外部写锁仍 <500ms 内 `database is locked`，错误文本与 TS oracle 一致。
- `same_root_lock_survives_writer_panic`：持锁写者 panic 后，新代写仍成功（锁不永久 poison）。
- `same_root_generation_matches_ts_matrix`：读 oracle，声明 Node v22.22.0、serial 全成功、
  threaded 真交叠的立即锁错误；Rust 自己的格必须给 serial 结果而非 threaded 结果。
- ignored `same_root_generates_identically`：真实 TS 重生成 oracle 逐字节一致。

`native-same-root-lock-poison-fatal`、`native-same-root-busy-wait`。绑定断言均带
