## 类别

配置语义复刻缺陷（待批）：webhook 通道构造器对 `rateLimit` / `maxBodyBytes`
的 `Number()` 强制转换。TS 基线（`WebhookChannel.ts:58-66`，固定基线
cc7c4e6）对每个字段先做 `?? DEFAULT_*` 再 `Number(...)`，一个非数值（字符串
`"not-a-number"`、普通对象等）被 `Number()` 转成 `NaN`，而两个守卫比较——
body 尺寸 `total > maxBodyBytes`、限流 `timestamps.length >= rateLimit`——
对 `NaN` 恒为 false，**两个上限都永不拒绝**。`Infinity` 同型（比较同样恒
false，`maxBodyBytes: Infinity` 已实测，`rateLimit: Infinity` 未单独实测）。

#1689.3 的两条路线（回落默认 1 MiB / 30，或复刻缺陷登记本条）里选了**复刻**：
回落会让 Rust 拒绝 TS 照常服务的请求（2 MiB body、超 30 的突发），是行为
分歧；复刻则两边逐格一致。`WebhookChannel::from_options` 的 doc comment
（`src/pilotdeck-gateway/src/channel/webhook/mod.rs`）与本条互为登记。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85（探针输出头部逐文件
sha256 钉基线源）。两份实测（基线源 esbuild 转译后原样执行，与金样生成器
同一加载方式）：

**初测**（`_tmp/20261110-issue-1608/ts-probe-1689/probe.mjs`，原始输出同目录
`probe.out`，Node v22.22.0 / ICU 78.2）：

```
nan-max-body/oversize: {"status":"accepted","delivery_id":"oversize"}   ← 2 MiB + 7 body
nan-max-body/normal:   {"status":"accepted","delivery_id":"normal"}
nan-max-body gateway calls: 2
inf-max-body/oversize: {"status":"accepted","delivery_id":"oversize"}
inf-max-body gateway calls: 1
```

**复测**（`_tmp/20261110-issue-1608/ts-probe-1689-r2/probe.mjs`，原始输出同
目录 `probe.out`，Node v22.22.1 / ICU 78.2，头部含五份基线源逐文件 sha256；
初测的 nan-rate 组只发了 6 个请求——未越过默认 `rateLimit`=30，区分不了
「NaN 无上限」与「回落默认 30」（Grok r2 boundary#1 / DS r2 复核），本组
补齐并与 Rust 直测的 40 连发对齐，另加同探针默认值对照组）：

```
nan-rate/r01 … r40: 全部 HTTP/1.1 200 OK {"status":"accepted","delivery_id":"r01…r40"}（40/40）
nan-rate gateway calls: 40
default-rate-control/c01 … c30: 全部 accepted
default-rate-control/c31: HTTP/1.1 429 Too Many Requests（完整 error body 见 probe.out）
default-rate-control gateway calls: 30
```

对照组（同一探针显式实测）：默认 `maxBodyBytes` = 1 MiB 下 2 MiB + 7 的
body 是零字节关闭（金样 `too-large` 格的 `closed`）；默认 `rateLimit` = 30
下第 31 个请求 429（金样 `rate-limit` 格，本复测的 default-rate-control 组
同形）。NaN 组 40/40 通过而默认组第 31 个即 429，证明 NaN 不是回落默认值。

## Rust 行为

`WebhookChannel::from_options`
（`src/pilotdeck-gateway/src/channel/webhook/mod.rs`）逐字段复刻 TS 的
nullish-then-`Number()`：`js_value::to_number(value).unwrap_or(f64::NAN)`
——非数值字符串经 ECMAScript StringToNumber 得 `NaN`，对象恒 `NaN`，与
Node 实测一致。守卫比较在 `f64` 上对 `NaN` 同样为 false，所以 Rust 也是
「两个上限都永不拒绝」。直测
`channel::webhook::tests::non_numeric_bounds_are_unbounded_like_the_ts_baseline`
在 `rateLimit: "not-a-number"` / `maxBodyBytes: "also not a number"` 下实测：
1 MiB + 1 字节 body 照常 accepted、40 连发全部 accepted、网关收到全部
41 次调用。

## 范围

仅 webhook 通道 `options.rateLimit` / `options.maxBodyBytes` 的非数值形态
（`NaN`；`maxBodyBytes` 的 `Infinity` 已实测同型）。数值正常值的行为不在
本条内，由金样 `rate-limit` / `too-large` 格覆盖。`port` 的强转失败走另一
条路：TS 构造器抛错、loader catch 记录 key 后不装配通道，Rust 在 mount 处
同型处理（#2301，`register`），不经本条。其余通道车道（sms 等）的
`Number()` 强转如有同型形态，归属各自条目，本条不豁免。

## 机器判据

`src/pilotdeck-gateway/src/channel/webhook/tests.rs`：

- `non_numeric_bounds_are_unbounded_like_the_ts_baseline`：`from_options`
  起真实通道，三断言分别钉 oversize accepted（`#1689 a NaN maxBodyBytes
  never rejects the oversize body`）、40 连发全部 accepted（`#1689 a NaN
  rateLimit admits request …`）、网关 41 次调用（`#1689 the NaN bounds
  deliver all 41 bodies to the gateway`）。该测试是**复刻**钉子：将来若有人
  改成回落默认值（视为修复），这三条转红，提醒先处理本条的批准状态；
- 本条没有专属 mutant 开关（钉的是复刻而非修复，没有「旧实现」可恢复；
  `webhook-rate-limit-off` / `webhook-oversize-answers` 等既有开关继续守
  正常数值路径的上限本身）。
