## 类别

有意改进（Rust 侧多一个请求截止）。TS 的每一条 Lark 出站 `fetch` 都不带 `AbortSignal`，
即没有请求期限；Rust 客户端给每个 HTTP 请求加了 60 s 截止，使挂死的 mock / 半开连接不会
把整轮 turn 永久钉住。方向是「向严」（多一个失败出口），但**用户可见行为不同**，故按差异
登记而非按等价处理。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/feishu/FeishuChannel.ts` 的九处 `fetch` 均无 `signal` 选项：
`:722` / `:741`（图片、文件上传）、`:845` / `:895` / `:930` / `:970`（发消息、改消息）、
`:1006` / `:1032`（加/删 reaction）、`:1050`（tenant access token）。
Node 内置 `fetch`（undici）默认 `headersTimeout` 300 s、`bodyTimeout` 300 s，但对端**永不
回响应头**时以 undici 的默认值为准而非无限；对端接受连接后既不回也不断时，TS 侧的表现由
这两条 undici 默认决定，本条不重测该读数。TS 侧除 undici 默认外没有应用层期限。

## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/client.rs:17`
`const REQUEST_TIMEOUT: Duration = Duration::from_secs(60);`，六处出站调用各传一次
（`:122` token 刷新、`:200` / `:308` 发消息、`:371` / `:425` 改消息、`:457` reaction），
经 `crate::channel::http_client::HttpClient::send` 的 `tokio::time::timeout` 生效
（`http_client.rs:114`），超时错误原文为
`TimeoutError: The operation was aborted due to timeout`。
注释 `client.rs:15-16` 已自认该分歧：「`AbortSignal`-free TS `fetch` calls here have no
deadline; the Rust client keeps one so a stalled mock cannot pin a turn forever.」

## 范围

只覆盖出站 HTTP 请求的等待上限：同一请求在 60 s 内完成时两侧行为一致；超过 60 s 时 Rust
判失败（发消息失败 → 回落文本 → 文本也失败 → 记 warn/error 并不再重试），TS 继续等
（undici 默认 300 s 量级后同样失败）。envelope 加密、去重、分段、reaction 的其它语义不变；
入站 webhook 的 body 读取（`native_http::serve_with_body`）没有整请求 deadline，不在本条
范围（见 `A8.3-CH-FEISHU-006` 的看门狗段）。

## 机器判据

- 读码判据：`grep -n REQUEST_TIMEOUT src/pilotdeck-gateway/src/channel/feishu/client.rs`
  必须命中常量定义与六处传参；`http_client.rs:114` 的 `tokio::time::timeout` 是唯一生效点。
- **无组件钉子**：常量是编译期 60 s，测试内无法缩短，本 PR 不制造「60 s 后必须超时」的
  用例；也不声称摘掉该常量必须转红。若后续要为它加钉子，须先把截止改成可注入参数
  （或给 `HttpClient` 测试缝传入短截止），属独立改动。
- 该分歧不改变金样：13 条 `channel-feishu` 场景的 mock 均在毫秒级响应，未触发截止。
