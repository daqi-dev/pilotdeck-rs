## 类别

更正 004 的两处表述（不改差异本体、不改差异方向、不改判分语义）：

1. **行号锚点全部过期**：004 写 `mod.rs:763-786` / `:775-779` / `:815-837` /
   `:1105-1136` / `:1081-1088`。批次定时器的 P0 修复（`JoinHandle::abort` 换成
   批次上的 `timer_seq` 作废）改动 `enqueue_inbound` / `drain_inbound_batch` /
   `reset_chat_interaction_state`，这些行号再次整体位移。本更正改用
   **符号锚点 + 可复算命令**，不再写会随每次改动漂移的绝对行号。
2. **`/new` 不再 abort 批次定时器句柄**：004 原文说重置时「清批次定时器」。
   实现已改为移除该 chat 的批次条目，由被作废的定时器自己在醒来后按
   `batch.id` / `timer_seq` 判断返回。机制见 `mod.rs` 里 `Batch::timer_seq`
   的字段注释。

## 基线依据

沿用 004：固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0，
`src/adapters/channel/feishu/FeishuChannel.ts:469-481`（`/new`：
`onStateChange` → `resetChatInteractionState` → `gateway.abortTurn(...).catch(...)`
→ `!mapped.message` 时回 `已创建新会话。`）。

本更正补引两段此前只被转述的基线原文（**节选**，回调体与定时器参数用 `...` 省略；
完整摘录存 `_tmp/20261107-issue-1329/ts-reset-and-enqueue.txt`）：

```ts
// :335-349 enqueueInboundMessage（节选）
const batch = this.inboundBatches.get(input.chatId) ?? { messages: [], draining: false };
batch.messages.push(input);
if (batch.timer) clearTimeout(batch.timer);
batch.timer = setTimeout(() => { batch.timer = undefined; void this.drainInboundBatch(input.chatId)... }, ...);
batch.timer.unref?.();
this.inboundBatches.set(input.chatId, batch);

// :528-537 resetChatInteractionState（末尾三行 :534-536）
const batch = this.inboundBatches.get(chatId);
if (batch?.timer) clearTimeout(batch.timer);
this.inboundBatches.delete(chatId);
```

即：TS 的 `/new` 重置**连同 `inboundBatches` 条目一起删除**，不是只 `clearTimeout`；
`drainInboundBatch`（`:411-434`，`finally` 见 `:423-433`）在 `finally` 里按 `batch.messages.length` 决定重排空还是删条目。
Rust 侧 `state.batches.remove(chat_id)` 与重置这一步同形；但**在跑 drainer 的收尾**不同形
（TS 按 `chatId` 键无条件删、Rust 只删自己那一批次），那处差异单独登记为
`A8.3-CH-FEISHU-012`，本更正不覆盖。

Node 的 `clearTimeout` 对「已到期、尚未执行」的定时器**有效**（实测：
`_tmp/20261107-issue-1329/node-cleartimeout-probe.txt`，Case C 输出
`C: c1-start`，后插入的同到期定时器未执行；Case B 微任务里清除同样生效）。
因此**定时器作废本身**不登记差异：两侧都是「作废旧定时器、由最新窗口或已在跑的
drainer 收走消息」。这一句只覆盖作废语义，不含 `A8.3-CH-FEISHU-012` 记的那处收尾归属差异。

## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/mod.rs`（符号锚点，用
`grep -n` 复算，不写绝对行号）：

- `/new` 分支：`if mapped.command == Some(FeishuCommand::New)` 到该分支结尾
  —— 先 `on_state_change(snapshot_js())`（顺序与 TS 一致：在 reset 之前），
  再 `reset_chat_interaction_state(&chat_id)`，再按 `mapped.message.is_empty()`
  决定回 `已创建新会话。` 还是带着**新**会话 key 继续提交。
- 该分支内的注释 `No \`abortTurn\` on the A7 port: …`：代次门只保证「复查时
  代次已变就不开始这一段」，复查通过之后（无论发送是否已经开始）落下的
  `/new` 拦不住。
- `fn reset_chat_interaction_state`：自增 `entry.generation`、清空
  `entry.queue`、清 `active_run`、清 permission 答复状态，并
  `state.batches.remove(chat_id)`（与上节 TS `:534-536` 同形；**不是** abort
  定时器句柄），随后 `elicitation_clear` / `permission_clear_after_turn`。
  尚未认领批次的定时器醒来后找不到条目、或在新条目的不同 `id` / `timer_seq`
  上返回；已在跑的 drainer 继续跑完。
- `async fn send_final`：每段发送前复查 `is_current(chat_id, generation)`；
  注释明确写这是**收窄而不是保证**。
- 收尾 flush 的 `if self.is_current(chat_id, turn.generation)` 门。
- reaction 清理（`api.remove_reaction`）在该门**之外**，与 TS `finally` 同形。

004 对两侧残余窗口的逐条结论（TS 收尾 `flushFinal()` 无条件、Rust 收尾受代次门、
共同部分只有已进入发送调用的那一段）**不变**，本更正只更新锚点与批次定时器措辞。

## 范围

与 004 相同：仅 `/new` 触发时对**上一轮在跑 turn** 的终止语义（无 `abortTurn`
端口，旧 run 在 gateway 侧跑完，输出在投递前被代次门跳过；已进入发送调用或
复查后发送前落下的那一段除外）。本更正不扩大、不缩小 004 的范围，也不改变
「不为『旧轮已缓存、尚未开始发送的文本』给出一致性保证」这一句。

批次定时器的**作废机制**不在本条目范围：按上节实测，两侧在作废语义上没有可观察差异，
不单独登记差异条目。`/new` 重置与在跑 drainer 交错时的**收尾归属**确有差异，已单独登记为
`A8.3-CH-FEISHU-012`。

## 机器判据

- 004 的判据全部照旧（`/new` 的可见行为钉子、`/new <正文>` 提交路径钉子、
  generation 隔离「只有读码路径、没有负控」的自述、`abortTurn` 无判据）。
- 本更正涉及的锚点可复算：

  ```
  cd src/pilotdeck-gateway/src/channel/feishu
  grep -n 'FeishuCommand::New\|fn reset_chat_interaction_state\|fn send_final\|fn is_current\|state.batches.remove' mod.rs
  ```

  其中 `state.batches.remove` 有两处命中（drain 收尾移除空批次、`/new` 重置），
  本条指的是 `fn reset_chat_interaction_state` 内那一处。
- 批次定时器的身份守卫由 `superseded_batch_timer_does_not_drain` 钉住
  （过期序列与过期批次 id 都不得取走消息或置 `draining`，当前序列仍能排空并
  移除条目）。该用例只覆盖守卫侧；`enqueue_inbound` 自增并传参的接线未钉，
  缺口见 #2055。
