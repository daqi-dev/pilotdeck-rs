## 类别

不可避免（共享交互 helper 无生产装配）。TS 的 bluebubbles 通道把 gateway 的
`elicitation_request` / `permission_request` 变成 IM 消息发给用户，再把同一
chat 里的下一条文本当答复交回 gateway；Rust 侧的通道编排（`InteractionPort`
的十六个方法、待答分流、答复确认与排队）已随 sms 车道移植、本车道接上，但
**装载挂载（loader mount）构造时传入 `no_interaction()`**：
`elicitation_pending` / `permission_pending` 恒为 `false`、capture 返回空，
生产路径上用户既看不到问题也交不回答复。与 feishu
（`A8.3-CH-FEISHU-008`）同类。

`elicitation_request` / `permission_request` 走
`capture` 并 `sendReply` 问题文案。helper 本体在
`src/adapters/channel/protocol/`（`ImElicitationHelper` / `ImPermissionHelper`），
feishu / wecom-callback / bluebubbles 三车道共用。

## Rust 行为

`src/pilotdeck-gateway/src/channel/bluebubbles/mod.rs:861-879`（`register`，
loader 挂载）构造 `BlueBubblesChannel::new(..., no_interaction())`；
`mod.rs:802-805` 的 `no_interaction()` 返回 `NoInteraction`
（`channel/im_interaction.rs:74`）：`elicitation_capture` 返回空串、
`permission_capture` 返回 `None`、`*_pending` 恒 `false`。通道侧分支已按 TS
接好：`mod.rs` 的 `dispatch_payload`（`:433` 起）先查两道 `*_pending` 再决定
答复或新 turn，`process_message`（`:604` 起）的 `elicitation_request` /
`permission_request` 走 capture/confirm 路径——但这些分支在挂载产物上永远
走不到。生产装配接线本身（谁调 `load_enabled_channels`）属独立单元、尚未
落地；本条登记挂载缝上的事实：接线落地后即生产形态。

## 范围

仅生产装配的交互 helper：bluebubbles 侧的提问投递、答复捕获、答复确认与
排队，以及因此产生的行为差异——需要权限确认或 elicitation 的 turn 在
bluebubbles 侧既没有提示也不会被答复（该 turn 在 gateway 自己的超时/中止
路径结束，而不是被用户答复推进）。不覆盖通道侧编排（已接好、金样全
驱动，见下）、不覆盖 feishu / wecom-callback 的同名缺口（各自条目）。
本条不构成判分豁免。

## 机器判据

- 金样 `tests/fixtures/channel-bluebubbles/` 的 `elicitation-answer-and-resume`
  / `elicitation-cancel-zero` / `permission-allow-once` / `permission-deny-zero`
  四条在回放里装 `HelperInteraction::new(scripted responder)`
  （`channel/bluebubbles/tests.rs:603-613`）驱动已移植的状态机，逐格比对 TS
  原文（`JSON.stringify` 键序）。
- 生产实现为零：`NoInteraction` 让两条 `*_pending` 恒为 `false`；可判据的
  只有「挂载构造确实使用 `no_interaction()`」——`tests.rs` 的
  `loader_mount_builds_bluebubbles_channel` 钉住挂载键与构造产物，构造点的
  `no_interaction()` 实参本身只有读码路径。给生产接真实 helper 时须补
  真实回环用例（发问题 → 用户答复 → turn 继续）并改本条目。
