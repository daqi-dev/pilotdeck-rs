## 范围

- 受影响：启用 always-on 的自动化装配 —— provider 构造成功（有 `alwaysOn` 配置且至少一个 `project.enabled`）时 TS 启动后台服务，并按 `trigger.tickIntervalMinutes` 周期调度 tick（`src/always-on/runtime/DiscoveryScheduler.ts:75-90`）。tick 不保证每周期都执行 discovery：先过 `evaluateAlwaysOnDiscoveryGates`（项目存在 / 租约 / 锁 / 会话在飞 / 休眠等，`:92-118`），再查 cycle 是否已满（`:120-130`）、再抢 discovery 锁（`:135-143`），任一不通过即 `blocked`，全部通过才 `fire`（`:149`）；后续 plan 执行取决于 discovery 结果。Rust 没有该运行时，这条周期性检查与 fire 路径都不存在。
- 不受影响：三个 WS 方法的信封与错误码差异（见 `A7.8-ALWAYS-ON-DEFERRED-001`）；cron —— 原生 manager / methods / migrate / recover 已实现并装配（`native_process/assembly/cron.rs:56`、`assembly.rs:676,739`），但**周期调度半未实现**：`runtime/cron/manager.rs:763` 的 `// this.scheduler.start() — #1305.` 与 `:775` 的 stop 同注释说明定时唤醒路径仍是占位（与本 PR 把 `gateway.background:cron` 记为 `rust-unaccepted` 一致，不是「后台类只差 always-on」）；channel 启动路径。
- **控制面与后台的边界**：TS 的 fallback control 能 apply 已持久化的 work cycle（无 scheduler 侧 plan rerun 状态）；Rust 侧对应控制面能力是三个方法一律 `CAPABILITY_UNAVAILABLE`。本条登记的是**后台服务本体**，不是这三个方法的信封。
- 用户感知：同一份自动化配置在 Rust 网关下不会产生 always-on 后台执行；该能力的缺失是暂缓本体的代价，不是静默失败（控制面仍如实回 `CAPABILITY_UNAVAILABLE`，不假装成功、不回 TS 兜底）。
