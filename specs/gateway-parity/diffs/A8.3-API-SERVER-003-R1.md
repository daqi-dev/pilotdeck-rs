## 类别

更正（bug 已修复）：原条目登记的「api-server 车道没有复刻 Node
`requestTimeout` 对请求体读取的期限，半截 body 使 `stop()` 挂起」已由
#1620 修复闭合，原「未消除的行为偏离（待修）」结论不再成立。本更正登记
修复后的对齐现状与机器判据，不改变原条目字节，也不改变任何判分豁免。

## 基线依据

固定基线 `cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85`，Node v22.22.0 /
ICU 78.2。`src/adapters/channel/api-server/ApiServerChannel.ts` 用
`http.createServer(...)` 且不设 `server.requestTimeout`，取 Node 默认
300 s；body 未读完时 Node 写 `requestTimeoutResponse`（51 字节）并关闭
连接。修复后的金样格 `body-read-timeout` 由
`src/pilotdeck-gateway/tests/fixtures/api-server-channel/generate.mts` 在钉住
基线上实测采集：客户端声明 `Content-Length: 64`、只发 8 字节并保持连接，
基线在 300 s 后回 `408`、body 为空、连接关闭（oracle `expect[0]` =
`status: 408`、`body: ""`、无 `error` 字段）。生成器对 `body-read-timeout`
故意不走 `req.end()`，这是该格的实测前提。同形态另有缩短期限的探针留档
（真 `ApiServerChannel`，`requestTimeout` 800 ms）：
`_tmp/20261106-issue-1620/probe/probe-408.out`，socket 上恰 51 字节
`HTTP/1.1 408 Request Timeout\r\nConnection: close\r\n\r\n`。该探针里客户端在
90003 ms 才收到 408，而不是 800 ms：`requestTimeout` 由默认 30 s 的
connections checker 按格点检查，缩短期限只改变「到期后第一次检查即触发」，
不改变格点本身（与 `A8.3-CH-WEBHOOK-002` 同一机制）。

## Rust 行为

`src/pilotdeck-gateway/src/channel/api_server/server.rs` 的 `chat_completions`
把 `read_body(request.into_body())` 包在
`tokio::time::timeout(shared.body_read_timeout, ...)` 里；超时返回带
`BodyReadTimeout` 扩展标记的 408，`handle` 见到标记后改返回
`crate::channel::webhook::node_request_timeout_response()`（复用 webhook
车道已钉死的 408 构造，不另造一套），并跳过 `finish`，因此不追加 Node
原文没有的 `Date` 头。`shared.body_read_timeout` 由
`ApiServerOptions::body_read_timeout` 注入，默认
`DEFAULT_BODY_READ_TIMEOUT = 300 s`；它与同文件同值的
`DEFAULT_REQUEST_TIMEOUT`（**轮次**超时）是两个机制，未合并。连接任务在
期限到点返回，`accept_loop` 的
`while tasks.join_next().await.is_some() {}` 因此有界，`stop()` 不再挂起。

线上字节与 webhook 车道同一形态：`HTTP/1.1 408 Request Timeout` +
`Connection: close` + hyper 对未知长度空 body 的 chunked 帧
（`Transfer-Encoding: chunked` + `0\r\n\r\n`）。这一**帧级呈现**差异
不在本条（原条目只登记「无期限」这一行为偏离），单独登记为
`A8.3-API-SERVER-004`。

## 范围

原条目的全部范围：`POST /v1/chat/completions` 且通过鉴权、已送达请求头与
部分 body、已收字节未超上限、读取无报错、客户端既不发完也不关闭。修复后该
形态在 300 s 期限到点时被应答并关闭。原条目列出的提前返回路径（其它路由 /
方法、鉴权失败、body 已完整、读途中超上限）行为不变。期限只覆盖 body
读取，不覆盖整个 handler：已读完 body 后 `null` body 等既有语义不受影响
（仍由 `shared.timeout` 的轮次路径决定）。

## 机器判据

- `src/pilotdeck-gateway/tests/fixtures/api-server-channel/oracle.json` 新增
  `body-read-timeout` 格（TS 实测 408 + 空 body + 关闭）；
  `channel::api_server::tests::replays_real_ts_api_server_cells` 对该格断言
  TS 侧形状（`status == 408`、`body == ""`、无 `error`、`stalledAfter` <
  声明的 `content-length`）。
- 同文件
  `channel::api_server::tests::partial_body_is_answered_at_the_body_read_deadline`：
  注入 200 ms 期限，半截 body + 保持连接 → 收到 408、`Connection: close`、
  空 body、**无 `Date` 头**（Node 原文没有，`handle` 为此跳过 `finish`），且
  并发 `stop()` 在有界时间内返回。`Date` 那条断言钉住的是「跳过 `finish`」
  这个机制本身：删掉 `BodyReadTimeout` 标记让响应走 `finish` 会多出基线没有的
  `Date`，该测试转红。
- 负控：`src/pilotdeck-gateway/tests/fixtures/api-server-channel/negative_controls.py`
  的 `api-server-body-read-no-timeout`（去掉 body 读期限，上条测试转红）与
  `api-server-timeout-response-date`（让 408 改走 `finish`，只让 `Date` 那条
  断言转红）。
- 复算：钉住基线上重跑 `generate.mts`，`generator_provenance` 的
  `api_server_channel_regenerates_identically` 要求 `oracle.json` 逐字节同一。
