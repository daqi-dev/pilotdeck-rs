脚本对每格断言上列四个值（`completes === 1`、`turnResultCount === 1`、`turnResultTypes === ['error']`、`attempts === 2`），补断言后复跑输出 `_tmp/20261106-1219/ts-probe-rerun/`（与原跑 `ts-probe/status-fail-drop.json` 逐字段相同）。断言可证伪性由负控证明：把期望值改成 2 后脚本退出 1，`_tmp/20261106-1219/ts-probe-neg/probe-neg.log:5: AssertionError [ERR_ASSERTION]: status_fail_fail-then-return: completeTurn must run exactly once`。

## Rust 行为

不变。Rust 的 Drop 取消该 turn 的 async transition；已经进入的 blocking status append 由 worker 跑完（成功或失败）并保留同一 `ActiveTurn` / `RuntimeLease`。turn 被 drop（`Recording` 随 `LiveTurnStream` 销毁、pending transition 取消）后不再启动 catch 的补偿写入，因此「**Drop 抢在失败的 status 写入落地之前**」这一时序下持久 `turn_result` 为 0（`forward_tests.rs::forward_status_fail_drop` 实测，见机器判据）。时序是本条的边界条件：反过来先失败、catch 补偿已跑完再 Drop（即 TS 探针的 fail-only 格；Rust 对应 `forward_tests.rs::forward_real_status_write_error`）时，Rust 同样交付 `turn_completed` 并落 1 条 durable `turn_result`（该用例新增 `store.completes == 1` 断言实测），与 TS 一致——差异只在 Drop 抢先的那一序。只停读而不 drop、且 status 写入失败的另一格 Rust 侧没有用例（`forward_status_cancel` 用的是成功写入 `noFail=true`），本条不实测这一组合、不记为通过。

与上文 TS 实测对照：在「Drop 抢在失败写入落地之前」这一序上，TS 仍留下 1 条 `type=error` 的 `turn_result`（catch 路径在生成器被 `return()` 抢先之前已跑完 `completeTurn`），Rust 为 0。这是本条登记的实际边界；先失败后 Drop / 不 Drop 的两序双方都写 1 条，不构成差异（见上段与机器判据）。

## 范围

在 A7.2-LIVE-DROP-COMPLETION-001 原范围（complete I/O 挂起期间销毁整个 LiveTurn）之外，追加「status durable 写入失败与 Drop 同拍」。仍不含「取消一个 next 借用」——那必须继续同一 transition。

对齐实现需要为失败路径引入脱离消费者的终结任务（谁持有 slot/lease、错误归属、是否重复写），属于原条目已声明「必须另行定义」的范畴，本次不做，只登记边界。
