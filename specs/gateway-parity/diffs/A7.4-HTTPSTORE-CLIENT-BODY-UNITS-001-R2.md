## 类别

更正（原条目与 R1 的「TS 按 UTF-16 码元计」前提被实测推翻）。

## 基线依据

node v22.22.0（macOS，undici `Response.text()`，`--max-old-space-size=3072`）
实测：重复「中」（UTF-8 3 字节、UTF-16 1 码元）的正文，收到的字节数
536,873,958（刚超 `buffer.constants.MAX_STRING_LENGTH` = 0x1fffffe8 =
536,870,888）、码元数 178,957,986（远低于上限）时抛
`Error: Cannot create a string longer than 0x1fffffe8 characters`；字节数
536,867,814（低于上限）时成功。即上限按**收到的 UTF-8 字节数**判定，
与解码后的 UTF-16 码元数无关；ASCII 输入下两种解释等价，故此前按码元
解释的 #641 ASCII 实测同样成立。实测原件：
`_tmp/20261025-issue-647-probe/RESULT.md`（probe.mjs / probe-control.mjs
及 out.json / time.txt 等原始输出同目录）。

## Rust 行为

`fetch_redirect::read_body` / `read_text_body*`（`src/pilotdeck-gateway/src/
fetch_redirect.rs`）与模型侧 `CappedText`（`runtime/model/http.rs`，#647 起）
都按收到的 UTF-8 字节累计，与本轮实测的 TS 行为一致；原条目与 R1 认定的
「TS 按 UTF-16 码元计、Rust 按字节计故多字节文本更早触发上限」的差异
不存在。http store 客户端路径（`user_dialog/http_store.rs`）继续用字节计数
的 `read_body`：2xx 超限 → `returned an invalid response.`，非 2xx 超限 →
`failed: HTTP n`（状态优先），与 TS `response.json().catch(() => undefined)`
吞错后的分支一致。

## 范围

仅接近 512 MB 上限的超大响应体；此前登记的「多字节文本更早触发」偏差
取消。BOM 字节是否计入上限未实测（见 `_tmp/20261025-issue-647-probe/
RESULT.md` 待查项），如后续实测不同再另行更正。

## 机器判据

`http_store_tests.rs:1000 client_body_limit_counts_utf8_bytes_not_utf16_units`
（64 B / 17 CJK 字符），负控放大上限后 `expect_err` 红；模型侧字节判据：
`runtime/model/http_tests.rs` `response_text_cap_counts_received_bytes_not_
utf16_units`、`complete_shape_probe_counts_received_bytes_not_utf16_units`、
`shape_probe_counts_eof_trailing_bytes_against_string_limit`，负控见
`tests/fixtures/model-complete/negative-controls.py`
`capped-text-cap-counts-utf16-units`（变异计回码元必须红）。

## 批准记录

未批准，非已接受差异。原条目（`accepted-diffs.md:583`）与 R1（`:624`）的
UTF-16 码元认定按上述实测不成立，本更正仅推翻该前提，不改变其余字段。
