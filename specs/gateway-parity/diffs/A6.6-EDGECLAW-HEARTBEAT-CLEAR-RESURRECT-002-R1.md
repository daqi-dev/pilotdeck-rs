bug 修复（有意偏离 TS 基线的延续评审轮，#1207 = #917 的 P2 跟进，DeepSeek P2-1 与 opus P2
两家同撞）。原条目 fix-r3 之后的两项残留面：① `clearSession` 记录被删 L0 行 id 的 SELECT
与 DELETE 分属两个 `conn()?`，连接守卫在两条语句之间释放——落在该窗口内的行被 DELETE 删除
却进不了 `removed` 记录，已列出它的在飞 heartbeat 复查 `removed_since=false` 后照常写盘

无关的 clearSession（配合非递增删除路径 `repair_l0_sessions` / `clear(all)` /
`clear(current_project)`，它们删除 L0 行而不递增清除代次）都使
`generation != baseline && contains(id)` 为真：重捕获的 turn 被静默丢弃且其行被标已索引
（正是 fix-r3 评审 P0 消灭的「静默丢 turn」形状经累积集合回归）。另按 append-only 规则在本
R1 更正原条目的证据指针与 Node 版本表述（见「范围」）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/memory/edgeclaw/`：

- `storage/entries.rs`（#1207 项 ①）：`clear_session_memory_data` 的被删行 id SELECT 与
  `DELETE FROM l0_sessions WHERE session_key = ?` 改为同一 `conn()?` 守卫内执行（与
  `storage.rs:739` `insert_l0_session_if_new` 的 #770 P1-1「读-判-插同守卫」同手法）。窗口内的
  并发 INSERT 因此阻塞在进程锁+连接锁上，只能落在 DELETE 之后：行保留为新数据、
  `removed_since=false`、不复活。不用 `DELETE … RETURNING`：RETURNING 没有可驻留的缝位，对
  「回滚成两条语句」的突变体无法做确定性杀灭；同守卫加缝可以；
- `file_memory.rs` 新缝 `ClearSessionStage::L0IdsSelected`（doc-hidden，生产不装 hook）：
  SELECT 之后、DELETE 之前、连接守卫持有中触发；hook 先 clone 出槽再调用（沿用 fix-r3 评审
  P3-3 模式）；hook 报错 = 清除中止（L0 行仍在、代次不动，与 `BeforeDeleteL0` 报错面一致：
  无数据丢失），hook 阻塞 = 清除停在守卫段内（并发捕获阻塞的确定性测试形状）；
- `file_memory.rs`（#1207 项 ②）：`SessionClearState.removed` 从 `HashSet<String>` 改为
  `HashMap<String, u64>`（行 id → 删除它的清除代次）；`bump` 以本次代次逐 id `insert`
  （与 `state.generation` 同锁原子更新，读者要么都见要么都不见）；`removed_since` 改为
  `removed.get(id).is_some_and(|cleared_at| cleared_at > baseline)`——删除发生在基线之后才答
  true。旧的 `generation != baseline` 前置被删去：`cleared_at > baseline` 已蕴含它（bump 与
  insert 同锁完成，`removed` 里的每个 id 都有某次 bump 的代次戳）；
- 不动的部分：清除代次仍只在 L0 DELETE 成功后递增（fix-r2 位置）；`clear(all)` /
  `clear(current_project)` 仍不递增（金格 `matrix-general-select-clearProject` 逐字节依赖）；
  heartbeat 两层复查（mismatch 臂按行判别 + 锁内按行判别）与 `Closed` fail-open 臂均不动；
  `repair_l0_sessions` 的非递增删除行为不动（TS `repairL0Sessions` 同形）。
