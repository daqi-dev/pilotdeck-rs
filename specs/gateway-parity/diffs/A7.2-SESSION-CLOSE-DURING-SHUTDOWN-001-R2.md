## 类别

更正（bug 已修复）：R1 登记的「A1–A6、B2/B3/B4、C1 全窗口与 TS 一致」不成立——
评审发现 `close(); shutdown();` 同 tick（close 已登记驱逐、任务未接管 record）时
Rust 仍答 Ok 且 `on_evict` 原因变 `shutdown`，TS 拒 per-key 且原因 `closed`。
本条登记该缺口（#1245 fix-r1 修复）与 shutdown drain 裸 spawn 的 panic 限制。

故 `shutdown()` 的同步清空见不到该 key；`shutdown()` 只经 `pendingEvictions`

`_tmp/20261026-issue-1245/probe/close-during-shutdown.{mts,out}`（宿主评审副本中
同文件位于 `remote-run/artifacts/round/probe/`）。

## Rust 行为

#1245 fix-r1：`shutdown()` 同步体收集 drain 清单时跳过有未结算 `closings` 条目
的 key（`owner.rs` shutdown 内 `unsettled_closing` 检查）——该条目只可能来自
一个已调用、任务尚未接管的 close（sweep 同锁移除 record，drain 登记在 shutdown
同步体之后）。效果对齐 TS：close 任务接管 record 后用自己的驱逐（reason
`closed`、per-key 结果），shutdown 经 `pending`（close 的 track 登记）聚合其失败。
不采用「close 调用时同步接管 record」方案：它与已批准差异
A7.2-SESSION-RECREATE-DRAIN-001（close 排在重建之后）冲突，会使 close 之后重建
发布的新 writer 存活。

已知限制（读码登记，TS 无 panic 概念，无法实测对照）：shutdown 的 per-key drain
是裸 `tokio::spawn`，drain 内 panic 时该 key 的 `closings` 条目停留未结算，
后续 `close(key)` 答 `wait_result` 的 `Session lifecycle executor stopped.` 而非
该 key 自己的结果；`unsettled_closing` 的注释已收窄为只声明 close/idle/shutdown
任务有 Completion 守卫。完整修法（drain 走 `spawn_with_error` + 确定性测试 + 负控）
超出 fix-r1 范围，另开条目跟进。

## 范围

`runtime/session/owner.rs` 的 `shutdown` drain 收集一处；`close`/`sweep_idle`/
drain 的登记语义、A7.2-SESSION-RECREATE-DRAIN-001（重建串行）不动。R1 的其余
结论（A2/A2b/A3–A6、B2/B3/B4、C1 全窗口对齐）经本轮全量回归确认仍成立。
P3（closings 条目结算后不即时移除，靠 `track()` prune）：沿用 R1 登记，不影响判定。
