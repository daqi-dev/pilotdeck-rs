## 类别

bug（per-session 目录回收时机）。本条只登记事实，暂不修：修复即 #1751 的方案 B，属产品判断，
按「暂不执行」处理。未批准，非已接受差异。

基线的 `close()` 在返回前**同步删除** per-session 临时目录；端口的 `close()` 只等已登记的清理任务，
握手仍在飞时它没有可等的清理，于是 `close()` 返回时目录仍在，删除推迟到迟到握手落地或握手超时之后的
detached cleanup。

「更松」只在**目录存在性**这一个可观察量上成立，且**对 `close()` 与 `dispose()` 两条 API 都成立**：
`dispose()`（`client.rs:1281-1292`）只比 `close()` 多等「**已登记**的 cleanup」（含
`wait_on_close=false` 的），而在飞握手的清理要等握手落定/超时才登记，所以 `dispose()` 同样在
目录还在时就返回。生产收尾路径 `McpRuntime::stop()` 走的正是 `dispose()`（`runtime.rs:242`），
即差异在生产路径上可见。PR #1782 分支的用例
`dispose_during_an_in_flight_handshake_removes_the_session_directory` 也明文写着
「`dispose()` must return now: it never waits for the handshake」并刻意不断言 dispose 之后目录是否还在。

另一面，资源顺序上端口更严：基线是在活着的子进程底下抽走目录（TS 金样逐字 `dir exists after close =
false` 与 `child alive after close= true` 并列），端口是先关子进程再删目录。

## 基线依据

固定基线 `resources/PilotDeck`（cc7c4e65，Node v22.22.0，`@modelcontextprotocol/sdk` 1.29.0）。

`src/mcp/client/McpClient.ts:361-377` 的 `close()`：`await this.client?.close()` 后置
`status = "idle"`，随后 `if (this.perSessionDir) { rmSync(this.perSessionDir, { recursive: true, force: true }); this.perSessionDir = null; }`
——删除是 `close()` 的同步步骤，返回前必然完成。

实测（探针 `_tmp/20261106-issue-401/probe/probe-dispose-inflight.mts`：`slow-mcp-server.mjs` 把
`initialize` 延迟 3 s，握手在飞时调用 `close()`；`PILOTDECK_SESSION_TMPDIR` 指到临时目录。
原样重跑，原始输出 `_tmp/20261106-1751-1754-diff/ts-probe-dispose-inflight.out`）：

```text
status before close = connecting
per-session dir     = /var/folders/yz/6smg7hrj57l05w6jlb3vgn240000gp/T/pd401-dispose-YDztyk/pilotdeck-mcp-slow-fe6r2a
child pid           = 6953 alive = true
close() returned in ms = 1

child alive after close= true

after handshake landed: child alive= true

PROBE RESULT = {"closeMs":1,"closeWaitedForHandshake":false,"dirRemovedAtClose":true,"childAliveAtClose":true}
```

即：TS 在 1 ms 内返回、返回时目录已删；迟到的握手随后仍然落地并把 status 抬回 `ready`
（此时它的 per-session 目录已被删掉，子进程在 `close()` 返回后、以及握手落地后都仍活着——
探针最后手动 `SIGKILL` 收尾）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/mcp/client.rs:1249` 的 `close()`：置 `epoch += 1`、`connect = None`、
`retire_connection()` 后，只对**当时已登记**且 `wait_on_close` 的清理 `await_cleanup`（`:1256-1270`）。
`spawn_cleanup`（`:603-620`）才把「关连接 + 删目录」登记进 `State.cleanups`。

在飞握手的目录此时尚未登记：它的 `PerSessionDirectory` 还在 `run_connect` 的局部变量里，
只有等握手落定、走到 `:957` 的 `state.epoch != epoch` 分支才 `state.spawn_cleanup(… dir.remove() …)`；
握手超时路径同理在 `:912-930` 里把目录交给 detached cleanup（默认
`DEFAULT_HANDSHAKE_TIMEOUT_MS = 10_000`，`:94`）。

所以端口的行为是：`close()` 快速返回，**目录仍在**（实测）；子进程按代码路径推断也尚未回收
（`close()` 只 `retire_connection()`，迟到连接的关闭在 detached cleanup 里；本条未测子进程存活，
且「子进程回收时机」不在本条范围）。删除发生在迟到握手落地或 10 s 握手超时之后的 detached cleanup 里；
迟到的连接被判 `aborted`，不会像基线那样把 status 抬回 `ready`——**这一点已由
`specs/parity/accepted-diffs.md` 第 4 条 `handshakeClose` 登记，本条不重复主张**。

实测（探针 `probe_1751_close_during_inflight_handshake_keeps_session_dir`，临时加在
`tests/mcp_client.rs` 尾部、不提交，源码见 `_tmp/20261106-1751-1754-diff/rust-probe.patch`；
命令 `cargo test --offline -p pilotdeck-gateway --test mcp_client probe_1751 -- --nocapture --test-threads=1`；
原始输出 `_tmp/20261106-1751-1754-diff/rust-probe.log`）：

```text
PROBE session_dir = /private/var/folders/yz/6smg7hrj57l05w6jlb3vgn240000gp/T/pdrs-probe-1751-close-inflight-94274289-4182-4ca0-ada9-d3443f014ec3/sessions/pilotdeck-mcp-mock-tE1VpO
PROBE dir_exists_before_close = true
PROBE close_ms = 0
PROBE status_after_close = idle
PROBE dir_exists_after_close = true
PROBE dir_exists_after_500ms = true
PROBE start_settled = Err("MCP handshake aborted: client closed during connect (server=mock)")
PROBE dir_exists_after_gate_opened = false
```

即：`close()` 在 0 ms 返回（status `idle`），返回时目录**仍在**，500 ms 后仍在；探针随后放行
被闸住的 `initialize`，迟到握手落地被判 `aborted`（`start()` 返回 `Err(MCP handshake aborted:
client closed during connect)`），目录才由 detached cleanup 删除（`dir_exists_after_gate_opened
= false`）。与基线对照：同一步骤下基线 `close_ms = 1`、`dir_exists_after_close = false`、
迟到握手仍 `{"ok":true}` 并把 status 抬回 `ready`。

「目录最终会被删」在正常收尾（运行时存活到 detached cleanup 跑完）时成立，但不是无条件：
端口的删除挂在 `spawn_cleanup` 出去的 async 任务里，若网关进程或 tokio runtime 在那之前被拆除，
未完成的清理任务被 drop，目录会残留在 `$TMPDIR`（基线因 `close()` 里同步 `rmSync` 不受此影响）。
这条交错**未实测**，列入下面的待补钉子清单。

## 范围

仅「per-session 目录（stdio 传输的 `--user-data-dir=` 临时目录）在 `close()` 期间的寿命」，
可观察差异只有一处：`close()` 返回那一刻目录是否存在（基线 false、端口 true）。

**status 走向不在本条**：`close()` 之后基线被迟到握手抬回 `ready`、端口保持 `idle` / `aborted`，
已由 `specs/parity/accepted-diffs.md` 第 4 条 `handshakeClose`（郑达奇 2026-10-21 已批）登记，
且方向相反——那条把基线的 `statuses:["ready"]` 判为「原版缺陷」（子进程永不回收的资源泄漏）、
把端口保持 `idle` 判为修复。本条只登记**目录寿命**，不重复登记 status，也不主张把端口改回 `ready`。

不含：目录内容与命名规则、`reconnect` 路径的旧目录回收（该路径两侧都已有用例覆盖）、
子进程回收时机（含「删目录与关子进程的先后」这一取舍——它须在 #1751 的决策卡上单独拍板）、
握手中断后的重连语义。

  ② 钉「运行时在 detached cleanup 跑完前被拆除 → 目录残留」这条交错（本条 `范围` 里的未实测项，
  当前无任何用例覆盖，也未实测确认 tokio runtime drop 后目录确实残留）。
  origin/main 的 `tests/mcp_client.rs` 没有钉「`close()` 返回时目录仍在」；
  PR #1782 分支的 `dispose_during_an_in_flight_handshake_removes_the_session_directory` 钉的是
  `dispose`（收尾）路径，且刻意不钉 dispose 之前的目录状态。补钉子 + 负控须另开跟进单，
  前置于本条从「待批」转「已接受」，也前置于 #401 自称「MCP 目录寿命边界已闭合」。
