## 类别

bug 修复（有意偏离 TS 基线）。TS `runHeartbeat` 收尾的批量 `markL0Indexed` 只按
`l0_index_id` 置 `indexed = 1`，没有「化身」（同一 id 的第几次捕获）维度。落在
persist 成功之后、批量 mark 之前的 `clearSession` 会把这一轮刚写的文件连同 L0 行一起
删掉；若随后以同一 `(session_key, timestamp, payload)` 重新捕获，新行拿回**同一个**
`l0_index_id`，TS 的 UPDATE 便把这个「文件从未写过的化身」置成已索引，该轮记忆永久
丢失。Rust 在 #917 fix-r3 之后已能在 persist 前复查清除记录，但这一格是 persist
**已经成功**之后才发生的清除，旧 Rust 与 TS 一样冒名顶替。本条登记 Rust 改为跳过这类
id 的偏离。

## TS 依据

cc7c4e6 基线（本地检出 `resources/PilotDeck`，`git log -1` = `cc7c4e65`）
`src/context/memory/edgeclaw-memory-core/src/core/pipeline/heartbeat.ts`：

- `:705` 无 focus turn 的会话直接 `processedIds.push(session.l0IndexId)`；
- `:953` persist 循环成功后 `processedIds.push(session.l0IndexId)`；
- `:982` 循环结束后无条件 `this.repository.markL0Indexed(processedIds)`。

`core/storage/sqlite.ts:1048-1053`：

```ts
markL0Indexed(ids: string[]): void {
  const uniqueIds = Array.from(new Set(ids.filter(...)));
  if (uniqueIds.length === 0) return;
  const placeholders = uniqueIds.map(() => "?").join(", ");
  this.db.prepare(`UPDATE l0_sessions SET indexed = 1 WHERE l0_index_id IN (${placeholders})`).run(...uniqueIds);
}
```

入参只有 id，没有代次或化身维度；`l0IndexId` 由 `(sessionKey, timestamp, payload)`
推导，所以清除后同内容同时间戳的重捕获必然复用同一 id。

真实实测（本单，Node v22.22.0，基线 cc7c4e6，隔离 `HOME` + 环回 scripted LLM +
冻结时钟；探针 `_tmp/20261106-issue-1656/probe-ts/probe-mark-incarnation.mts`，原始
输出 `probe.out.json`）：捕获一轮 → heartbeat persist 写出 `Project/alpha-*.md` →
在 `markL0Indexed` 拦截点 `clearSession('s1')`，再以同一 `(sessionKey, timestamp,
messages)` 重捕获 → 真正的 `markL0Indexed` 跑完后的观测：

```json
"markIds": ["s1_48a24602b1_raw"]
"rowsAfterClear": []
"rowsAfterRecapture": [{"l0IndexId": "s1_48a24602b1_raw", "indexed": false}]
"filesAfterRecapture": ["MEMORY.md", "project.meta.md"]
"rowsAfterMark": [{"l0IndexId": "s1_48a24602b1_raw", "indexed": true}]
"filesAfterMark": ["MEMORY.md", "project.meta.md"]
```

即 TS 把「文件从未写过的化身」置成已索引，该轮记忆永久丢失。该窗口不在
`tests/fixtures/edgeclaw-heartbeat-indexer/oracle.json` 的 19 格里
（`matrix-single-beforeMark-clearSession` 只清不重捕获），因此本条不是金样偏离，而是
新窗口上的行为偏离：既有金样与 `fix-917.json` 的期望不动。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/memory/edgeclaw/heartbeat/indexer.rs`：

- `:689` 每会话的待标记列表改为 `processed_ids: Vec<(String, u64)>`，第二个字段是该
  id 本轮 persist 时的清除代次 `persist_generation`；
- `:904-910` 在 focus turn 循环前声明 `persist_generation = u64::MAX`，`:1261` 在每一
  轮 persist 的**任何写入之前**取 `min(当前 session_clear_generation)`（读点之前只有
  classify 与 createNote 两类 await；候选选择 `route_general_candidate` 的 select 请
  求在读点之后、写入之前，不在读点之前。一个会话的多轮 persist 取最低代次；
  必须在写入前取：写入之后再读会把「写入期间完成的清除」算进地板，正是本条要关的窗
  口），`:1781-1782` 仅在未被 #917 丢弃（`discarded_for_clear`）时压入；无 focus
  turn 的路径 `:885` 用当前代次；
- `:744-780` 批量 mark 前先 `snapshot_operation_scope()`（与 `clearSession` 同一临界
  区，清除无法在读数与 UPDATE 之间插进来），再对每个 id 读
  `session_clear_deleted_since(session, persist_generation, id)`
  （`storage/entries.rs:645`），命中者不进 `mark_l0_indexed`；
- `session_clear_deleted_since` 是**记录-only**：直接用
  `SessionClears::removed_since`（`file_memory.rs`，`cleared_at > floor`），刻意不加
  `session_clear_removed_since` 的「行仍在」限定——同一 id 的新行可能正躺在
  `l0_sessions` 里，那正是要跳过的重捕获；
- `floor` 用 persist 代次而非 list 基线：清除发生在 persist **之前**、本轮列到的本就是
  重捕获时，文件确实写了，仍要 mark（`recapture_with_the_same_id_after_clear_is_not_marked_indexed_unpersisted`
  与 `discarded_session_does_not_mark_the_recaptured_id_indexed` 两条既有回归锁住这一
  侧）。

净效果：上述窗口里 Rust 保留 `indexed = 0`，下一次 heartbeat 重新处理该轮并写出文件；
TS 置 `indexed = 1` 且无文件。

## 范围

- 只影响「persist 成功之后、批量 mark 之前完成 `clearSession`，并且同 id 被重新捕获」
  这一格。被 #917 丢弃的会话（`discarded_for_clear`）本来就不进 `processed_ids`。
- 清除后没有重捕获时结论相同、行为等价：行已被删，TS 的 UPDATE 匹配 0 行，Rust 的
  `mark_l0_indexed(&[])` 直接早退（`storage.rs:952-959`，不取连接）。因此
  `matrix-single-beforeMark-clearSession` 等 5 个既有关闭/清除格的行、文件、trace、
  requests 仍逐字节不变；三个 `close` 格的列表非空，仍走 `conn()` 并按 TS 的同一错误
  失败。
- **已知偏离面（关闭的库 + 全部 id 被过滤器跳过）**：若清除发生在 persist 之后、随后
  库被关闭，过滤器会把全部 id 跳过，`mark_l0_indexed(&[])` 早退返回 `Ok`；同一时序下
  TS 的 `markL0Indexed(非空)` 在已关闭的 db 上抛错，心跳以 error 收尾。该组合下 ts 与
  rust 的 trace/stats 收尾不同（Rust 正常收尾、TS 报错）。取舍：Rust 侧「无可标记即
  no-op」是 `mark_l0_indexed` 既有语义（`:952-959`，与本条无关的早退分支），不为这一
  格新增错误路径；如需逐字节对齐，须把该格单独登记并给它一条错误注入用例。19 格金样
  与 `fix-917.json` 均不涉及该组合（清除格不关库、关库格不重捕获）。该面列
  `P2-跟进`（前置于 A6.6 收口）。
- **已知未覆盖面（同形窗口的兄弟删行路径）**：本条只认 `clearSession` 写进
  `SessionClears` 的逐 id 删除记录。`clear_all_memory_data` /
  `clear_current_workspace_memory_data`（`storage/entries.rs:371` 的
  `DELETE FROM l0_sessions`）与导入态重置 `clear_l0_sessions`
  （`storage/bundle.rs:758`）与 `repair_l0_sessions` 的逐行
  `DELETE FROM l0_sessions WHERE l0_index_id = ?1`（`storage.rs:1074`；它的
  `repair_removed` 记录只服务丢弃原因的区分，不写清除代次）同样删行、同样不记 id、也
  不推进代次，因此「persist 之后删行 + 同 id 重捕获」这一格仍是旧行为（与 TS 一致，不
  是对拍偏离，但数据保全目标未达成）。列 `P2-跟进`（前置于 A6.6 收口）。
- **gap 3（repair 删除可区分）只在前循环判定点生效**：`L0Removal::{Cleared, Repaired}`
  由 `session_cleared`（`indexer.rs:1824-1848`）给出；提交段内的逐候选复查
  （`indexer.rs:1298`）仍只查 `session_clear_removed_since`，落在两处之间的
  `repair_l0_sessions` 删除既不区分原因、也不会被该窗口的写入感知（既有行为，本条未
  扩大范围）。同列 `P2-跟进`。
- **安全方向的已知副作用**：清除在「写入之后、mark 之前」完成且同 id 又被重捕获、且
  同轮后续候选仍写出文件时，这一行会保留 `indexed = 0`，下一轮 heartbeat 重新
  classify / createNote 一次（重复处理一轮，不丢数据，也不重复写已存在的文件）。这是
  id 单键设计的固有歧义，收口需要「写后代次」维度，超出本条范围。
- 空 focus turn 的会话（TS `:705`）同样带当前代次：清除之后不 mark 是操作等价（行已
  删），只在同 id 重捕获时保住新一轮。
- 不改变 `l0_index_id` 推导、去重、stats、trace 结构与 requests；不引入 schema 变更；
  `mark_l0_indexed(&[String])` 签名不变（对拍按 id 重放，`INIT_SQL` 逐字节冻结）。
- 与 `A6.6-EDGECLAW-HEARTBEAT-CLEAR-RESURRECT-001`/`-002` 互补：那两条管「清掉的会话
  不再写文件」，本条管「写了又被清掉、同 id 重捕获不得冒名顶替」。
