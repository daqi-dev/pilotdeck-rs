## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/mod.rs`（符号锚点，`grep -n`
复算，不写绝对行号）：

- 逐事件门：`process_turn` 事件循环内
  `if !self.is_current(chat_id, turn.generation) { break; }`。
- flush 门：`process_turn` 收尾 `if self.is_current(...)` 包住 flush；
  `send_final` 每段发送前复查。reaction 清理（`api.remove_reaction`）
  在门**之外**，与 TS `finally` 同形（004 结论不变）。
- #2055-2 新增 `State::elicitation_answering`（`HashSet<String>`）：
  `try_handle_pending_interaction` 的 elicitation 分支里「查占用 + 插占用」
  与 `elicitation_pending` 判定后置于一**个**临界节，答复任务
  （`answer_pending_elicitation`）结束（含 panic，见下）后移除；
  `reset_chat_interaction_state` 一并清它。生产端口
  （`HelperInteraction`）的 `elicitation_answer` 已是单临界节原子取
  （#1339 fix-r1 融合形），通道级占用把「两线程都观察到 pending」的窗口
  收进同一个 `Mutex` 临界节——这是与 TS 的**结构**等价物（TS 单事件环
  天然原子），代价见「类别」第 2 条的可观察差异。
- #2055-3 panic 兜底：drainer 定时器任务、elicitation 答复任务、
  permission 答复任务三处 `catch_unwind(AssertUnwindSafe(...))`
  （`futures_util::future::FutureExt`），对应 TS `drainInboundBatch` 的
  try/finally、答复链上的 `.finally`/`.catch`；drainer 侧 panic 后按
  `batch.id == timer_batch` 复位 `draining` 并以条目当前 `timer_seq`
  重试，条目被替换（`/new`）则退出。`lock_state()` 以
  `unwrap_or_else(|poisoned| poisoned.into_inner())` 从锁中毒恢复
  （weixin 车道 `lock_inner` 的 #1780 同款）。
- #2055-4 generation 同临界节：`process_inbound_messages` 把
  `mapper.resolve` 与 generation 读入同一段 `lock_state()`；
  `reset_chat_interaction_state` 返回 reset 后的 generation，`/new <正文>`
  的 follow-up 带它出临界节。

## 机器判据

004 的判据除下述一句外全部照旧；「`abortTurn` 无判据」照旧（端口补齐时
须新增用例并改条目）。

- **作废句的替代判据**（原「摘掉 generation 检查必须转红……不成立」）：
  `tests.rs` 的 `gated_submit_superseded_by_new_sends_nothing_and_deletes_reaction`
  钉死两道门 + reaction 删除：gated turn 在飞时经
  `process_inbound_messages` 直投 `/new`（双 drainer 交叠的确定性构造，
  理由见 S0-RESULT P5 送达路径说明）。stale 流按事件分期（`gate_each`
  逐事件门缝）：delta 在 turn 仍 current 时消费进 live 缓冲（其后紧跟的
  marker 问题 POST 是消费完成的可观测证明——流是 FIFO），`/new` 之后才
  放行 stale elicitation。断言出站零 STALE、stale elicitation 问题从未
  发出、reaction 仍被 DELETE、`已创建新会话。` 恰一次。变异分别可杀：
  - 摘逐事件门（事件循环内 `is_current` break 失效）→ 断言
    `#2055 the superseded turn's stale elicitation question is never asked`
    转红（elicitation 问题在事件落地的瞬间直发，不过 flush 门）；
  - 摘 flush 路径（收尾 `if self.is_current` 包裹与 `send_final` 每段
    复查**成对**失效）→ 断言
    `#2055 the superseded turn's stale events send nothing` 转红（缓冲的
    delta 经收尾 flush 发出）。**两处必须一行变异成对摘除**：Rust 的
    `send_final` 比 TS 多一道每段发送前的 generation 复查（自述为
    narrowing、非保证），单摘收尾门会被这道复查兜住、单摘复查会被收尾
    门兜住——两个单点变异都必 SURVIVED，故判据登记为成对变异
    （`gated-flush-and-segment-checks-dropped`）。
- **新增登记差异的判定**：`concurrent_elicitation_events_answer_once`
  钉占用语义（竞态第二事件不再起第二个答复任务，`answers == ["true:first"]`；
  占用摘除变异 → 同断言转红）。TS 侧「在飞事件流回批次」无 Rust 判据
  （该差异属新增登记，待人批；批前按已登记差异处理）。
- **panic 兜底判定**：`panicking_permission_answer_releases_the_token`、
  `panicking_drainer_resets_batch_and_chat_recovers` 分别钉 permission
  token 释放与批次复位（对应变异：摘 `catch_unwind` 恢复裸 await /
  恢复定时器直调 drain → 各自 `until` 超时转红）。
- **generation 同临界节判定**：`new_followup_survives_a_reset_racing_in_the_state_change_window`
  钉 `/new` follow-up 带 reset 后 generation（变异：丢弃
  `reset_chat_interaction_state` 返回值、沿用 resolve 时读数 →
  `#2055 the /new follow-up submits despite the racing reset` 超时转红）。
  **诚实限制**：`resolve` 与 generation 的融合读本身（非 `/new` 路径）
  无确定性单线程杀手——修前修后该窗口内都没有 await，竞态纯跨线程抢占，
  任何单线程用例都无法构造该交错；其依据是 TS 侧同步块结构锚
  （`processInboundMessages` 的 `mapper.resolve` 与 generation 直读同块，
  P6 探针 `p6-resolve-generation.txt`），**不登记为可杀变异**。
- 上述各变异在 S4 已以 `negative_controls.py` 扩面正式落地（六行：
  逐事件门、flush 路径成对门、占用、permission 兜底、drainer 兜底、
  `reset` 返回值），并逐条按注册字符串重验（apply → `cargo test
  --no-run` → 按名跑杀手用例 → restore）：六行全部转红。S1 期间的手工
  验证覆盖逐事件门、占用、drainer 兜底、`reset` 返回值四类；
  flush 门 S1 仅做了结构论证（当时用例未分期，缓冲 delta 到不了
  flush 门），S4 的分期用例 + 成对变异补上了这块判据。
