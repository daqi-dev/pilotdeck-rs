## 类别

不可避免（A7 端口没有 abort 能力）。TS `/new` 在重置会话后调用
`gateway.abortTurn({ sessionKey, runId? })` 终止上一轮仍在跑的 turn；
Rust 的 `TurnGateway` 端口只有 `submit`，没有 `abortTurn`，因此 `/new`
只做本地重置（generation 自增、清队列、清待答交互、清批次定时器），
上一轮 turn 在 gateway 侧继续跑到底，它的输出则在**每次投递前**复查代次、
代次已变即跳过（复查与真正发出之间仍有竞态，见「Rust 行为」节末段）。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/feishu/FeishuChannel.ts:469-481`：

```ts
if (mapped.command === "new") {
  this.onStateChange?.(this.mapper.snapshot());
  const activeRun = this.chatState.activeRun(chatId);
  this.resetChatInteractionState(chatId);
  await this.gateway?.abortTurn({
    sessionKey: activeRun?.sessionKey ?? previousSessionKey,
    ...(activeRun?.runId ? { runId: activeRun.runId } : {}),
  }).catch(...);
  if (!mapped.message) { await this.send({ chatId, text: "已创建新会话。" }); return; }
}
```

`previousSessionKey` 在 `:467` 于 `resolve` 之前取；`around :576` 另有一处
`abortTurn(reason: "system:timeout")`，同属端口能力缺失，见
`A8.3-CH-FEISHU-006`。

## Rust 行为

`src/pilotdeck-gateway/src/channel/feishu/mod.rs:763-786`：先
`on_state_change(snapshot)`（顺序与 TS 一致，在 reset 之前）、再
`reset_chat_interaction_state`，最后按 `mapped.message` 是否为空决定是否
回 `已创建新会话。`；`/new <正文>` 在重置后带着**新**会话 key 继续走
提交路径（与 TS 相同：基线只在 `!mapped.message` 时返回），不做 abort；
注释 `:775-779` 写的是「…the generation bump below makes the event loop and the
flush skip this chat's output once the generation has moved; a segment whose check
already passed — in flight or not yet sent — is outside this gate」：代次门保证的
只是「复查时代次已变就不开始这一段」，**复查通过之后（无论发送是否已经开始）
落下的 `/new` 都拦不住**，见下段。
`reset_chat_interaction_state`（`:815-837`）自增 `entry.generation`、
清空队列与 `active_run`、清 elicitation/permission 状态并 abort 批次定时器；
`process_turn` 的事件循环、收尾 flush、以及 `send_final`（`:1105-1136`）的
**每一段**发送前都过 `is_current(chat_id, generation)`。

**这一层只是把窗口收窄，不是「旧轮回复永不落到该 chat」的保证**：一次段发送在
`send_post`（`client.rs:242` → `send_raw_inner_named:433`，内含
`tenant_access_token` 与 HTTP POST 两个 await）或它的 `send_raw` 文本回退里
挂起时，`/new` 仍可能在两次复查之间自增 generation，该段会继续尝试发送
（是否真的到达 chat 取决于这两次调用的结果）；复查通过后、调用 `send_post`
之前落下的 generation 自增同样拦不住那一段。

两侧残余窗口**不能直接对等**，逐条按源码写：

- TS `FeishuChannel.ts:647` 只用 `isCurrentTurn()` 门住交互状态清理
  （`elicitation.clear` / `permissions.clearAfterTurn`），随后**无条件**
  `await liveReply.flushFinal()`；`abortTurn` 对已经发起的发送是尽力而为
  （调用点带 `.catch(...)`），`flushCurrent` 的回退也不看 abort。因此**若该轮
  执行到收尾路径**，TS 在 `/new` 之后仍会调用 `flushFinal()`，并在 controller
  未关闭且有可发送文本时尝试发出**尚未开始 flush 的缓存文本**
  （`ImLiveReplyController.ts:229` 在 `closed` 时直接返回，发送本身也可能
  失败）。
- Rust 的收尾 flush 与 `send_final` 的每一段都受代次门约束，所以「旧轮已缓存、
  尚未开始发送」的那部分 Rust **可能比 TS 少发**，不是两侧同阶。
- 两者共同的部分只有「已经进入发送调用的那一段仍会继续尝试，可能落地」。

Rust 侧真正的缺口是本条主项：没有 `abortTurn` 端口，旧 run 在 gateway 侧继续
消耗算力与副作用。旧轮的 reaction 清理**不**受 generation 约束——TS 在
`finally` 里删，abort 后也删（Rust `:1081-1088` 同形）。

## 范围

仅 `/new` 触发时对**上一轮在跑 turn** 的终止语义：TS 会请求 gateway 停止该
run（`abortTurn(...).catch(...)`，尽力而为；成功时省算力、停工具调用），Rust
任其跑完，输出在投递前因代次已变被跳过（已进入发送调用、或复查后发送前落下的
那一段除外，见上节）。
**会话切换本身、`已创建新会话。` 回复、持久化 state、后续消息进入新会话的
路径一致**；但**不为「旧轮已缓存、尚未开始发送的文本」给出一致性保证**——
按上节逐条源码描述，这一格 TS 若执行到收尾路径且 controller 未关闭，仍可能
尝试发出、Rust 通常拦下，差异方向是 Rust 少发。
差异的实质在于后台计算与副作用（工具调用、写文件）不会因 `/new` 停止。
不含 `system:timeout` 的 abort（另一条目）。本条不构成判分豁免。

## 机器判据

- `src/pilotdeck-gateway/src/channel/feishu/tests.rs` 的重放用例钉死
  `/new` 的可见行为：`已创建新会话。` 回复、会话 key 形状
  `feishu:chat=<id>:s_<uuid>`、state 回调快照在 reset 前发出。
- generation 隔离目前**只有读码路径、没有组件钉子也没有负控变异**：旧
  generation 的事件在 `process_turn` 的事件循环与收尾 flush 处被
  `is_current` 丢弃（`send_final` 每段发送前再查一次），但本单没有任何
  用例制造「turn 在跑时 `/new`」的时序，因此「摘掉 generation 检查必须
  转红」这句话**不成立，不要按它验收**。缺口登记为
  `P2-跟进`（并发收口单，不前置本 PR 合入）：补一个 gated-submit 用例
  （提交挂起时自增 generation，放行后断言零出站、reaction 仍被 DELETE）。
- `/new <正文>` 的提交路径由组件钉子
  `new_command_with_text_submits_on_the_new_session` 钉住：gateway 收到
  且只收到 `message: "请总结"`（会话 key 形如 `feishu:chat=c7:s_<uuid>`），
  出站没有任何 `已创建新会话。` 文案。
- `abortTurn` 本身无判据（端口无此方法）；补端口时须新增「`/new` 后旧
  run 收到 abort」用例并改本条目。
