## 类别

传输层呈现差异（不可避免）。`wecomCallback` 车道的监听是手写的
`node:http` 等价实现（`src/pilotdeck-gateway/src/channel/wecom_callback/http.rs`），
空闲持久连接的回收时机与响应头由 hyper 决定，而不是 Node `http.Server` 的
`keepAliveTimeout` 路径：Node 在 5 s 空闲后销毁连接并在 keep-alive 响应上
写 `Connection: keep-alive` 与 `Keep-Alive: timeout=5`，Rust 侧这两个头都没有，
空闲连接由 `header_read_timeout`（本模块取 60 s，与 Node `headersTimeout` 的
**取值**对齐、触发时刻不同，见「范围」）兜底关闭。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/wecom-callback/WeComCallbackChannel.ts:123`
`http.createServer(...)` 不带 options，因此 `keepAliveTimeout` 取 Node 默认
5000 ms、`headersTimeout` 60000 ms、`requestTimeout` 300000 ms。Node 在
keep-alive 响应上追加 `Connection: keep-alive` 与 `Keep-Alive: timeout=5`，
空闲超过 5 s 即销毁 socket（`_http_server.js` 的 connections-checker）。

## Rust 行为

`src/pilotdeck-gateway/src/channel/wecom_callback/http.rs:211-222` 的
`http1::Builder` 只设了 `half_close(true)`、`timer(TokioTimer::new())` 与
`header_read_timeout(Timeouts::headers)`（默认 60 s，`http.rs:46-52`）；未设
任何 keep-alive 空闲计时，hyper 也不生成 `Keep-Alive` 头。线上可见结果：

- 空闲持久连接在 Rust 侧最多存活 60 s（下一次请求头读超时到期才关闭），
  Node 为 5 s；
- keep-alive 响应缺 `Keep-Alive: timeout=5`，也缺 Node 显式写出的
  `Connection: keep-alive`（hyper 在 HTTP/1.1 下把 keep-alive 当默认语义，
  这两个头都不生成；同一仓里手写的 Node 等价实现
  `src/pilotdeck-gateway/src/native_http.rs` 明确补了这对头，本条车道没有）。
  22 场景金样只比 status / content-type / body，头名与头顺序不在比较面内，
  故不影响判分。

`stop()` 语义不受影响：`Listener::stop` 翻 watch 后对所有在册连接
`graceful_shutdown`，空闲连接立即退休，不等 60 s，与 Node `server.close()`
一致。该分支的用例覆盖见「机器判据」：现有排空用例只覆盖**半截请求**，
**空闲** keep-alive 连接没有用例。

## 范围

仅 `wecomCallback` 车道监听端**空闲 keep-alive** 的时限与响应头呈现。不覆盖：

- 单请求的 `headersTimeout` / `requestTimeout` 触发**时刻**：本条只对齐了
  `headersTimeout` 的**取值**（双方 60 s），两侧的**起算点**与裁断方式都不同：
  Node 从**每个头的首字节**起算，到期后落在 listen 锚定的 30 s
  connections-checker 网格上（`A8.4-NATIVE-HTTP-002-R2` 第 1 条及其
  `fix-r2/probe-c1.out`：首字节 +30 s 恰在网格点、deadline +90 s 恰在网格点，
  Node 于 +120.001 s 才应答）；hyper 在 **accept 后首次 poll 读头**时武装 60 s
  定时器（本模块的连接任务在 accept 后立刻 poll 一次），**到期即裁**、无网格。
  于是「连接后静默 30 s 再发半截头」这一格：Rust 约在连接后 60 s 关闭，
  Node 约在连接后 120 s 才关闭，差约 60 s（一个完整网格周期），不能用「差一个
  网格点」概括。Rust 侧时刻为读码推断（hyper 1.7.0 `server/conn/http1.rs`
  的 `header_read_timeout` 分支），未用同场景探针实测；
  `requestTimeout` 见 `A8.3-WECOM-CALLBACK-408-001` 与
  `A8.3-CH-WEBHOOK-002` 的时序残差；
- 408 的帧化字节（`A8.3-WECOM-CALLBACK-408-001`）；
- 金样 22 场景矩阵：所有用例都用 `Connection: close`
  （`tests/fixtures/wecom-callback/README.md`），不含空闲 keep-alive 格，
  故本条不影响任何金样判分。

本条不构成判分豁免。

## 机器判据

- `src/pilotdeck-gateway/src/channel/wecom_callback/tests.rs`
  `request_timeout_answers_408_and_releases_stop` 与
  `stop_after_stalled_request`：`stop()` 必须让**半截请求**的在册连接在有界
  时间内退休，防止为对齐 5 s 空闲而把 drain 改坏（**空闲** keep-alive 连接
  不在本判据覆盖内，见下条）。
- 同文件 22 场景重放（`channel_matches_real_ts`）钉死所有用例的状态码、
  `content-type` 与正文（`tests.rs` 的 `parse_raw_response` 只保留这三个
  字段）；头名、头顺序与其它头**不在**比较面内，故加一个 `Keep-Alive` 头
  不会被现有重放发现，需要在 `oracle.json` 新增一条 keep-alive 用例才能
  证明对齐。要主张逐字节验收须另加原始响应字节探针。
- 负控：`src/pilotdeck-gateway/tests/fixtures/wecom-callback/
  negative_controls.py` 的 `header-timeout-timer-removed`（摘掉
  `headersTimeout` 的 timer）必须让
  `stop_drains_a_half_sent_header_once_the_header_timeout_fires` 转红 ——
  即 `stop()` 对**半截请求**的退休是有界且被钉住的。**空闲** keep-alive
  连接分支没有用例覆盖（22 个场景全部带 `Connection: close`），也没有能把
  「`stop()` 跳过空闲连接」杀死的变异体，故不在此登记为机器判据；补齐该
  用例与变异体前，本条只主张半截请求分支。
