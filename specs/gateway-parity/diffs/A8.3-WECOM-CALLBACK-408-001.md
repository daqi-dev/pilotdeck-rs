## 类别

传输层呈现差异（不可避免）。`wecomCallback` 车道的监听是
`src/pilotdeck-gateway/src/channel/wecom_callback/http.rs` 手写的第二个
`node:http` 传输（不复用 `crate::http_proxy` 共享车道）。body 读超时
（Node `requestTimeout` 等价，默认 300 s）后写出的 408 在语义上与 TS 一致
（状态行 408 Request Timeout、`connection: close`、零长 body、随后关连接），
但字节不是 Node 的 51 字节原文：hyper 用公开 API 帧化该响应，线上多出
`date` 与 `content-length: 0`。hyper 不提供改写状态行/帧头的公开扩展点，属
`A8.3-CH-WEBHOOK-001` / `A8.4-NATIVE-HTTP-001` 已登记的同一 hyper-public-API
呈现差异类。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/wecom-callback/WeComCallbackChannel.ts:123`
`this.server = http.createServer((req, res) => void this.onHttp(req, res));`
——无 options，故 `requestTimeout` 取 Node 默认 300000 ms、`headersTimeout`
60000 ms。body 未读完即超时时 Node 走 `_http_server.js`
`requestTimeoutResponse`，原文恰为 51 字节
`HTTP/1.1 408 Request Timeout\r\nConnection: close\r\n\r\n`（无
`content-length`、无 `date`、无 `Transfer-Encoding`）。该字节常量在仓内另见
`src/pilotdeck-gateway/src/user_dialog/http_store.rs:85`（`NODE_408_RESPONSE`，
真实 `node:http` 探针与 fixture
`tests/fixtures/user-dialog-http-store/header-lifecycle/node-408.bin`），与
`A8.3-CH-WEBHOOK-001` 引用的是同一份实测。

## Rust 行为

`src/pilotdeck-gateway/src/channel/wecom_callback/http.rs`
`request_timeout_response()`（`:73-80`）构造：

```text
HTTP/1.1 408 Request Timeout
date: <httpdate 当前时刻>
connection: close
content-length: 0
```

随后 `connection: close` 让 hyper 关闭该连接；handler 在
`http.rs:205-208` 用 `tokio::time::timeout(Timeouts::request, …)` 把
超时映射为该响应（默认 `request` = 300 s，见 `http.rs:46-52`）。
与 Node 逐项比对：状态行、`connection: close`、零长 body、关连接一致；
多出 `date` 与 `content-length: 0`，且头名小写（hyper 的 HTTP/1.1 线上写法）。

## 范围

仅 `wecomCallback` 车道 body 读超时 408 的**帧级呈现**，一条响应、一个场景：
客户端声明 `Content-Length` 后不把 body 发完，超时到期时线上字节。不覆盖：

- 超时**触发时机**（Rust 恰在 deadline，Node 落在 30 s connections-checker
  网格）——同族时序残差登记在 `A8.3-CH-WEBHOOK-002`，本车道未单独登记；
- 空闲 keep-alive 的 60 s vs 5 s 与缺失的 `Keep-Alive: timeout=5` 头——见
  `A8.3-WECOM-CALLBACK-KEEPALIVE-001`；
- 金样 22 场景矩阵不含 408 格（`tests/fixtures/wecom-callback/README.md`），
  故本条不影响任何金样判分。

本条不构成判分豁免：把 408 字节断言改松仍会让下列测试报错。

## 机器判据

- `src/pilotdeck-gateway/src/channel/wecom_callback/tests.rs:1121`
  `request_timeout_answers_408_and_releases_stop`：半截 body + 客户端保持
  socket，`Timeouts { request: 300 ms }` → 收到的字节以
  `HTTP/1.1 408 Request Timeout\r\n` 开头、含 `\r\nconnection: close\r\n`、
  **首个空行（`\r\n\r\n`）之后没有任何字节**（零长 body——不是「以
  `\r\n\r\n` 结尾」，后者对正文恰为那四字节的响应也成立），**且在 1 s 读取
  期限内读到 EOF**（只收到响应头就到期与真正的零长正文在字节上无法区分，
  单看字节会假通过），并发 `stop()` 在有界时间内返回。反方向同样钉住：`requestTimeout` 调大到 30 s 的同一半截
  请求在 1 s 内**一个字节都收不到**（读取函数的超时分支保留已收字节，不会把
  「提前应答但未到 EOF」当成没应答）。
- 同文件 `concurrent_posts_for_one_chat_dispatch_once`（`PORT 18994`）与
  `tcp-open` 相关用例复用同一 `listen_with` 路径，防止为过 408 断言而改坏
  排空语义。
- 负控：`src/pilotdeck-gateway/tests/fixtures/wecom-callback/
  negative_controls.py` 的 `wecom-408-without-close`（删 `connection: close`
  头）与 `wecom-408-with-body`（把 408 的正文换成 `\r\n\r\n` 这四字节——正
  是「以 `\r\n\r\n` 结尾」判据抓不到的那种正文）必须让上条测试转红。
