Rust 侧 fire-and-forget 发送可能整行丢失请求，TS 基线确定。修复后已对齐，

## Rust 行为

修复前：`runtime/mcp/http.rs` 的 `send_streamable` 对 initialized GET 用裸
`tokio::spawn(start_sse(...))`，无派发保证；调度饥饿时该任务首询晚于
`close()` 的同步取消，`network_fetch` 的
`if !continuation_before_abort && aborted.is_cancelled()` 门把未派发请求按
`network_abort` 拒绝，GET 整行不发。同类兄弟位：`runtime/mcp/wire.rs` 请求
后台发送、`notifications/cancelled` 超时发送、`dispatch_http` 回复发送（均为
TS 同步调用点、Rust 裸 spawn）。

修复后（`runtime/mcp/http.rs:1477` `detach`）：先把 continuation 内联首询到
第一次挂起（一次到达 exchange 注册的 poll），再把余下部分照旧 `tokio::spawn`。
内联 poll 用 no-op waker：可能丢失的唤醒均为锁存状态（tokio I/O/timer、
oneshot 值），spawn 后首询可观察到并重注册真实 waker；`detach` 本身不挂起
调用者。应用于 http.rs:1353（initialized GET）、wire.rs:531（请求发送）、
wire.rs:456（`send_detached`，覆盖超时 cancel 与 HTTP 回复）。

abort 发生在 exchange 已真正在途时的行为不变（undici `forwardAbort` 同款，
TS 一致）；本修复只消除「abort 早于派发但晚于 send() 返回」的窗口 A。

## 范围

仅 fire-and-forget 发送在调用者下一步操作之前的派发顺序：streamable HTTP 的
initialized GET、请求 POST、`notifications/cancelled`、服务器请求的
`Method not found` 回复。stdio 队列语义不变（本就同步）。不改变 wire 上的
请求顺序（此前也只有一个在途请求）；不加 sleep、不加重试、不放宽 oracle。
已建立 SSE 流的 `handle_sse_stream` 消费、`event_source`、重连（无再入队
间隙）不属于该窗口，未改动。
