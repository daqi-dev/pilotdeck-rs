## 类别

**本轮有意未对齐**（停机时长有界化差异）：sms 车道 `SmsHandle::stop()` 的
**drain 上限**。#2026（决策 C，人 2026-11-07 07:24Z 拍板）把 `stop()` 从「立即
返回、连接 detach」改为「等在途连接到自然期限」，但因为 TS 的对应语义是
`server.close()` **无界阻塞**（半截头连接上实测永不返回，见基线依据），抄
`wecom_callback` 形态时必须给 drain 加上限；本条登记的就是这个「有界 vs 无界」的
差异及其三条派生残差。**这不是漏抄，是决策 C 的明文要求**（任务书：「必须加
drain 有上限，因为照抄 TS 的语义会在半截头连接上无限阻塞」）。

四条具体差异（同源于同一个上限，合并登记）：

1. **无界 vs 60 s 上限**：TS `stop()` 等到客户端离开（在档 199,001 ms 未
   resolve，右删失）；Rust `stop()` 最多等 `STOP_DRAIN_LIMIT`（60 s）。
2. **截断后的处置**：上限到点时剩余连接被 **abort**（`JoinSet` drop 会中止其
   中所有任务，socket 随任务 drop 关闭，实测截断后 2 s 内 EOF）——TS 下没有
   「截断」概念，那些连接会一直把 `stop()` 钉在 close 回调里。
3. **空闲 keep-alive 停机时长**：TS `httpServerPreClose` 先
   `closeIdleConnections()`，空闲 keep-alive 连接在 close 时立即被关；
   Rust 的 drain 不区分 idle，一条等下一请求头的空闲连接要把 stop 拖到它的
   头读期限（读下一请求头也由 `header_read_timeout` 兜底，`A8.3-CH-SMS-012`
   残差 3），上限 60 s 封顶。
4. **截断时刻的 client**：TS 在 close 回调（连接全部结束后）才清 client；Rust
   在上限截断 `stop()` 返回时即清，此时被截断的连接刚被 abort、socket 已在
   关闭中——即
   `A8.3-CH-SMS-013-R1` 更正后剩下的那半条残差（未截断的 drain 内 TS 与 Rust
   已一致：client 都可用）。

## Rust 行为

`src/pilotdeck-gateway/src/channel/sms/mod.rs`（#2026，基于 5c694ee6e）：

- `STOP_DRAIN_LIMIT = 60 s`（`:104`），命名常量，依据写在注释里：头读期限同量级
  ——头阶段停发的连接必然在「accept + 60 s」内自然到期，而 drain 从 `stop()`
  调用起算、晚于 accept，所以**头阶段连接总能被 drain 到自然期限**；更长连接
  （体读 300 s、handler 挂起）在 60 s 被截断并 abort。
- accept 循环任务内 `tokio::task::JoinSet`（`:650`）收每条连接任务，spawn 后
  `try_join_next` 回收已完成的（`:698`，防 JoinSet 随进程增长；wecom 同形）。
- 循环 break 后 drain（`:722-741`）：`tokio::time::timeout(STOP_DRAIN_LIMIT,
  while connections.join_next().await.is_some() {})`；超时 `warn` 一行（含
  剩余连接数），随后任务收尾 drop `JoinSet`，**剩余连接任务被 abort**（tokio
  JoinSet drop 中止其中所有任务），socket 随之关闭。
- `SmsHandle::stop()`（`:356-384`）结构不变：`shutdown.send(true)` →
  `server.task.await`（**drain 在 task 内，await 即等 drain**，`:379`）→ 清
  client（`:381`）。client 清理因此落在 drain 之后，与 TS close 回调的顺序一致
  （`A8.3-CH-SMS-013-R1`）。
- 变异开关：`sms-stop-no-drain`（`:725`，回到 #2026 前的 detach 形状）与
  `sms-stop-drain-unbounded`（`:728`，回到 TS 无界形状）；旧开关
  `sms-stop-waits-for-connections`（#2035）随语义反转删除。
- 停机期间新连接：drain 中 backlog 挂起，`stop()` 返回（listener drop）后
  拒绝——TS 在 close 一开始就拒绝（`afterStopPort: refused`）；两侧
  「`stop()` 返回后拒绝」一致，drain 窗口内的差异并入残差 1。

## 范围

只影响 `SmsHandle::stop()` 从调用到返回这段窗口的时长与截断行为：

| 场景 | TS | Rust（本条登记后） |
| --- | --- | --- |
| stop 时有半截头/零字节连接 | 阻塞到客户端离开（≥199 s 实测，无界） | drain 到头读期限（≤60 s），`stop()` 必然等到自然到期 |
| stop 时有体读停发（≤300 s）/handler 挂起的连接 | 同上无界 | 60 s 截断返回，剩余连接被 abort、socket 关闭 |
| stop 时空闲 keep-alive 连接 | `closeIdleConnections` 立即关，stop 快速返回 | drain 等其头读期限（≤60 s）或上限截断 |
| stop 期间 client | drain 中可用（013 实测） | 未截断：drain 中可用（一致）；截断：stop 返回即清（残差 4） |
| stop 后新连接 | 拒绝 | 拒绝（drain 窗口内 backlog 挂起，残差 1 并入） |

不在本条范围：

- 头读期限到期时的**线上字节与 30 s 网格**（`A8.3-CH-SMS-010` / `-012` 残差
  1/2/3，决策 B 另开单，本条不动其批准状态）；
- `fire-and-forget` 的 `handleIncoming` 后台任务（`mod.rs` 的
  `tokio::spawn(handle_incoming...)`）：它们不是连接，Node 的 `close()` 也不等
  它们，两侧一致不在 drain 内；
- `stop()` 的 reason 默认值（`A8.3-CH-SMS-004` 族）；
- 56 格金样：`tests/fixtures/channel-sms/oracle.json` 无 stop-drain 场景格，
  本条不影响判分，也不增加豁免。
