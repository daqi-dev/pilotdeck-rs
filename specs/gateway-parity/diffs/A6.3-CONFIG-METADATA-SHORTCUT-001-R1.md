## Rust 行为

更正原条目「两种实现都把读取失败哈希成『无内容』而不重试（#1792）」与「『#1739 前能检出』还隐含两次内容读都成功且读到不同字节」两句：

1. 「旧实现能检出」的成立条件是**两次内容哈希不同**（充分条件的写法）：一次成功、一次失败（`Some(bytes)` 对 `None`）哈希也不同，预 #1739 的实现照样能检出（并触发一次 reload）；只有**两次都读失败**（都哈希成 `None`）才检不出。原句把它写成「两次都成功且字节不同」，是必要条件的过窄表述（#1819 第 10 条）。
2. #1792 修复后该括号说明已过期：不完整采样（stat / `read_dir` / 内容读任一失败）**不提交 metadata 指纹**，下一 tick 重试直至完整样本落地；失败的读取不再永久关闭恢复路径，「两种实现都不重试」不再是本条目（或 POLL 条目）的口径。恢复语义由 `config::store::tests::transient_read_failure_is_retried_until_the_content_is_seen` 与 `startup_read_failure_is_retried_until_the_content_is_seen` 钉住。

## 范围

漏检四条件的第 3 条更正为「**两次哈希的 `modified().ok()` 相等**」：粗粒度文件系统上同一 mtime tick 内的改写可能天然 mtime 相同；两次 `modified()` 都失败（都 `None`）也相等。「改写方把 mtime 精确还原」（`rsync -t` / `cp -p` / `touch -r`）只是达成该条件的一种方式，不是条件本身（#1819 第 11 条）。其余三条（ctime tick、长度一致、inode 不换）与「经父目录监视时同目录其它参与指纹的目录项也不变」的完整条件、HFS+ / APFS 窗口宽度论证均同原条目，不改。
