## 类别

有意改进（方向更严）：cron 调度器的 tick 串行化与权威 stop，消除 TS `CronScheduler`
的两个定时器竞态——poke-during-tick 定时器泄漏（tick 可重叠）与 post-stop tick
（stop 后仍可再跑一个 tick）。竞态不消除时泄漏的定时器会重复触发任务提交；本条
选择结构性消除（单线程串行 + stop 全权威），不是行为对齐。

## TS 依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0 / ICU 78.2。
`src/cron/runtime/CronScheduler.ts:71-90`：timer 槽是单字段，`scheduleNextTick`
直接赋值 `this.timer = setTimeout(...)`——tick 进行中（timer 槽已清）时到达的
poke 会臂一个 250ms 定时器，tick 结束的重臂再覆盖同一个槽，旧定时器**不被清除**
（泄漏，两个都会触发，tick 可重叠）；`:43-53` 的 `stop()` 只 `clearTimeout` 当前
槽，一个已入队、槽外无法清除的定时器回调仍会跑一个 post-stop tick。实测原件：
`tests/fixtures/cron-scheduler/probe.mts`（钉 2026-01-01 时钟 + `node:test` mock
timers）的 `S8-poke-during-tick-leaks-second-timer` 与 `S10-post-stop-tick-leak`
两格均输出 `leakedTimerFired:true`（18 场景三轮字节一致的原始输出见
`_tmp/20261108-issue-2295-r2/r1-probe-output.txt`，探针命令同目录
`r1-probe-command.txt`）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/cron/scheduler.rs`：定时器的席位是一根专用
调度线程在 `(Mutex<TickState>, Condvar)` 上等待的 `deadline`；tick 在该线程上
串行执行（`tick_busy`），poke 递增 `generation` 并把 `deadline` 置为
`now + MIN_TIMER_MS(250ms)`，tick 结束后的重臂只在 `generation` 未变时落位
（poke 已置的更近 deadline 保留）；`stop()` 置 `stopped`、清 `deadline`、
notify 后等 `tick_busy` 清零再 join 调度线程（= TS `await
tickInProgress.catch(() => undefined)`），线程退出后**结构性不可能**再有 tick
——post-stop tick 在 Rust 侧不可达，tick 重叠同理。

## 范围

只覆盖 cron 调度器的两个竞态面：tick 重叠（S8）与 stop 后触发（S10）。tick 的
其余语义不变：60 s 空转轮询 + `isDue` 过滤、poke 的 250 ms 下限、`runTickOnce`
不受串行门（CronScheduler.ts:66-69 对应）。claim 栅栏
（`matchesScheduledSnapshot`）本就把重叠 tick 的二次触发折为 aborted 无记录，
因此本条在任务提交面上多数情况不可观测；可观测差异是泄漏定时器造成的重复
fire 线程与 warn 噪声在 Rust 侧不出现。always-on（无 abort、无调度线程）与
cron 管理面（create/update/delete）不受本条影响。
