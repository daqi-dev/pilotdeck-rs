## 类别

bug 修复（安全，向安全偏离）。`PILOTDECK_DUMP_REQUEST=1` 的 dump 正文含完整用户对话，TS 用毫秒时间戳做文件名并经 `writeFileSync`（默认 flag `w`，O_WRONLY|O_CREAT|O_TRUNC）写入共享临时目录：同毫秒并发请求互相截断覆盖 dump（数据丢失），毫秒可预测的文件名 + 跟随符号链接的截断打开允许共享目录上的其他用户用预置 symlink 覆盖任意可写目标（数据破坏），默认 umask（实测 0644）让 dump 全局可读（内容泄露）。三条均属 CLAUDE.md「什么算 bug」第 ③ 条安全问题，按「默认修」授权修复；与 TS 的一致性让位于安全，故登记本条。不能因 TS 同样有此写法而忽略（任务 #621 明确）。

## TS 依据

cc7c4e6 的 `src/model/streaming/streamModel.ts`：

- `:196-203`（OpenAI 路径）与 `:395-401`（Google 路径）：`if (process.env.PILOTDECK_DUMP_REQUEST === "1")` 后 `path.join(os.tmpdir(), \`pilotdeck_request_${Date.now()}.json\`)` + `fs.writeFileSync(dumpPath, JSON.stringify(body, null, 2))`。
- `os.tmpdir()` 在 macOS 返回用户私有 `$TMPDIR`，在 Linux 常为共享 `/tmp`；文件名只有毫秒时间戳，`writeFileSync` 跟随既有符号链接、截断既有文件、按 umask 建权限。
- Rust 侧最小实测（darwin，探针与原始输出见本树 `_tmp/20261025-issue-621-provider-tail/scratch/probe-output.txt`）：`File::create` 对 symlink 目标截断改写（受害者数据丢失）；同名二次 `File::create` 截断前次内容；默认 mode 0644；对照 `create_new`（O_CREAT|O_EXCL）对 symlink 与既有文件均报 `AlreadyExists` 且不触碰目标，`mode(0o600)` 得 600。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/model/http.rs` 的 `dump_request_to_file` / `write_dump_exclusively`：

- 目录改为 `std::env::temp_dir()`（对齐 TS `os.tmpdir()`，修正此前硬编码 `/tmp` 与 TS 落点不一致的偏离）。
- 文件名 `pilotdeck_request_<毫秒>_<pid>_<进程内单调序号>.json`（`next_dump_name`）：进程内单调序号保证并发唯一，跨进程 pid 不同；TS 只有毫秒时间戳。
- 创建用 `OpenOptions::write(true).create_new(true)`（O_CREAT|O_EXCL，unix 下 `mode(0o600)`）：拒绝跟随预置 symlink、拒绝截断既有文件；`AlreadyExists` 换下一候选名（最多 8 个）而不是截断。
- 触发条件、目录、日志行（`[model-debug] Request dumped to <path> (model=<model>)`）与 TS 一致；Google 路径本轮才接上（TS `:395-401`），model 取自 canonical 请求而非 URL 之外的信息。**fix-r2 起 dump 仅在流式发送触发**：TS 只在两条流式循环里 dump（`:196` 与 `:395`），`complete()`（`:124`）直接调 `sendProviderRequest` 不 dump；Rust 的 `send_provider_request` 此前被 `complete_model` 与 `stream_model` 共用而无分流，complete 也会 dump，属未登记偏离，fix-r2 以 `stream` 门控对齐（此前 complete 路径的 dump 是 main 既有行为，本轮修正）。Google 的 `send_google_request` 只服务流式路径（Rust 不支持 Google complete，另行登记），无需门控。
- 残余已知项（不在本条修复）：dump 在 async 路径上同步 `std::fs` 写 + `println!`，阻塞 tokio worker（旧评审 P3，debug 门控下影响有限，未修）；写中途失败可能留下部分文件（TS `writeFileSync` 同样可能，实测 `ulimit -f` 下 TS 留 1024B 部分文件）。

## 范围

仅 `PILOTDECK_DUMP_REQUEST=1` 的调试 dump。dump 调用点与 TS 一一对应：通用发送路径 `send_provider_request`（anthropic、openai、openai-responses 三种协议共用，仅 `stream_model` 流式调用触发；`complete_model` 走同一函数但不 dump，与 TS `complete()` 一致）与 Google SDK 路径 `send_google_request`（仅流式）。正常请求路径、请求正文内容、错误形状均不受影响。偏离点：

- ① 文件名多出 pid 与序号（TS 只有毫秒时间戳）；
- ② 独占创建拒绝而非跟随/截断（TS `writeFileSync` 跟随并截断）；
- ③ 权限 0600（TS 按 umask，共享 `/tmp` 下实测 0644）；
- ④ **dump 正文投影**：Rust dump 的是实际发送的 wire body——OpenAI 为 `extraBody` 合并后、Google 为 SDK `config` → `generationConfig` 投影 + `extraBody` 深合并后（`providers::google::final_body`）；TS 两处 dump 的都是 `buildModelRequest` 的 pre-SDK 输出——TS dump 含 `model` 字段、`config` 形状、`abortSignal` 序列化伪影 `{}`、且不含 `extraBody`，与其实际发送的 wire body 是两个不同投影。实测依据（fix-r1 轮补）：`_tmp/20261025-issue-621-fix-r1/ts-probe/`（fix-r2 时已不在树上；现树可用探针为 `_tmp/20261025-issue-621-fix-r2/ts-probe/`，其 Google 流式 case 的 dump 正文同为 pre-SDK 投影，可复算）。保留「dump 实际发送正文」的实现：dump 的用途是核对线上真实负载，且 OpenAI 路径 main 早已是发送正文投影；按任务约束本轮不擅自改变 dump 投影，登记为已明确分歧待人批（若人批要求对齐 TS 形状，需同步处理 OpenAI 路径的同类偏差）。
- ⑤ **写失败的错误语义**：实测（fix-r2 探针：本树 `_tmp/20261025-issue-621-fix-r2/ts-probe/`，`PROBE.md` 及 `scratch/out-*.json`；fix-r1 轮的 `ts-probe/` 证据已不在树上，由本探针替代）TS 两路 dump `writeFileSync` 失败都不发送——Google 路径 throw 落进 attempt catch → `toProviderError` → 恰一个非重试 `error` 事件，SDK 完全不调用；OpenAI 路径 throw 原始 fs Error 出生成器（dump 在 send 的 try 之外），不发送不重试。探针实测（ENOENT/EACCES/ENOTDIR/EFBIG 四形）钉住：`raw` 是 fs Error 自身的 JSON 投影 `{errno,code,syscall,path}`，**`errno` 为 libuv 负值**（-2/-13/-20/-27）；open 阶段失败（目录不存在/不可写/父组件是文件）`raw.path` 在、消息为 `<CODE>: <描述>, open '<路径>'`；write 阶段失败（`ulimit -f` 实测 EFBIG）**`raw` 无 `path`**、消息为 `EFBIG: file too large, write`（无路径后缀）；四种 errno 的 `retryable` 均 `false`（TS `isRetryable(undefined,"<errno code>")` 走 fallback false）。Rust 对齐 Google 路径：`write_dump_exclusively`/`dump_request_to_file` 返回 `DumpFailure`（`code`/描述取自 `node_io` 的 Node v22 libuv 生成表 `crate::node_io::lookup`——fix-r2 改，此前按平台 strerror 文本解析的映射表与 libuv 文案对不上，darwin 的 ENAMETOOLONG（strerror 为 "File name too long"）落不进表；`syscall`；open 失败带 `path`，write 失败不带，同 TS；`errno` 存 `-raw_os_error()`，同 TS 符号），`dump_failure_error` 构造同 TS 的 canonical 非重试错误事件（`normalize_model_error` 保留传入的 `raw`，不覆写），先于 `send_google_request` 的发送返回；`retryable` 显式钉 `false` 与 TS 对四种实测 errno 的推导一致（非 ENOENT 也不重试）。OpenAI 路径维持本 port 既有（main 已在）的「打印 stderr 后继续发送」，登记为残余偏离待人批。
