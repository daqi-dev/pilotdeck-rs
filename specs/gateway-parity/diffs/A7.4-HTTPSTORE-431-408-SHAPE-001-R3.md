## 类别

差异消除（请求头超时 408 的字节与触发；431 的额外头与头名大小写），并登记剩余差异。
R2 记录的「Rust 头超时为 0 字节 EOF」「Rust 431 为 123 字节且多
`content-length: 0` / `date`」在常规读路径上不再成立；本条目只登记本单消除的部分和仍然
存在的差异，**未批准，非已接受差异**。

Node 408 与 431 的常量来自 `_http_server.js`（`process.binding('natives')` 逐行核对）：
`requestTimeoutResponse` 51 B、`requestHeaderFieldsTooLargeResponse` 67 B，均只有状态行 +
`Connection: close` + 空行。

实测的关键语义（R2 未覆盖）：

- 后续请求不是无条件 408：`keepAliveTimeout + keepAliveTimeoutBuffer`（默认 6 s）的
  `socket.setTimeout` 与首字节起算的 `headersTimeout` 竞速。默认单次部分后续头在
  **6,049 ms 静默 EOF**（`keepalive-partial-head`）；短配置
  `headersTimeout=300 ms, keepAliveTimeout=5 s` 时才在 358 ms 收到 51 B 408
  （`short-keepalive-partial-header-wins`），`keepAliveTimeout=100 ms` 时 111 ms 静默关闭
  （`short-keepalive-partial-idle-wins`）。
- body 未收完时 Node 也在 requestTimeout 回同一 51 B 408（短超时 308 ms，
  `short-body-timeout`）。
- `server.close()` 会先清掉 connections checker：parser 已消费部分头或 body 在途时连接
  既不销毁也不再触发定时器，实测 4–8 s 挂起、0 B（`short-shutdown-initial-partial`、
  `short-shutdown-body-pending`）；零字节 / 部分头在 close 抢在 parser 之前时才被 RST 销毁
  （`short-shutdown-initial-zero`、`short-shutdown-initial-partial-immediate`）。所有
  shutdown 路径都 **不发 408**。

## Rust 行为

`src/pilotdeck-gateway/src/user_dialog/http_store.rs`：

- `NODE_408_RESPONSE` / `NODE_431_RESPONSE`（`:82`、`:85`）逐字节复制 Node 常量。
- `KeepAliveTimer::expired`（`:1888`）区分 `Headers` 与 `Idle`：`InitialHeaders` /
  `NextHeaders` 的 `header_deadline` 到期归 `Headers`；`Idle` 或 `NextHeaders` 中先到期的
  idle 期限归 `Idle`。`NextHeaders` 里 idle 先于 header 的判断与 Node 两定时器竞速一致。
- `TimeoutStream::expire`（`:2232`）在 `Headers` 到期时把 51 B 写入底层 socket，再返回
  EOF；`Idle`（keep-alive 超时）仍静默 EOF。写用同一个 `poll_read` 任务的
  `poll_write`（`:2256`），不新开任务，避免和 hyper 的响应头写出竞态（#702 第一处）。
  `server.close()` 启动后 `KeepAliveTimer::begin_shutdown` 把 header 期限折叠成 `Idle`，
  所以 close 等待期不会写 408（Node 在 close 里清掉 checker，同样不发 408）。
- `HeaderGuard`（`:2024`，`push` 在 `:2101`）在 `poll_read` 里按 Node v22.22.0 的
  `maxHeaderSize` 账本累计：请求 target + 每个字段 name + 每个字段 value；方法、空格、
  `:`/CRLF 不计，值前导空白不计、尾随空白计入（与上节探针逐项一致）。累计到
  `>= max_header_bytes` 即写 67 B 431 并 EOF，未完成行也逐字节计入，因此不会等行结束才
  触发。`begin` 在 `Idle` / `NextHeaders` 重置扫描器，覆盖 keep-alive 后续请求；body
  相位不扫描。
- 另有两道资源上界（`hyper_buffer_bytes` `:95`、`header_guard_raw_limit` `:106`）：
  `max_buf_size = 4 × max + 3 × 8 KiB`，guard 的 raw 计数到
  `4 × max + 2 × 8 KiB` 就用同一 67 B 431 关闭。`4 × max` 覆盖最密的 Node 合法形状
  （`a:` 每 1 个计数字节占 4 个 raw 字节），所以常规路径上 hyper parser 不会先写自己的
  123 B 431；raw 上界只对超量不计数前导空白生效（见「仍存在」）。
- `serve` 的既有 `header_bytes` 检查保留为「hyper 已缓冲、guard 看不到」的背压兜底
  （`:2682`，计数在 `:2717`）。它改成同一 Node 账本（target + name + value、`>=`、
  与 guard 相同的 8 KiB floor），但仍经 `empty_response` 走 hyper 形状的 123 B 431。
  hyper 已去掉首尾值空白；前导空白与 Node 一致，流水线头若带尾随 OWS 会少计 Node 的总数
  （guard 的正常路径按 raw 字节计，精确）。

## 范围

已消除（常规读路径，逐字节等于 fixture）：

1. 首请求零字节空闲 → 60 s 写 51 B 408，随后 EOF。Rust 取 Node 60–90 s 窗口的确定性下界
   60 s：不模拟 30 s `connectionsCheckingInterval` 的相位量化，避免实际超时落在 60–90 s
   的随机点；字节与关闭语义逐字节对齐（`rust-default-probe.log` 60.001495 s）。
2. 首请求部分头 → 51 B 408；keep-alive 后续部分头在 header 期限先到时 → 51 B 408；
   idle 期限先到时 → 静默 EOF（与 Node 的 `socket.destroy()` 一致，不发 408）。
3. 首请求 / 后续请求的超限头（16 KiB 字段预算；字段数 ≤ 4,096 且 raw 未触发
   `仍存在` 的资源上界）→ 67 B 431，不再有 `content-length: 0` / `date`，头名
   `Connection` 大写。计数口径改为 Node 的
   target + name + value：恰 16,383 通过、16,384 失败；2,000×`aaaaa: x`（raw 20,000 B）
   通过、2,730 个失败；不再按整行 raw 字节提前拒绝。未完成行按到达字节累计，16,384 raw
   已完成字段 + 16,368 B 未完成行的形状也由 guard 写出 67 B（`node-header-budget.json`
   的 `buffer-boundary-incomplete-line` 与同名 Rust 用例）。

仍存在、如实登记（不据此新增豁免）：

- **body `requestTimeout` 的 408 形状**：仍由 `serve` 的 `empty_response`
  （`http_store.rs:2672`）经 hyper 写出，带 `content-length: 0` / `date`、头名小写；
  Node 实测为 51 B（`short-body-timeout`）。本单验收只覆盖请求头超时；该差异留待后续单。
  计时也不同：Rust 300 s 整点触发，Node 受 30 s checker 量化到 300–330 s。
- **hyper 已缓冲的流水线头**：若客户端在请求 body 期间把下一个请求头整个流水线进同一读
  缓冲，guard 在该相位不扫描，会走 `serve` 的 `header_bytes` 兜底并写出带
  `content-length` / `date` 的 123 B 431。读码推断，未单独抓包。
- **guard 的 raw 资源上界**：Node 没有 raw 缓冲上限，且不把值前导空白计入
  `maxHeaderSize`；hyper 必须先缓冲完整头再解析，所以 guard 在
  `4 × max + 2 × 8 KiB` raw 字节处用同一 67 B 431 提前关闭。实测 90,000 B 前导空白的
  `X: <spaces>a` Node 返回 200，Rust 返回 431（`node-header-budget.json` 的
  `leading-ows-90000` 与 `header_guard_raw_cap_uses_node_431_bytes`）；这是资源约束，
  未批准。
- **hyper `max_headers(4096)` 字段数兜底**：Node v22.22.0 运行时 `maxHeadersCount` 为
  `null`（不限；文档的 2000 不生效），hyper 的 parser 数组需按上限预分配，所以保留
  4,096。一个 Node 合法、计数仍 < 16,384 但字段数 > 4,096 的头（如 4,097 个 `a:`）会拿到
  hyper 的 123 B 431；Node 实测 200（`node-header-budget.json` 的
  `fields-4097-empty-value`）。未批准。
- **shutdown**：Node 在 parser 已消费部分头 / body 在途时 `close()` 挂起、0 B；Rust 的
  `graceful_shutdown` 在部分头时同样挂起且 header 期限折叠为静默 EOF（不发 408），body
  在途时仍会在 `request_timeout` 后写 hyper 形状的 408 再关。两者都不发头超时 408；
  终止界限不同。
- **malformed request 400 / URI too long 414**：hyper parser 的自动响应形状与 Node
  `_http_server.js` 的 `badRequestResponse` 不同；不在 R2 / 本单范围，另开跟进。

#702 的两处未改：新代码只在请求头相位写 raw 字节，不参与 shutdown 判定，也不改早退
响应 + 未读 body 的 `Connection: close` / RST 路径；`poll_write` 在 `closed` / raw 写出
期间拒绝 hyper 追加响应，避免在 408/431 之后混入第二个响应头。
