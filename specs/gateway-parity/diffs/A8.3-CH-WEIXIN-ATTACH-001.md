## 类别

有意改进（防资源放大 · 向严）。基线 `ImAttachmentStore.saveFromUrl` 只在两处比
`maxBytes`：响应头 `content-length` 与**变换后**的 `buffer.byteLength`；读 body
本身不设上限（`await response.arrayBuffer()` 把整个响应吃进内存）。Rust 侧在读流
上封顶 50 MiB，且这一步发生在附件变换（微信媒体解密）**之前**，所以「密文因
padding 略大于 50 MiB、解密后不超过 50 MiB」的附件会被拒，而基线接受。拒绝超限
附件的端到端可观察结果不变；变的是这一个边界工况与超限诊断里的字节数。

本条与 `A8.3-CH-WEIXIN-MEDIA-CAP-001`（#1823 登记的读流上限）是同一处实现的两个
面：那条记的是「无 `content-length` 的超大响应会提前截断、错误串报 `limit + 1`」，
本条补记「截断发生在解密前，因此密文比明文多出的 PKCS#7 padding（≤ 16 字节）会
落进上限」这一后果。两条都不改判分，均由人复核。

## 基线依据

固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85，Node v22.22.0。
`src/adapters/channel/protocol/ImAttachmentStore.ts`：

1. `:62-65` 读 `content-length`，`Number.isFinite` 且 `> maxBytes` 时抛
   `Attachment is <n> bytes (limit <max>).`；
2. `:67` `Buffer.from(await response.arrayBuffer())`——**无读流上限**；
3. `:68-70` `buffer = Buffer.from(await input.transform(buffer))`；
4. `:71-73` 变换后再比 `buffer.byteLength > maxBytes`，同样报
   `Attachment is <n> bytes (limit <max>).`。

微信调用方 `src/adapters/channel/weixin/WeixinChannel.ts:578-590`（image）与
`:592-608`（file）把 `decryptWeixinImageOrThrow` / `decryptWeixinFile` 作为
`transform` 传入，即上限比较的就是**解密后**的明文长度。金样格
`media-cdn-download-declared-too-large` 钉的是第 1 条（声明长度 52428801 →
读 body 前拒绝），与 Rust 一致，不在本条范围。

## Rust 行为

- `src/pilotdeck-gateway/src/channel/weixin/media.rs:490-501`：
  `read_body(..., WEIXIN_ATTACHMENT_MAX_BYTES, ...)` 在**原始响应字节**
  （微信附件此时仍是 AES-CBC 密文）累计越过 50 MiB 时立即停止，映射为
  `Attachment is 52428801 bytes (limit 52428800).`——报的是必然已到达的最小
  超限字节数（上限 + 1），不是基线那样的真实总长度。
- `src/pilotdeck-gateway/src/channel/im_attachment.rs:228-239`：`transform` 之后
  再比 `buffer.len() > self.max_bytes`，与基线第 4 条同序同文案
  （`Attachment is <n> bytes (limit <max>).`，不含 label）。

## 范围

影响所有「实际响应体超过 50 MiB、而响应头没有给出一个**有限且 > 上限**的声明长度」
的下载（也就是基线不会在读 body 之前就拒绝的那些），包括两种形态：

- 没有 `content-length`，或该头不可解析 / 非有限；
- 声明长度可解析且 ≤ 50 MiB，但实际响应体超过（头部偏小或分块传输）。

基线 `:62-65` 只按声明值做前置拒绝，`:67` 随后无上限地吃下整个 body，再在
`:71-73` 按**变换后**长度判定；Rust 在读到 50 MiB + 1 时即停。两者的差异因此
只出现在「实际体 > 50 MiB」这一侧，声明长度是否可解析只决定谁先拒绝。

| 场景 | TS 表现 | Rust 表现 | 用户感知 |
|---|---|---|---|
| 实际体 ≤ 50 MiB，变换后 ≤ 50 MiB | 成功落盘 | 成功落盘 | 无差别 |
| 声明长度 > 50 MiB | 读 body 前拒绝，错误串带声明值 | 同左 | 无差别 |
| 实际体 > 50 MiB，且变换后明文 > 50 MiB | 先吃下整个 body（内存无上界），执行 transform，再按**变换后**长度拒绝，错误串带**变换后**字节数；transform 自身抛错时报的是解密错误 | 到 50 MiB + 1 即停止并拒绝，错误串固定 `52428801`，**不执行** transform | 都被拒；错误串里的字节数不同，Rust 更快、内存有界 |
| 实际体 > 50 MiB，但变换后明文 ≤ 50 MiB（PKCS#7 padding ≤ 16 字节，或 transform 收缩） | 解密后落在上限内，**成功落盘** | 读流阶段即拒绝 | Rust 丢掉一个基线可接收的附件（仅这一格） |

不改变：`content-length` 检查的判定（含 JS `Number` 的 hex/`Infinity` 语义）、
`response.ok` 检查、重定向策略、60 s 取头期限；声明大小闸（`input.bytes`）与
变换后大小闸的顺序、文案与基线逐字一致。

## 批准记录

未批准，非已接受差异，不增加任何判分豁免。由 #1822 的第二家评审（Codex，
`_tmp/20261107-issue-1822/codex-r1.log` P1-1）指出：读流上限早于解密，可能丢弃
基线可接收的附件；r2（`codex-r2.log` P1-1）补正了上面的范围与表格口径——形如
「声明长度可解析且未超限、实际体超限」的响应也在范围内，且基线失败时带的是
**变换后**长度而不是密文长度。实现方登记，是否接受由人签字。

收敛方向分两半，**不能只做一半**：把读流上限放宽到 `上限 + padding 上界`
（微信媒体 ≤ 16 字节）只消除「丢附件」那一格；「实际体超限时的错误串」（基线报
变换后字节数、Rust 报 `52428801`）要另做——要么同样吃满再判定，要么同步更正
`A8.3-CH-WEIXIN-MEDIA-CAP-001` 的记账口径（口径更正见
`A8.3-CH-WEIXIN-MEDIA-CAP-001-R1.md`）。
