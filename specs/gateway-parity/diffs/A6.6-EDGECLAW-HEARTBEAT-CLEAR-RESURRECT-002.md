## 类别

bug 修复（有意偏离 TS 基线）。`A6.6-EDGECLAW-HEARTBEAT-CLEAR-RESURRECT-001` 修复了
classify/createNote await 窗口内的「文件复活」，但复查只做一次且落在 await 之后，且依赖
SQLite 可读。#917 fix-r1（评审修复轮）补齐三个残留面：① `selectIndexProject` await 窗口
与同一轮后续候选（第二轮复查之前）仍会复活；② `clearSession` 后紧跟 `close()` 时 L0 查
询报 `database is not open`，按 -001 的 fail-open 臂被当作「未清除」，已清候选照样写盘；
③ 非 `Closed` 的 L0 读错误也被 fail-open 吞掉。三者都与 `clearSession` 自身语义相悖
（intent ②）并构成隐私偏离（intent ③）。fix-r2（第 2 轮评审修复，评审 P1-1）再补清除代次
的语义面：标记从「清除已开始」改为「清除已完成」（bump 挪到 L0 行删除成功之后），使
失败清除不再静默丢 turn，也使「heartbeat 基线读到新代次而 L0 行仍在」的窗口从语义上
消失（读到新代次 ⇒ 行已删 ⇒ 该轮 listing 为空）。fix-r3（第 3 轮评审修复，评审 P0/P1/P2/P3）
把清除判别从会话级收窄到 L0 行级：bump 随删除原子地记下被删的行 id 集合，两层复查
（mismatch 臂与锁内复查）都改为查该集合——清除完成后新捕获的 turn 不再被会话级代次
比较静默丢弃（评审 P0 数据丢失面）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/memory/edgeclaw/heartbeat/indexer.rs`：

- `:312-320` 每会话在 `list_unindexed_l0_by_session` 之前读 `session_clear_generation`
  作基线；
- `:329-330` 每会话在 `list_unindexed_l0_by_session` 之前读 `session_clear_generation`
  作基线，随后触发 `HeartbeatStage::BeforeListUnindexed`（`:139`，fix-r3 新增 Rust 专属
  测试缝：基线已读、listing 未做、什么锁都没拿——同线程 `clearSession` 恰在此完成的
  交错由直测锁定，生产不装 hook）；
- `:1167-1169` persist 循环前经 `session_cleared`（`:1712-1736`）复查：代际标记不等于
  基线 → fix-r3（评审 P0）改为查 `session_clear_removed_since`（被删行 id 集合里有没有
  本行）——代次不等只说明「有过一次完成的清除」，不再等价于「本行已清除」；标记等于
  基线时回查 L0 行是否仍在；`Err(StorageError::Closed)` → 未清除（fail open，仅此一臂，
  保住 close 各格字节行为）；其余错误 → 传播（fail closed，诚实报错而不是静默复活）；
- `:1198-1216` 每个候选：`route_general_candidate` 的 select await 在锁外；随后
  `snapshot_operation_scope()`（`storage/snapshots.rs:438`，workspace+global 快照锁，
  `clearSession` 走 `storage/entries.rs:412` 的同一 `snapshot_operation`）拿住后在锁
  内经 `session_clear_removed_since` 复查（fix-r3 起同样按行判别），再
  `BeforePersistCommit`（`:143`，Rust 专属测试缝）→ meta 物化 → `upsert_candidate`，
  段内无 await——复查与写入和 `clearSession` 互斥；
- 标记实现在 `file_memory.rs`（`SessionClears`）：per store 单调计数 + per session 的
  （代次, 被删行 id 集合）记录（fix-r3 评审 P0/P3-1：计数 per `EdgeClawFileStores` 而
  非 per 进程），仅 `clear_session_memory_data` 递增，`clear(current_project)` /
  `clear(all)` 不递增（保住 `matrix-general-select-clearProject` 金格逐字节一致），
  `close()` 后仍可读。fix-r2（评审 P1-1）：bump 挪到 `DELETE FROM l0_sessions` 成功
  之后（`entries.rs:479-492`，仍在同一 `snapshot_operation` 内），代次由此表示「该
  会话的清除已完成」——清除在任何一步失败都不递增、不改变代次，也不丢任何 L0 行，
  在飞 heartbeat 照常 persist，L0 行只在 persist 真正写出后随成功路径标已索引，不再
  出现「候选被丢弃、行却被标已索引」的静默丢 turn；fix-r3（评审 P0）：bump 携带在
  DELETE 前同一临界区内 SELECT 出的被删行 id（`entries.rs:479-488`），复查只拦截这些
  行——清除完成后新捕获的 turn 得以 persist（与 TS 下一轮写入一致）；`entries.rs`
  的 `ClearSessionStage` 两个阶段是 fix-r2/r3 的 Rust 专属测试缝（生产不装 hook）：
  `BeforeRemoveData`（`:444-447`，fix-r2，在旧 bump 位置触发：hook 报错即「清除中途
  失败」、阻塞即「清除停在临界区内」）、`BeforeDeleteL0`（`:463-478`，fix-r3 评审 P2，
  在「文件已删、L0 行未删」的半清除位置触发）；两处 hook 都先 clone 出槽再调用
  （fix-r3 评审 P3-3），hook 重入 `set_clear_session_hook` 不再自死锁。
