## 类别

bug 修复（有意偏离 TS 基线）。`A6.6-EDGECLAW-HEARTBEAT-CLEAR-RESURRECT-001` 修复了
classify/createNote await 窗口内的「文件复活」，但复查只做一次且落在 await 之后，且依赖
SQLite 可读。#917 fix-r1（评审修复轮）补齐三个残留面：① `selectIndexProject` await 窗口
与同一轮后续候选（第二轮复查之前）仍会复活；② `clearSession` 后紧跟 `close()` 时 L0 查
询报 `database is not open`，按 -001 的 fail-open 臂被当作「未清除」，已清候选照样写盘；
③ 非 `Closed` 的 L0 读错误也被 fail-open 吞掉。三者都与 `clearSession` 自身语义相悖
（intent ②）并构成隐私偏离（intent ③）。fix-r2（第 2 轮评审修复，评审 P1-1）再补清除代次
的语义面：标记从「清除已开始」改为「清除已完成」（bump 挪到 L0 行删除成功之后），使
失败清除不再静默丢 turn，也使「heartbeat 基线读到新代次而 L0 行仍在」的窗口从语义上
消失（读到新代次 ⇒ 行已删 ⇒ 该轮 listing 为空）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/memory/edgeclaw/heartbeat/indexer.rs`：

- `:312-320` 每会话在 `list_unindexed_l0_by_session` 之前读 `session_clear_generation`
  作基线；
- `:1138-1153` persist 循环前经 `session_cleared`（`:1689-1710`）复查：代际标记不等于
  基线 → 已清除；否则回查 L0 行是否仍在；`Err(StorageError::Closed)` → 未清除（fail
  open，仅此一臂，保住 close 各格字节行为）；其余错误 → 传播（fail closed，诚实报错而
  不是静默复活）；
- `:1167-1197` 每个候选：`route_general_candidate` 的 select await 在锁外；随后
  `snapshot_operation_scope()`（`storage/snapshots.rs:438`，workspace+global 快照锁，
  `clearSession` 走 `storage/entries.rs:412` 的同一 `snapshot_operation`）拿住后先在锁
  内复查代际标记，再 `BeforePersistCommit`（`:143`，Rust 专属测试缝）→ meta 物化 →
  `upsert_candidate`，段内无 await——复查与写入和 `clearSession` 互斥；
- 标记实现在 `file_memory.rs:403-445,577`：进程内单调计数 per session，仅
  `clear_session_memory_data` 递增，`clear(current_project)` / `clear(all)` 不递增（保住
  `matrix-general-select-clearProject` 金格逐字节一致），`close()` 后仍可读。fix-r2
  （评审 P1-1）：bump 挪到 `DELETE FROM l0_sessions` 成功之后（`entries.rs:453-464`，
  仍在同一 `snapshot_operation` 内），代次由此表示「该会话的清除已完成」——清除在
  任何一步失败（含 `conn()` 即失败的 `Closed`，不产生任何副作用）都不递增，在飞
  heartbeat 照常 persist，L0 行只在 persist 真正写出后随成功路径标已索引，不再出现
  「候选被丢弃、行却被标已索引」的静默丢 turn；`entries.rs:418-431` 是 fix-r2 的
  Rust 专属测试缝（`ClearSessionStage::BeforeRemoveData`，生产不装 hook），在旧 bump
  位置触发：hook 报错即「清除中途失败」、阻塞即「清除停在临界区内」。

  / `clear(all)` 见「已知边界」）。fix-r2（评审 P1-1）补登记失败清除面：清除中途失败
  （storage 报错、SQLite 仍开）时代次不递增，在飞 heartbeat 照常 persist——与 TS 一致

  顺序曾使 Rust 在此交错静默丢 turn、偏离 TS；未另做 TS gate 探针，Rust 侧行为由直测
  `failed_clear_midway_keeps_the_turn_persistable` 锁定）。

  SQLite 时也被丢弃，随后在同一批 close 失败点拒绝（`database is not open`）——复活差异
  在此登记。fix-r2 后代次只在删除完成后递增，「heartbeat 基线读到新代次而 L0 行仍在」
  的窗口从语义上消失（读到新代次 ⇒ 行已删 ⇒ 该轮 listing 为空、整轮跳过），不再依赖
  `getProjectMeta` 恰好持快照锁这一偶然阻断（直测
  `clear_parked_mid_scope_does_not_resurrect_turn_started_inside_window`）。
- 非 `Closed` L0 读错误：Rust fail-closed（会话失败 + warn 带原始错误，不写文件）；无 TS
  金样，本条即登记依据。fix-r2（评审 opus P2）补登记：该 pre-loop 复查无条件执行，
  即使本轮无候选（`created_candidates` 为空，无写盘可保护）也会回查 L0，非 `Closed`
  读错误照旧 fail-closed 使会话失败——表被 DROP 时后续 `markL0Indexed` 也会以同一错误
  失败，最终状态一致；TS persist 路径不做该读，无 TS 字节行为可保。
- 提交段与 `clearSession` 的互斥是 Rust 侧并发缝（TS 事件循环内 clearSession 为同步
  SQLite 调用，无同形并发观测格）。
- 已知边界（无金样，未另登记，前置于后续 clear 语义单）：`clear(current_project)` /
  `clear(all)` 落在 classify/createNote await 窗口内时同样删除全部 `l0_sessions` 行
  （`entries.rs:369`），-001 起的 L0 空复查即判「已清除」并丢弃，而 TS 会写盘；现有金格
  `matrix-general-select-clearProject` 的清除落在该复查之后，故不受影响、仍逐字节一致。
  该时机无金样覆盖，后续单需补 clearProject/clearAll 的 classify/createNote 金格或独立
  差异条目，不得以本条 6 格冒充全覆盖。
- 不改变 capture、去重、路由决策、trace 其余结构与 stats 聚合语义。
