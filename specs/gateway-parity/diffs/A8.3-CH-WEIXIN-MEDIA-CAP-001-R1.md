## 类别

更正（范围句与表格漏了一种响应形态，差异本身不变）：原条目「范围」节把受影响集合
写成「响应没有 `content-length`（或该头不可解析/非有限），且实际正文 > 50 MiB」，
但基线只在声明值**有限且大于上限**时于读 body 之前拒绝；声明值可解析且 ≤ 上限
（含 `0`、含被分块传输推翻的偏小值）时，基线照样把整个 body 吃进内存再判定，因此
「声明长度偏小或不超限、实际正文超限」同样落在读流上限的影响面内。原条目
`A8.3-CH-WEIXIN-MEDIA-CAP-001` 原字节不动，本条只更正口径：判定规则、Rust 实现、
金样与负控均不变，也不新增任何判分豁免。

## 基线依据

固定基线 `cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85`，Node v22.22.0。
`src/adapters/channel/protocol/ImAttachmentStore.ts:62-73`（与原条目同一处）：

1. `:62-65` 读 `content-length` → `Number(...)`；只有 `Number.isFinite(n) && n > maxBytes`
   才在**读 body 前**抛 `Attachment is <n> bytes (limit <max>).`；
2. `:67` `Buffer.from(await response.arrayBuffer())`——此前置拒绝不成立时**无读流上限**；
3. `:71-73` 读完再比 `buffer.byteLength > maxBytes`。

即前置拒绝的**唯一**条件是「有限且 > 上限」；`content-length` 缺失、不可解析、
非有限，以及可解析但 ≤ 上限，四种都走第 2 步。原条目的「没有 / 不可解析 / 非有限」
把第四种漏在范围之外。

## Rust 行为

不变，与原条目登记一致：`src/pilotdeck-gateway/src/channel/weixin/media.rs` 的
`WeixinCdnClient::download` 用共享 `crate::fetch_redirect::read_body` 逐帧读，
累计越过 50 MiB 即停，映射为 `Attachment is 52428801 bytes (limit 52428800).`；
声明长度检查（`finite_js_number` + `> limit`）与基线第 1 条同序同文案，先于读 body。

## 范围

受影响集合更正为：**实际正文 > 50 MiB，且响应头没有给出一个有限且 > 上限的声明长度**
（也就是基线不会在读 body 之前就拒绝的那些响应）。两种形态：

- 没有 `content-length`，或该头不可解析 / 非有限；
- 声明长度可解析且 ≤ 50 MiB，实际正文超过（头部偏小或分块传输推翻声明值）。

| 场景 | TS 表现 | Rust 表现 | 用户感知 |
|---|---|---|---|
| 声明长度有限且 > 50 MiB | 读 body 前拒绝，错误串带声明的精确值 | 同左 | 无差别 |
| 声明长度缺失 / 不可解析 / 非有限，正文 ≤ 50 MiB | 成功 | 成功 | 无差别 |
| 声明长度可解析且 ≤ 50 MiB，正文 ≤ 50 MiB | 成功 | 成功 | 无差别 |
| 声明长度缺失 / 不可解析 / 非有限，正文 > 50 MiB | 先吃下整个 body（内存无上界），再拒绝，错误串带真实字节数 | 到 50 MiB + 1 字节即停止并拒绝，错误串固定 `52428801` | 都被拒；Rust 更快、内存有界，错误串里的字节数是下界而不是真实值 |
| 声明长度可解析且 ≤ 50 MiB，实际正文 > 50 MiB | 同上（声明值不触发前置拒绝） | 同上 | 同上 |

不改变：声明长度检查的判定（含 JS `Number` 的 hex / `Infinity` 语义）、
`response.ok` 检查、重定向策略、60 s 取头期限与正文的 undici 默认 `bodyTimeout`。
配套后果（读流上限早于微信媒体解密，密文比明文多出的 PKCS#7 padding 会落进上限）
由 `A8.3-CH-WEIXIN-ATTACH-001` 登记，两条合起来才是完整口径。
