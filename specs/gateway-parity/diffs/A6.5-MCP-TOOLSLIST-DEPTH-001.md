## 类别

不可避免（向严）。MCP `tools/list` 结果里带 `outputSchema` 的工具，由端口的固定结构深度上限 256
提前拒绝，早于基线 Ajv 在 V8 上的栈断点；后果是**整张工具列表被拒**，而不只是某个工具不可用。

本条只登记 #1754 的差异二。原正文的差异一「nameless 工具不校验」已被 2026-11-06T03:01:44Z 的
更正与两家非作者评审（anthropic + minimax）独立推翻并作废：`wire.rs` 在迭代工具之前就
`parse_result(ResultSchema::ListTools, …)`，缺 `name` 在结果形状层同样被拒，`client.rs` 的
`let Some(name) = … else { continue }` 对「缺 name」不可达。TS 金样
`_tmp/20261106-issue-401/probe/probe-nameless.{mts,out}`（Node v22.22.0）与端口用例
`list_tools_rejects_a_tool_without_a_name` 逐字节相同，无差异可登记（该用例目前只在 PR #1782
分支，未合入 main）。因此本条不含 nameless 的任何主张。

## 基线依据

固定基线 `resources/PilotDeck`（cc7c4e65，Node v22.22.0，`@modelcontextprotocol/sdk` 1.29.0）。

调用链：`src/mcp/client/McpClient.ts:221` `listTools()` → SDK `client.listTools()`；
SDK `dist/esm/client/index.js:568` 在返回前 `this.cacheToolMetadata(result.tools)`，
`:539-546` 对每个带 `outputSchema` 的工具调 `_jsonSchemaValidator.getValidator(tool.outputSchema)`
现场编译 Ajv 校验器；深度过大时抛 `RangeError: Maximum call stack size exceeded`，
被 `callWithReconnect` 包成 `mcp_call_failed` /
`MCP call failed (server=mock): Maximum call stack size exceeded`。

实测（探针 `_tmp/20261106-1751-1754-diff/probe-ts-depth-single.mts`：每次只跑一个深度、独立冷进程、
3 次重复；原始输出 `_tmp/20261106-1751-1754-diff/ts-probe-depth-cold-3runs.out`）：

- 深度 255 / 256 / 257 → `ok(1)` 各 3/3（`ts-probe-depth-cold-256.out`）；
- 深度 300 → `ok(1)` 3/3；
- 深度 350 / 380 / 399 / 400 / 410 / 450 → `err(mcp_call_failed) … Maximum call stack size exceeded` 3/3。

同一探针把多档深度串在同一个进程里跑时接受上限会上移（`ts-probe-depth-boundary.out` 与
`ts-probe-depth-wide-3runs.out` 里 257 至 400 均为 `ok(1)`），说明接受上限随 V8 JIT/调用栈状态漂移，
与既有 `A6.5-MCP-OUTSCHEMA-DEPTH-001` 记录的同因一致。可稳定复现的接受区间至少是 **255–300**；
即**深度 256 是冷进程实测的确定分界**：基线接受 3/3，端口拒绝。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/mcp/output_schema.rs:83`
`const MAX_SCHEMA_DEPTH: usize = 256;`；`:448` `if self.depth >= MAX_SCHEMA_DEPTH` 时返回
`SchemaError("schema nesting is deeper than this port supports (256)")`。

`src/pilotdeck-gateway/src/runtime/mcp/client.rs:401` `list_tools` 在 `:430` 对每个工具的
`outputSchema` 调 `check_schema`，任一失败即
`return Err(McpClientError::client(CallFailed, "MCP call failed (server=…): …"))`：整张列表不返回、
一个工具也不缓存，连接状态仍为 `ready`。

实测（端到端探针 `probe_1754_tools_list_depth_rejects_whole_list`，临时加在
`tests/mcp_client.rs` 尾部、不提交，源码见 `_tmp/20261106-1751-1754-diff/rust-probe.patch`；
命令 `cargo test --offline -p pilotdeck-gateway --test mcp_client probe_1754 -- --nocapture --test-threads=1`；
原始输出 `_tmp/20261106-1751-1754-diff/rust-probe.log`）：

```text
PROBE depth=255 -> ok(2) status=ready
PROBE depth=256 -> err(code=Some("mcp_call_failed")) MCP call failed (server=mock): schema nesting is deeper than this port supports (256) status=ready
PROBE depth=257 -> err(code=Some("mcp_call_failed")) MCP call failed (server=mock): schema nesting is deeper than this port supports (256) status=ready
PROBE depth=300 -> err(code=Some("mcp_call_failed")) MCP call failed (server=mock): schema nesting is deeper than this port supports (256) status=ready
PROBE depth=399 -> err(code=Some("mcp_call_failed")) MCP call failed (server=mock): schema nesting is deeper than this port supports (256) status=ready
PROBE depth=400 -> err(code=Some("mcp_call_failed")) MCP call failed (server=mock): schema nesting is deeper than this port supports (256) status=ready
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 19 filtered out; finished in 10.55s
```

即端口的**实际拒绝起点是深度 256**（`depth >= MAX_SCHEMA_DEPTH`，根算 0），不是 257；
拒绝后 `status` 仍是 `ready`。探针在 `tools/list` 里放两个工具（`good` + `deep`），故成功档是
`ok(2)`；TS 探针只放一个工具，故为 `ok(1)`，两者深度构造逐字相同（`depth` 层
`{type:"object",properties:{x:…}}` 包住 `{type:"string"}`），可直接比。

## 范围

仅 MCP `tools/list` 结果中带 `outputSchema` 的工具。向严区间为「**256 ≤ 深度 ≤ 基线实测接受上限**」：
该区间内基线把工具列出来并可调用（冷进程实测 256 / 257 / 300 各 3/3 `ok(1)`），端口整单拒绝，
该 MCP server 的**所有**工具都不可见（不只深度超限的那一个）。深度 ≤ 255 两侧一致（都接受）。

超过基线接受上限后两侧**仍不同因、不同文案**：基线是 V8 栈溢出
`mcp_call_failed … Maximum call stack size exceeded`，端口是自己的固定上限
`mcp_call_failed … schema nesting is deeper than this port supports (256)`。两侧都拒绝、
都不崩，故这一侧不构成行为差异，只是错误文案不同。

本条与既有 `A6.5-MCP-OUTSCHEMA-DEPTH-001` 不重叠：那条讲的是 `callTool` 阶段 outputSchema
校验的 2048 单位预算（单次校验结果差异，且其「范围」明写「仅 outputSchema 校验」、不覆盖列单路径）；
本条发生在**列单编译阶段**，后果是整服务器工具丢失，属独立差异，不沿用其范围与豁免。

不含：`inputSchema`（端口不校验）、`callTool` 的 structuredContent 校验、深度超过基线断点后
两侧都拒绝的区（行为一致、只有错误文案不同），以及 nameless 工具（见「类别」，已作废）。
