## 类别

更正（失败形态更正，差异本身仍成立）：原条目「类别」判定的数据缺口不变——
无时区后缀的 `runAt` 按进程 TZ 解析，Rust 读宿主 zoneinfo 树、TS 用 Node 自带
ICU-local，进程 TZ 在宿主不可解析时 Rust 构造失败；在「不内嵌 tzdata 规则」
约束下不可消除，仍是**不可避免**。被更正的是原条目「范围」段的失败形态：
「接线后表现为该任务不被调度，不是错误」与 #1325 已落地的实现相反——
`createTask` / `updateTask` 在 `computeNextRunAt` 返回 `undefined` 时**抛错
拒绝创建**，create/update 面不产生任何「不排期的任务」（启动恢复路径有，
且只对 cron / delay 形状成立，见「范围」）。据此，原条目「类别」段那句
「失败时 fail-closed 返回 `undefined` **而不是抛错**」也须限定：它只描述
`computeNextRunAt` 这一个计算层；create/update 面把这个 `undefined` 立刻
转抛同一句错。经人批（#1644 选项 ②）本更正件登记该真实形状；原条目字节
不动、不回写。

## 基线依据

同原条目固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85、Node v22.22.0 /
ICU 78.2。本次按两个来源分别复算：

1. **`runAt` 串不可解析源**：TS 侧 `computeNextRunAt` 的 once 臂是
   `new Date(runAt)`；串本身非法 → Invalid Date → `undefined` → createTask
   抛错。该形状与金样 `src/pilotdeck-gateway/tests/fixtures/native-cron/oracle.json`
   的 `create-errors` 共用同一条错误出口（第 8 步，`Error: Cron schedule does
   not produce a valid future run time.`，由 `generate.mts` 对基线 cc7c4e6 真实
   TS 源码跑出）。
2. **宿主缺 tzdata 源**：本机（macOS）实测原件 `_tmp/20261106-1767-cron-diff-r1/ts-probe.mjs`。
   两轮环境：
   a) 受限 `TZDIR`：`env -i TZ=US/Pacific TZDIR=<受限树>`（该树只有 `UTC` /
   `Asia/Tokyo`，`US/Pacific` MISSING）下跑 Node v22.22.0 / full-icu：
   `wall:2026-03-05T09:30:00 {"time":1772731800000,"iso":"2026-03-05T17:30:00.000Z"}`
   ——09:30 本地墙钟（PST, UTC-8）正常解析成 17:30Z。换
   `TZDIR=/usr/share/zoneinfo` 重跑，除 `TZDIR` 字段外逐行相同
   （`ts-probe-v2-restricted.log` 与 `ts-probe-v2-system.log`；
   `icu` 行打印 `icu_small=false (full-icu)`，`typeof process.config.variables.icu_small`
   实测为 `boolean`，v1 那行只是没加标注，数据行两轮一致）。
   b) **直接掐断宿主树**（这才是「不读宿主 zoneinfo」的正证）：本机树是
   `/usr/share/zoneinfo -> /var/db/timezone/zoneinfo -> /var/db/timezone/tz/2026e.1.0/zoneinfo`，
   `/var -> private/var`，另有 `/usr/share/zoneinfo.default`；`sandbox-exec`
   profile 覆盖四条字面路径，五次 `cat`（含未列入 deny 的 `/etc/localtime`）
   全部 rc=1（逐条见 `_tmp/20261106-1767-cron-diff-r1/sandbox-negctl-r4.log`）。
   「符号链接会不会绕过」另用隔离负控钉死：只 deny `/private/var/db/timezone`，
   先打 profile 头，再跑一条允许读正控 `/etc/hosts`（rc=0，证明 profile 没有整体
   拒读）与四条测试路径——`/private/var/db/timezone/zoneinfo/UTC`（在 deny 内，
   rc=1，证明规则生效）、`/var/db/…`、`/usr/share/zoneinfo/…`、`/etc/localtime`
   （字面路径都不在 deny 内，也全部 rc=1）；四条 denial 的 stderr 均为
   `Operation not permitted`（与 ENOENT 区分开），逐条原始输出在
   `_tmp/20261106-1767-cron-diff-r1/sandbox-resolve-semantics-v2.log`，即匹配按
   解析后的真实路径、链接绕过不成立。同一 profile 下跑同一探针 rc=0：`zone:US/Pacific` /
   `Asia/Calcutta` / `Europe/Kiev` 全部 `ok:true`，`wall:2026-03-05T09:30:00`
   仍是 `2026-03-05T17:30:00.000Z`（`ts-probe-v4-zoneinfo-denied.log`）。即 TS
   的 cron 时区计算走 Node 自带 ICU，**不需要宿主 zoneinfo 树上的任何文件**。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/cron/schedule.rs:149-156`
`once_computed_run_at` 把 `parse_node22_date_with_local` 的
`Ok(None) | Err(_)` 一并折成 `ComputedRunAt::Undefined`
（`resolve_local` 在 `src/pilotdeck-transport/src/system_clock.rs:123`，经
`/usr/share/zoneinfo` 读进程 TZ 的 TZif）；随后
`src/pilotdeck-gateway/src/runtime/cron/manager.rs:877-881`（`create_task`）与
`:1008-1012`（`update_task`）把 `undefined` 转成
`CronError::error("Cron schedule does not produce a valid future run time.")`，
在各自写库之前返回（create 的 `self.store.put_task` 在 `manager.rs:928`，
update 的 `self.store.update_task` 在 `:1033`），两条路径都不落盘、不留半成品
任务。与 TS 的分歧只在「宿主缺 tzdata」源：TS 解析成功照常建任务，Rust 抛这
同一句错。

## 范围

更正原条目「范围」段这一段（逐字引用）：

> 差异表现：进程 TZ 在宿主上
> 不可解析时，once 任务的 `computeNextRunAt` 返回 `undefined`（TS 算出日期）；
> 接线后表现为该任务不被调度，不是错误、不静默换时区。接线前置约束（#1325，
> 与 A8.3-CRON-TZ-ALIAS-001 同一条）：`ComputedRunAt::Undefined` 同时承载
> 「`runAt` 串不可解析 / 366 天内永不匹配 / 宿主缺 tzdata」三种来源，调用方
> 不得把它当作「无后续运行」落盘终止任务，否则换宿主装上 tzdata 后任务不会
> 恢复。

新措辞：**「接线后表现为该任务不被调度，不是错误」在 create/update 面上是
错的。** 六方法（create/list/update/delete/stop/runTaskNow）中直接消费
`computeNextRunAt` 的是 `create_task`（`manager.rs:877`）与 `update_task`
（`:1008`）：它们在该函数返回 `undefined` 时一律抛 `Cron schedule does not
produce a valid future run time.` 并拒绝创建 / 更新，什么都不落盘——**是
错误**。`list` / `delete` / `stop` 不经过该计算；`run_task_now` 经内部
`create_task`（`manager.rs:1234`）**间接**经过同一计算，但它合成的 `runAt`
是 `real_now_iso()` 的 `Z` 后缀 UTC 串（`manager.rs:1213-1215`），不带无后缀
本地墙钟，不查进程 TZ、也不会折成 `undefined`，故本条差异不经它触发（若日后
改成无后缀本地墙钟就会触发）。

原条目那条「调用方不得把它当作无后续运行落盘终止任务」的前置约束**不作废，
而是收窄到启动恢复路径，且只对 cron / delay 形状成立**：
`recover_interrupted_runs`（`manager.rs:1462-1609`）只筛 `status == "running"`
的被打断任务（`:1478-1484`），**once 形状在进入该计算之前就被直接删除并
`continue`**（`:1537-1552`），所以 once 任务不会在恢复面留下「在库、scheduled、
无 `nextRunAt`」的形态；该形态只对 cron / delay 形状存在，但两者来源不同：
cron 形状来自 `computed_next_run_at` 返回 `None`（宿主缺 tzdata）；delay 形状有
两类来源、**都与 tzdata 无关**——(i) 存量 `amount` 非有限或 ≤ 0
（`task_schedule_shape` 的 `:1829-1835` 直接折成 `runAt: undefined`）；(ii)
`amount` 合法但 `now + delay` 超出 TimeClip：`delay_run_at_iso`（`:1655-1665`）
以 `raw as i64` 饱和转型（`|raw|` 超出 `i64` 范围才饱和；下溢到 `i64::MIN`
只有注入的超范围时钟可达，即 A6.4 那一支）产出
`format_epoch_iso` 串，该串**重新解析不构成合法日期**——6 位扩展年
（275760–999999）被 `src/pilotdeck-transport/src/system_clock.rs:116-118` 的
`±TIME_CLIP` 包含检查折成 `None`，7 位及以上年（含饱和值约
`+292,278,994`）连 ISO 固定宽度解析都过不去（`parse_iso` 的 `fixed(6)`，
`:775-790`）——于是 `compute_once` 折 `Undefined`、恢复面得 `None`
（`:99-101` 的 ±1e6 年检查在这条路径上不可达）。这条路径与
`A6.4-CLOCK-TIMECLIP-001` 的饱和转型同族；该条目的登记范围与批准状态见其原
条目（`specs/gateway-parity/accepted-diffs.md:296-303`）与本目录 2026-10-23
#505 人批记录（同文件 `:659-670`），本条不复述；用户 delay 超 TimeClip 时 TS
侧的出口未实测，若构成差异需单独登记，已作为跟进写进 #1645（前置于 #1326
接线）。只有 `amount` 合法且 `now + delay` 落在 TimeClip 内，才会重算成
`Z` 后缀串、必有 `nextRunAt`（`:1837-1841`）。两者的 `None` 分支
（`:1575-1600`）都按 TS 镜像（`CronRuntime.ts` 的
`nextRunAt: computeNextRunAt(...)?.toISOString()`）落盘 `status: "scheduled"`
+ `nextRunAt: undefined`（序列化丢键，`store.rs:520-522` 的 `string_or_drop`），
不报错。「装回 tzdata 也不会自动恢复」只描述 cron 形状；故该约束对恢复路径的
cron 分支与 #1326 的未来调用方**仍然必要**（once 分支无需该约束，任务已删除；
delay 分支的恢复条件是修好存量 schedule，与本条差异无关）。

三源折叠（`runAt` 串不可解析 / 366 天内永不匹配 / 宿主缺 tzdata）仍成立：
create/update 面统一报同一句错；恢复面对 cron 形状（tzdata 源）与 delay 形状
（存量 `amount` 非法 / `now + delay` 超 TimeClip 两源）折成无 `nextRunAt` 的
scheduled 任务（once 形状在恢复时被删除，见上）。

用户可见面（接线 #1326 后）：进程 TZ 在宿主不可解析、`runAt` 又是无后缀本地
墙钟串时，用户**建不出 once 任务**，看到同一句「schedule 不产生有效运行时
间」；同一台机器装上 tzdata-legacy（或 macOS + 常见 TZ）即与 TS 一致。带
时区后缀（`Z` / `±HH:MM`）与**严格** date-only 串（`1970-01-01`，两侧无空白）
不受本条影响，固定按 UTC，不查进程 TZ，与 TS 逐格一致（transport 测试
`iso_date_only_defaults_to_utc_but_date_time_defaults_local` 钉死）。
**但被空白包裹的 date-only 串（`"1970-01-01 "` / `" 1970-01-01"`）落在本条
范围内**：实测（原件 `_tmp/20261106-1767-cron-diff-r1/ts-probe-whitespace.mjs`，
原始输出 `ts-probe-whitespace.log`，首行记录 `node v22.22.0 icu_small false
TZ US/Pacific TZDIR null`）：
`"1970-01-01 "` 得 `28800000` / `1970-01-01T08:00:00.000Z`，
即走无后缀本地墙钟路径、按进程 TZ 解析；Rust 侧同一分流由 transport 测试
`iso_date_only_defaults_to_utc_but_date_time_defaults_local` 的两个空白变体
断言（`src/pilotdeck-transport/tests/system_clock.rs:228-229`），但该测试的
夹具是 **Asia/Shanghai (+08:00)** 注入闭包（`:16-18
shanghai = |wall| Ok(wall - 28_800_000)`，头注 `:2-3`），断言值 `-28_800_000`
是 **UTC+8** 下 1970-01-01T00:00 的 epoch，与上引 UTC-8 探针数值异号；
**同值对账要用同 TZ 的格**：`tests/fixtures/node22-date-parse.json` 的
America/Los_Angeles 组 `" 2024-01-02 "` → `1704182400000` /
`2024-01-02T08:00:00.000Z`（UTC-8 本地午夜，`:621-624`），Shanghai 组同输入 →
`1704124800000`（`:382-385`）；两格都由
`slim2_actual_node22_fixture_preserves_valid_legacy_and_invalid_dates` 断言
相等，但回放方式不同——LA 格走合成 TZif
（`resolve_tzif_local(wall, &la)`，`:51-58`），Shanghai 格走固定 `+08:00`
闭包（`Ok(wall - 28_800_000)`），该测试头注（`:2-3`）明说不主张任意系统 / ICU
tzdata 等价。
故两侧一致的是**分流**（都走无后缀本地墙钟路径、都按进程 TZ）；只是
Shanghai 夹具与 US/Pacific 探针不可直接互为对账。
该格在缺 tzdata 宿主上会与本条其余无后缀串同样 fail-closed 抛错。

## 机器判据

Rust 侧真实运行（本树 HEAD，`CARGO_TARGET_DIR` 独立）：

```sh

  -p pilotdeck-transport --test system_clock -- --test-threads=4
# test iso_date_only_defaults_to_utc_but_date_time_defaults_local ... ok
# test valid_local_profile_errors_propagate_instead_of_disabling_deadlines ... ok
# test result: ok. 40 passed; 0 failed; …（原始输出 _tmp/20261106-1767-cron-diff-r1/rust-transport-system-clock.log）
```

**取证边界（如实写）**：上面两条 transport 测试都通过 `parse_with` **注入**
固定的 local 闭包（`shanghai` = `|wall| Ok(wall - 28_800_000)`；错误侧注入
`Err("local-profile-gap")`），钉死的是「无后缀串走 local 闭包、date-only 串不走」
这一层分流，**没有**驱动生产 `resolve_local`（`system_clock.rs:123`）去读宿主
TZif。生产侧「宿主树缺该 zone → 构造失败」通路由同一 `timezone_tzif` 的
`resolver_rejects_zones_the_host_tree_lacks`（`ZonedPartsResolver::new("Not/AZone")`
等返回 `Err`）间接覆盖；cron 调度层再用 `once_local_wall_unresolvable_fails_closed`
注入恒 `Err` 的解析器钉死 `schedule.rs:149-156` 的 fail-closed 分支（不依赖本机
缺 zone 文件）。真正「在生产 `resolve_local` 上跑一个宿主树没有的进程 TZ」的
端到端实测需要缺 tzdata 的宿主，本机（macOS 含 backward 链接）做不到，记为本
更正件未覆盖项、留给宿主验收。

`once_local_wall_unresolvable_fails_closed` 注入恒 `Err` 的 local 解析器，钉死
`schedule.rs:149-156` 的 fail-closed 分支（不依赖本机缺 zone 文件）；
`six_methods_replay_the_ts_gold` 把 `manager.rs:877-881` 抛错那一路的实际输出
与金样错误**逐字节**比对。`cron-schedule` 侧负控
`once-local-wall-guessed-utc` 不变，把 `Err` 猜成 epoch 0 的变体必须被该测试
按专用消息杀掉。
