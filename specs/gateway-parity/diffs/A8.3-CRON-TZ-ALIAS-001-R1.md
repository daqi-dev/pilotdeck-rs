## 类别

更正（失败形态更正，差异本身仍成立）：原条目「类别」判定的数据缺口不变——ICU
名单内的 101 个 legacy 别名 zone 在拆掉 backward 链接的宿主上系统树没有 TZif
文件，在「不内嵌 tzdata 规则」约束下不可消除，仍是**不可避免**。被更正的是原
条目「范围」段对失败形态的描述：「接线后表现为该任务不被调度，不是错误」与
#1325 已落地的实现相反——`createTask` / `updateTask` 在 `computeNextRunAt`
返回 `undefined` 时**抛错拒绝创建**，create/update 面不产生任何「不排期的
任务」（启动恢复路径有，见「范围」）。原条目「类别」段那句「规则解析失败时
fail-closed 返回 `undefined`」也据此限定：它只描述 `computeNextRunAt` 计算层，
create/update 面会把该 `undefined` 转抛同一句错。经人批（#1644
选项 ②）本更正件登记该真实形状；原条目字节不动、不回写。

## 基线依据

同原条目固定基线 cc7c4e653b15c8b2cec7bcf2d15d41d69396ae85、Node v22.22.0 /
ICU 78.2。本次按两个来源分别复算：

1. **表达式非法源**：TS 自己的行为由金样钉死——
   `src/pilotdeck-gateway/tests/fixtures/native-cron/oracle.json` 的
   `create-errors` 格第 8 步
   `{"method":"createTask","input":{…,"schedule":{"type":"cron","expression":"not a cron"}}}`
   记录 `{"ok":false,"error":{"name":"Error","message":"Cron schedule does not
   produce a valid future run time."}}`。该金样由同目录 `generate.mts` 对基线
   cc7c4e6 的真实 TS 源码跑出（fail-closed esbuild 装载器 + pinned 时钟），
   `sourceCommit` / `sourceSha256` 记在金样内。
2. **宿主缺 tzdata 源**：本机（macOS，系统 `/usr/share/zoneinfo` 含 backward
   链接）实测原件 `_tmp/20261106-1767-cron-diff-r1/ts-probe.mjs`，在受限环境
   `env -i TZ=US/Pacific TZDIR=<受限树>`（该树只有 `UTC` / `Asia/Tokyo`，清单
   见同目录 `restricted-tzdir-files.txt`；`US/Pacific`、`Asia/Calcutta`、
   `Europe/Kiev` 均 MISSING）下跑 Node v22.22.0 / full-icu
   （`icu_small=false (full-icu)`）：`zone:US/Pacific {"ok":true,…hour=01
   minute=30…}`、`zone:Asia/Calcutta {"ok":true,…}`、
   `zone:Europe/Kiev {"ok":true,…}`，名单外 `zone:Mars/Phobos` 抛
   `RangeError: Invalid time zone specified`。换 `TZDIR=/usr/share/zoneinfo`
   重跑，除 `TZDIR` 字段外逐行相同
   （`_tmp/20261106-1767-cron-diff-r1/ts-probe-v2-restricted.log` 与
   `ts-probe-v2-system.log`；`ts-probe-restricted-tz-alias.log` /
   `ts-probe-system-tzdir.log` 是同一探针修正 `icu` 打印前的首轮原件，数据行
   相同）。`TZDIR` 本身不是宿主树的替身，故补**直接掐断宿主树**的正证：本机树是
   `/usr/share/zoneinfo -> /var/db/timezone/zoneinfo -> /var/db/timezone/tz/2026e.1.0/zoneinfo`，
   `/var -> private/var`，另有 `/usr/share/zoneinfo.default`；`sandbox-exec` 对
   四条字面路径全部 `deny file-read*`，五个负控 `cat` 各得
   `Operation not permitted`（rc=1 逐条记在 `sandbox-negctl-r4.log`）；第五条
   `/etc/localtime` 未列入 deny 却也 rc=1——它指向被拒的 `/var/db/timezone/tz/…`，
   说明 `subpath` 按解析后的真实路径匹配，符号链接绕过不成立。同一 profile 下
   同一探针 rc=0，`US/Pacific` / `Asia/Calcutta` / `Europe/Kiev` 全部 `ok:true`
   （`ts-probe-v4-zoneinfo-denied.log`）。即 TS 的 cron 时区计算走 Node 自带
   ICU，**不需要宿主 zoneinfo 树上的任何文件**，受限树里没有别名文件也算得出
   日期。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/cron/schedule.rs:161-172`
`compute_next_cron_run_at` 在名单有效但 `ZonedPartsResolver::new(timezone)`
构造失败（系统树找不到该 zone 的 TZif）时经 `compute_next_resolved` 返回
`Ok(None)`；`src/pilotdeck-gateway/src/runtime/cron/manager.rs:877-881`
（`create_task`）与 `:1008-1012`（`update_task`）把这个 `None` 直接转成
`CronError::error("Cron schedule does not produce a valid future run time.")`。
两处都在各自写库之前返回（create 的 `store.put_task` 在 `manager.rs:928`，
update 的 `store.update_task` 在 `:1033`），所以失败时不落盘、不留任何半成品
任务；这与 TS 在「表达式非法」源上的形状逐字节相同（同一个 `name: "Error"`
与同一句 message，见金样第 8 步）。与 TS 的分歧只在「宿主缺 tzdata」源：TS
算出日期照常建任务，Rust 抛这同一句错。

## 范围

更正原条目「范围」段这一段（逐字引用）：

> 差异表现：legacy 别名
> zone 的 cron 任务在缺 backward 链接的 Linux 宿主上 `computeNextRunAt` 返回
> `undefined`（TS 算出日期）；接线后表现为该任务不被调度，不是错误、不静默
> 换时区。接线前置约束（#1325）：`ComputedRunAt::Undefined` 同时承载「表达式
> 非法 / 366 天内永不匹配 / 宿主缺 tzdata」三种来源，调用方不得把它当作
> 「无后续运行」落盘终止任务，否则换宿主装上 tzdata 后任务不会恢复。

新措辞：**「接线后表现为该任务不被调度，不是错误」在 create/update 面上是
错的。** 直接调用 `computed_next_run_at` 的六方法面是 `create_task`
（`manager.rs:877`）与 `update_task`（`:1008`）：它们在该函数返回 `undefined`
时一律抛 `Cron schedule does not produce a valid future run time.` 并拒绝创建 /
更新，什么都不落盘——**是错误**。`list` / `delete` / `stop` 不经过该计算；
`run_task_now` 经内部 `create_task`（`manager.rs:1234`）**间接**经过同一计算，
但它合成的 `runAt` 是 `real_now_iso()` 的 `Z` 后缀 UTC 串（`manager.rs:1213-1215`），
不查进程 TZ、也不会因宿主缺 tzdata 折成 `undefined`，故本条差异不经它触发
（若日后改成无后缀本地墙钟，就会触发）。

原条目那条「调用方不得把它当作无后续运行落盘终止任务」的前置约束**不作废，
而是收窄到启动恢复路径**：`recover_interrupted_runs`（`manager.rs:1462-1609`）
对 `computed_next_run_at`（`:1575`）返回 `None` 的任务按 TS 镜像
（`CronRuntime.ts` 的 `nextRunAt: computeNextRunAt(...)?.toISOString()`）落盘
`status: "scheduled"` + `nextRunAt: undefined`（序列化丢键，`store.rs:520-522`
的 `string_or_drop`），不报错。场景：任务在有 tzdata 的宿主上运行中被杀，
store 搬到缺 tzdata 的宿主重启（该路径只筛 `status == "running"` 的任务，
`manager.rs:1478-1484`），恢复后即得到一个「在库、scheduled、无 `nextRunAt`」
的任务；装回 tzdata 也不会自动恢复它——这正是原条目要防的形态，故该约束对
恢复路径与 #1326 的未来调用方**仍然必要**。恢复面的这一折 `None` 只对
cron / delay 形状成立：once 任务在恢复时被直接删除并 `continue`
（`manager.rs:1537-1552`），从不进入该计算。

三源折叠（`ComputedRunAt::Undefined` 同时承载表达式非法 / 366 天内永不匹配 /
宿主缺 tzdata）仍然成立：create/update 面统一报同一句错，cron 形状的恢复面
统一折成无 `nextRunAt` 的 scheduled 任务。

用户可见面（接线 #1326 后）：在缺 tzdata-legacy 的宿主上用 legacy 别名 zone
建 cron 任务的用户**建不出任务**，看到的是同一句「schedule 不产生有效运行
时间」；同一台机器装上 tzdata-legacy（或 macOS）即与 TS 一致。不静默换时区、
不静默失败这两点与原条目一致，未变。不属于本条：有效性 / resolveCronTimezone
优先级、已解析 zone 的规则数值、金样计算格——同原条目。

`six_methods_replay_the_ts_gold` 逐步驱动 `methods::cron_create` 并把它返回的
`CronError::as_json()` 与金样 `create-errors` 第 8 步**逐字节**比对（不等即
红），即 `manager.rs:877-881` 抛错那一路的实际输出与 TS 完全一致。

`Ok(None)` 分支；`resolver_rejects_zones_the_host_tree_lacks` 用宿主树确实
没有的 zone 名钉死「缺文件 → 构造报错」通路。`cron-schedule` 侧的
`valid-timezone-accepts-all` / `offset-identifier-zone-unresolved` /
`zone-resolver-failure-returns-run` 负控不变，仍绑上述测试。

**本更正件的取证缺口（如实写，已挂 #1645）**：
1. create 侧抛错有金样 `create-errors` 第 8 步逐字节钉死；**update 侧的同一
   抛错（`manager.rs:1008-1012`）没有对应金样格**，本文对它的描述是读码推断
   （两处调用同一 `computed_next_run_at` 与同一错误串）。
2. 恢复面 `None` 分支（`manager.rs:1575-1600` 落盘 `nextRunAt: undefined`）
   **没有单测钉死**；`recoverInterruptedRuns` 在 TS 侧也无金样。现有 restart
   用例只覆盖 cron 形状（`src/pilotdeck-gateway/tests/cron_manager_native.rs:473`
   起的两个用例）；once 的删除分支（`manager.rs:1537-1552`）与 delay 的两类
   `None` 源（存量 `amount` 非法；`now + delay` 超 TimeClip 后格式化串重解析
   不构成合法日期，机制见 A8.3-CRON-ONCE-LOCALWALL-001-R1「范围」）都没有用例。
两缺口均不影响本更正件的结论方向（读码路径确定），按 P2-跟进「前置于 #1326
接线」登记在 #1645。
