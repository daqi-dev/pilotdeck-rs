# gateway-parity 冻结登记「发车制」（车次批处理）

人批 2026-11-05（本条即授权）；决策卡 `state/decisions-20261105-frozen-batch.md`。
本文件规定「一次冻结登记周期承载 N 张单」的编排。它是**新增的可改载体**，不改任何冻结字节：

| 文件 | 状态 | 本文件能否改它 |
|---|---|---|
| `FROZEN.md` 哈希列表 | 由 `check_frozen.py --write` 生成，只有车长执行 | 否，只规定「谁在什么时候跑一次」 |
| `FROZEN.md` 哈希列表以外的叙述 | 相对 merge-base 原字节冻结（`check_registration`） | 否 |
| `accepted-diffs.md` 与其哈希行 | 原字节冻结（`check_append_only`） | 否 |
| `diffs/README.md`、`diffs/` 既有条目、`frozen/` 既有事件 | 相对 merge-base 原字节冻结 | 否 |
| `specs/gateway-parity/BATCH-RELEASE.md`（本文件） | 新增文件，不在任何哈希清单内 | 是 |
| `scripts/gateway-parity/README.md` | 装置的 `DATA_FILES` 白名单成员，无哈希行 | 是（只放指针） |

机器规则以 `check_frozen.py` 为准；本文件与机器规则冲突时以机器为准并另开单修本文件。

## 1. 不变量（批处理不削减任何一条）

- **I1 一单一初始事件**：每张单在 `specs/gateway-parity/frozen/` 有一个本次新增的**初始**事件文件 `YYYYMMDD-<ID>.md`，四个字段（`Calibration-Evidence` / `Independent-Reviews` / `Approved-By` / `Approval-Basis`）各自非空。修复 / 再登记按 §5 追加 `-r<n>` 修订事件（同单续号，编号跨日续算），已合入的事件不可改。
- **I2 一单两评审**：`Independent-Reviews` 必须是两条**不同谱系、不同引用**的真实非作者评审；机器只查格式与去重，不把格式通过当审批通过。
- **I3 一单真实复算**：单的「机器判据」必须能在车次复算产物里逐条指到具体测试名 / 报告字段 / 负控日志。**不接受**用「整车复算 PASS」代替单的证据。
- **I4 判分语义零漂移**：车次只合并「登记与复算的次数」，不改阈值、分母、映射、归一化、差异账本。判分语义变更须另有明确批准，且按 §3 A4 限制上车。
- **I5 `--write` 唯一执行人**：车长（协调者），且在车次 HEAD 固定后只执行一次；§5 失败处置里追加事件后的重跑仍由车长执行，不计入「一次」。
- **I6 原字节冻结**：不得为了「一次搞定」而改 `FROZEN.md` 叙述、`accepted-diffs.md`、`diffs/` 既有文件或 `frozen/` 既有事件。

## 2. 名词与产物

- **车次（train）**：一次冻结登记周期。产物 = 一条集成分支 `chore/train-<YYYYMMDD>-<n>`（落为一个到 main 的 PR；owner 用 `chore` 是因为 `scripts/check-naming.py` 的分支白名单只认 `codex|docs|dev|chore|fix`，新增 owner 属改工具语义），含 N 个已收敛单的装置改动 + N 个初始事件文件（修复时另有 `-r<n>` 修订事件）+ 一次 `--write` 后的 `FROZEN.md` + 一次车次复算（失败处置会追加事件并重跑 `--write` / 复算，见 §5）。
- **单元（unit）**：一张单在车次内的增量（代码提交 + 事件文件 + 复算切片）。
- **车长**：协调者。负责组车、`--write`、复算、出车与失败处置，不承担单的实现。
- **冻结窗口**：从步骤 8 的登记提交（事件 + `FROZEN.md`）落地起，到合并完成、车次分支 HEAD 不再变化的时间段。步骤 3 固定的 HEAD 指**装置输入字节**（各单元代码提交），不是最终 PR HEAD；登记提交落地后不得再改装置输入字节或已写入的事件，任何变化按 §5 追加事件并重跑。
- **车次证据目录**：`_tmp/<YYYYMMDD>-frozen-train-<n>/`。失败后重跑**不换车次、不重走 §4.1**：在本车次目录下新建 `-r<k>/` 子目录存新产物（旧子目录原样保留作证据），k 递增不覆盖。**装置字节变化时**复用旧归档会响亮失败（`check_ruler.py` 的 apparatus / 基线哈希失配即 `ValueError`）；但**字节完全相同时机器会静默复用旧轮并重写 `ruler.json` 等汇总产物**——目录唯一性只能靠 §4.1 的占位动作保证，不能依赖机器报错。

## 3. 上车准入

必须上车：改动落在 `check_frozen.py:manifest_inventory()` 任一哈希行的文件（当前 28 行：`acceptance.md`、`normalization.md`、`accepted-diffs.md`；`common.A2_SCRIPTS` 18 件；`fixtures/session-calibration.json`、`fixtures/session-expectations.json`；`scripts/a5-19/` 5 件）。

**不用上车（登记成本为零）**：只新增 `specs/gateway-parity/diffs/<ID>.md`；只改 `scripts/gateway-parity/README.md` 等未登记文件；只改产品代码 / Rust 测试。

**账本例外**：`accepted-diffs.md` 虽在 28 行清单里，但它是**原字节冻结**的旧账本（`check_append_only` 强制）——车次不能改它，新条目走新增 `diffs/<ID>.md`，它自身的任何字节变化都不属于车次处置范围，按冻结程序另办。`FROZEN.md` 叙述同理。

一个单元可同车，当且仅当全部满足：

- **A1 已收敛**：两家非作者评审到无 P0/P1，评审引用可追（写进事件）。
- **A2 不打架且链可被机器接受**：单元之间文件面不冲突；同文件面的单元按顺序叠加成链，每个单元的增量 diff 可独立复核。**上车前须核该文件的整条链机器可接受**：不得回环、不得净零变化（同文件 `a→b→a` 会让新增事件变成陈旧边而被 `check_frozen.py --base` 判 FAIL）；不满足就改单或拆车，不能靠「顺序叠加」的措辞兜底。
- **A3 同语义域**：都在 `gateway-parity` 装置内。跨装置（`scripts/parity`、`scripts/ui-server-parity`）不得同车——三套登记按 #1089 各自独立。
- **A4 判分语义**：改变判分语义的单元必须已有明确批准记录并写进事件的 `Approval-Basis`；**未获批的判分语义变更禁止上车**（先写决策卡）。即使已获批，改判分语义的单元也**独占一车**，不与其它单混装。
- **A5 规则语义独占**：改 `check_frozen.py` 的**检查规则语义**（新增 / 收紧 / 放宽检查）的单元独占一车，不与其它单混装。这里的规则语义单指**只动本装置检查器、不需要三套同步**的情形。
- **A5b 三套同步的规则变更不组车**：改三套检查器共享函数的语义时，`frozen/README.md` 要求同步改三套、跑三套登记单测（`test_manifest.py` 比 AST，CI 在跑），拆成三个单装置车次会留下中间态红——这类单按原冻结批准程序**一次性原子交付**（三套各自登记、各自复算、同一合并），不适用车次机制。车次只承载本装置内、无需跨装置同步的单元。
- **A6 并发/生命周期不同车**：CLAUDE.md 人定「并发包不合成 PR」继续生效。
- **A7 规模 1–5 单元**：超过 5 拆车（冻结窗口越长，后续单被拖得越久）；全部单元都下车（0 单元）时取消车次，不发空车。

## 4. 组车步骤（车长按序执行）

1. **起车**（先占号再动作）：① 从 `origin/main` 建车次分支 `chore/train-<YYYYMMDD>-<n>`；② 在该分支提交一行 §9 占位（车次号 / 日期 / 状态=起车）；③ **把这条占位提交推到远端同名分支**——多车长可能在不同 worktree / 仓外 clone 里工作，只提交在本地互相看不见，占号以**远端先到者**为准；④ `mkdir _tmp/<YYYYMMDD>-frozen-train-<n>/` 原子占位证据目录。**mkdir 撞目录即该号烧毁**——自己的远端分支也要一起撤或改名，换号后把 ①–④ 整个循环重走，不能只换一半。
2. **上车**：按 A2 的文件面分组顺序把各单元分支的增量提交 `cherry-pick`/rebase 到车次分支；同一文件面的单元严格顺序，后一单元在前一单元落地后重放。
3. **固定 HEAD**：所有单元代码已提交、工作树干净（`git status --porcelain` 为空）。`--write` 要求登记文件的工作树字节等于 HEAD 字节，所以这一步不能省。
4. **写事件**：每单元一个 `frozen/<YYYYMMDD>-<单号>.md`（模板见 `frozen/README.md`）。`Change:` 的 old/new 分两种情况：**单一变化**（该文件在本车次只有一个单元改）old 取 `merge-base(origin/main)` 的 blob 完整 SHA256、new 取当前树；**同文件多单元**按落地顺序形成 `a→b→c` 唯一链——链首单元 old 取 merge-base 的 blob，后续单元 old 取前一单元落地后的树摘要（即前一单元 new）、new 取本单元落地后的树。新增文件 old 用 `-`，删除用 new `-`。两条边共用同一个 old 会被机器判重复边而 FAIL。
5. **一次 `--write`**：`python3 -I scripts/gateway-parity/check_frozen.py --write`（车长执行；`--write` 不能与 `--base` / `--print-ledger` 组合）。
6. **自检**：`check_frozen.py`（无 `--base`）、`check_frozen.py --base origin/main`、`test_safety.py` 全过；装置目录无 `__pycache__`。
7. **一次车次复算**：在车次 HEAD 跑一次全量真实复算（本装置当前口径：`check_ruler.py` k=5 + E1 `--suite calibrate`），产物落车次证据目录。每单元从这份产物摘自己的判据切片，写进事件的 `Calibration-Evidence` 与单的证据文件。多车次 / 多装置同时复算共用 `/tmp/pdrs-parity.lock`，但两个入口的等锁能力不同：`check_ruler.py` 一次复算在**同一把锁里串 6 轮**（单轮 timeout 上限 900 s、默认 180 s，整程无机器封顶），等锁默认 600 s、可用 `--lock-timeout` 调大；E1 `--suite calibrate` 的等锁**硬编码 30 s 且无旗标**，并行时只能错峰。其它装置同样抢这把锁，且合法持锁时间可能更长：`scripts/parity`（A1）、`cli-parity`（整批）、`fe-parity`（裸 `mkdir /tmp/pdrs-parity.lock` 形态）、`scripts/ui-server-parity`（`calibrate.sh` 26 遍采集 + 两轮 `check_ruler`，很可能是最大竞争者）。`--lock-timeout` 应按最大竞争者持锁时间设置。等锁超时按失败处置（换证据目录重跑），不改判据。**楔锁**：等锁超时先读 `owner.json`——带 `cleanupPending` 的锁机器永不自动接管（原持有者可能被硬杀或断电），不得当作陈旧锁循环重试。确认孤儿要按**本装置真实工件**读：`<车次目录>/cur/processes.json` 里每条的 `processGroup`（每次 start 增量落盘，硬杀路径下它是唯一来源）、`run.json` 的 `audit.ownedGroupsRemaining` 与 `allStopped`（正常收尾路径）、`owner.json` 的 `cleanupPending` 列表（非硬杀失败清理时发布）。**键名别混**：本装置每进程 `cleanupAudit.remaining` 是 **bool** 不是列表；`audit.remaining` 是 cli-parity 的 schema，`isolation.json` 是 fe-parity 的产物。端口检查只作辅助（`run_round.py` 允许任意 28xxx，只扫默认 28791–28794 会漏掉改端口的孤儿）。再核锁内 `owner.json` 是否仍是原持有者（有没有别的装置正在持锁）——证据不足就**保留锁、把车次挂起**，不赌。确认无人持有后，再由人明确授权删锁。另注意 `common.MAX_AGE = 2400 s`：**裸 `mkdir` 形态**的竞争者（fe-parity）没有 `owner.json`，机器按 mtime 判过期，超过 2400 s 会被**自动接管**——那不是等锁超时，而是抢走仍存活持有者的锁；遇到裸目录锁要么等它退出，要么先核实持有者已停。复算收尾核对 `ruler.json` 的 `lock_takeovers` 为空（有接管即说明本次编排撞锁，需记录）。
8. **提交登记**：事件文件 + `FROZEN.md` 作为一个独立提交（例：`chore(frozen) 车次 <n>：N 单登记`），提交信息逐个列单号。此后进入冻结窗口。
9. **出车**：PR 正文列单元表（单号 / 改动文件 / old→new 摘要 / 两家评审引用 / 复算切片路径），过常规合并闸门（两家非作者覆盖当前 head；登记正确性按 §6 增量复核）后入 merge queue。

## 5. 失败处置

- **F1 上车前未收敛**：该单元不上车，其余照常发车；下车单重挂下一车，不阻塞整车。
- **F2 上车后、固定 HEAD 前单元自检红**：指的是 §4.3 固定 HEAD 之前（工作树尚可改）各单元自己的测试与装置自检。能定位到单文件就把该单元摘掉后重排；定位不到就整车挂起（`state/board.md` 记缺口）。
- **F3 已 `--write` / 已推送后发现问题**：**不改写已合入的事件**（append-only 只约束 merge-base 已有事件；车次内未合入的事件可改写或摘掉，见 F4）。分两种：
  - **普通修复**（判分语义未变）：① **先提交修复、工作树干净**，固定新的装置输入 HEAD（`--write` 要求登记文件工作树字节等于 HEAD，未提交会报 `--write source differs from HEAD`）；② 追加修订事件 `YYYYMMDD-<单号>-r<n>.md`（**文件名必须以八位日期开头**，否则 `EVENT_NAME` 判非法；old 取修复前的树摘要、new 取修复后的树；同单续号、跨日续算）——若这次修复把该文件恢复成 merge-base 字节（净零，如 `a→b→a`）或形成回环，链会失效，须按下面回滚分支同法收拾车次内未合入事件；③ 重跑 `--write`、§4.6 与 §4.7（装置字节已变，旧复算不可复用——在本车次目录下新建 `-r<k>/` 子目录重跑，旧子目录保留，切片更新）。
  - **触及判分语义 / 需回滚该单元**：整车停；回滚用**新提交**（不 force push）。回滚必须把机器边一起收拾，否则 `check_frozen.py --base` 必然 FAIL（链从 merge-base 起算，机器不会自动消解）：
    - **按 `Change:` 行整理该单元未合入的事件**（append-only 只约束已合入事件）：一个事件可同时登记多个文件，整份摘掉会让同单元其它文件缺边而 FAIL——只删失效 / 净零 / 回环那几行边，仍有效的其它文件行保留或按新树重建；**只有整个单元退出车次（所有行都失效）时才摘整份事件**（事件的 `Change:` 行不能为空）；
    - 若同一文件上还有**后续单元**，把它们重放到回滚后的树上并重建各自的 `Change:` 边——中间断一环，后续边全部失效；重放后的单元坐标变了，须**增量重审**并更新其 `Calibration-Evidence` 切片；
    - 三种失败形态都要靠「摘 / 改未合入事件」消解：回滚该文件**唯一**单元 → `old==new` 且残留边被判 stale；回滚**最后一个**单元（`a→b→c` 回到 `b`）→ 残留 `b→c` 被判 stale；回滚**中间**单元 → 后续边**断链**。都不改已合入事件。
    收拾完重跑 `--write`、§4.6、§4.7，其余单元在新 HEAD 重跑复算后再出车。
- **F4 rebase / 队列更新 / 冲突解决（含无冲突重放）**：处理完一律比较 `merge-base(origin/main)` 与每个登记文件的当前摘要——**只要 merge-base 或任一登记文件字节变了就重新登记**，不要只在「有冲突标记」时才动作：无冲突重放同样会换 base、换装置字节，旧事件链不再从新 base 出发、旧复算也不再对应新树。触发后按序做（**先修清单与边、再自检**，否则 §4.6 会在旧 `FROZEN.md` 与旧事件链上先卡住）：① 把重放 / 解冲突结果**提交、工作树干净**（`--write` 要求工作树字节等于 HEAD）；② 按新摘要**重建受影响的 `Change:` 边**——车次内尚未合入的事件可改写，已合入的事件不可改（另开 `-r<n>` 事件）；③ 重跑 `--write`；④ 跑 §4.6 自检（`check_frozen` 无 `--base` / `--base origin/main` / `test_safety`）；⑤ **在本车次目录下新建 `-r<k>/` 子目录重跑 §4.7**（旧产物的装置字节摘要已失配、不可复用；不换车次、旧子目录保留），更新受影响单元的 `Calibration-Evidence` 与切片；⑥ 变化了的单元做**增量重审**（评审对象变了）；⑦ 把事件 + `FROZEN.md` 作为登记提交落盘，**对最终 HEAD 再跑一次 §4.6**。
- **F5 同一处修 3 次不过**：按 CLAUDE.md 挂起该项，其余单元照常出车。

## 6. 评审强度（不降，只换聚合粒度）

- 每单元仍是**两家非作者**，评审对象是该单元的增量 diff；两份引用写进事件，机器校验两条不同谱系、不同引用（只校格式，不校内容）。
- 车次 PR 的闸门只增加**登记正确性**增量复核，四项：① 单元 diff 与已评审 head 逐字节一致（`git diff` 相同，防止评审后偷改）；② 事件 `Change:` 的 old/new 与树摘要一致；③ `FROZEN.md` 行由 `--write` 生成（重跑 `--write` 应无差异）；④ 每个复算切片可点开且指向真实产物，事件里记该产物文件的 sha256，复核时比对确认冻结窗口内未被后续运行改写；⑤ 车次内 N×2 条评审引用**两两互不相同**（跨事件去重：机器只在单个事件内查重，把单元 1 的评审引用复制进单元 2 能全绿；同一引用出现在两个单元即视为该单元未被评审，退回补审）。这**不是**重审语义。
- **人复核不因上车而免除**：每单元仍走原有冻结批准程序（独立 issue / 理由 / 真实数据复算 / 两家非作者评审 / 人复核）；`frozen/README.md` 的「机器通过不代表人签字」继续有效。事件的 `Approved-By` 要如实写明状态——已签字、还是按决策分级标「AI 代批，待人复核」——不得用车次的机器绿或两家评审冒充人签字。
- 判分语义变更、检查规则语义变更仍需人复核 / 签字；车次不改变这一点。
