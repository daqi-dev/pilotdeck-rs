`_guard.run_entry` 原先在 `main()` 正常返回时直接 `raise SystemExit(code)`。CPython 把
`SystemExit(None)` 与 `SystemExit(False)` 都折成进程退出码 0（任务书「现场事实」原始输出：
`raise SystemExit(None)` → 0，`raise SystemExit(False)` → 0），所以一个忘记返回状态、或返回
`False` 的入口会被下游当成 PASS。本次只改这条成功路径：`None`/`False` 折到 2，其余值原样
传回；失败路径 `raise SystemExit(code)` 与 `_failure` 各策略不动。

必须用 `is` 而不是 `==`：`0 == False` 为 True，用等号会把合法整型 0 错折成 2；`0 is False`
为 False，整型 0 原样通过。`True` 也原样（`SystemExit.code` 为 True，进程退出码按 CPython 为 1）。
这条分支在当前 10 个入口的可达路径上不可达：它们的 `main()` 今天都返回整型（任务书现场
grep 的 10 个 `run_entry` 派发行），因此不改变任何现有入口的退出码或 JSON 形状。

并列测试只新增两个方法：子进程级用真实 `session_domain.py` 派发验证 `return None` /
`return False` 得 rc=2；进程内验证 `run_entry` 的 `SystemExit.code` 映射（None/False→2；
0/1/2/3/True 原样）。现有 AST 断言（入口 `__main__` 恰为 `run_entry(main, policy)`、`-I`
先于其它标准库 import、无私有 verifier）不动。两个 fixture 的 9 处成功路径锚
（7 个 `*-normal-exit-zero` 与 `guard-main-exit-zero`/`session-cli-exit-zero`）随成功路径
旧文本同步，变异语义仍是“成功路径折回 0”，见 `anchor-updates.md`。

不改阈值、分母、比较器、归一化、场景、锁协议、判分语义；`FROZEN.md` 与
