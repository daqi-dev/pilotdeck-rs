## 类别

bug（per-session 目录回收时机），登记为已接受差异（人批记录见「批准记录」）。基线的 `close()`
当下即删 per-session 临时目录；端口等迟到握手落地 / 握手超时之后的 detached cleanup 才删，
极端情况下（运行时在清理跑完前被拆除）残留。修复（`close()` 即删）属产品判断，#1751 人拍选项 A
暂不执行，留作后续可选优化单。

本条与 `specs/gateway-parity/diffs/A6.5-MCP-SESSION-DIR-LIFETIME-001`（及其更正 `-R1`）为
**同 ID 跨套登记**：同一差异在 gateway-parity 账本与本（阶段 C parity）账本各一条，事实同源
（同一组探针与实测），本条按本套口径书写。

## 基线依据

固定基线 `resources/PilotDeck`（cc7c4e65，Node v22.22.0，`@modelcontextprotocol/sdk` 1.29.0）。
`src/mcp/client/McpClient.ts:361-377` 的 `close()`：`await this.client?.close()` 后置
`status = "idle"`，随后同步 `rmSync(this.perSessionDir, { recursive: true, force: true })`——
删除是 `close()` 的同步步骤，返回前必然完成。

实测（真 TS 探针 `_tmp/20261106-issue-401/probe/probe-dispose-inflight.mts`：`slow-mcp-server.mjs`
把 `initialize` 延迟 3 s，握手在飞时调 `close()`，`PILOTDECK_SESSION_TMPDIR` 指到临时目录；原始输出
`_tmp/20261106-issue-401/probe/probe-dispose-inflight.out`，原样重跑
`_tmp/20261106-1751-1754-diff/ts-probe-dispose-inflight.out`，Node v22.22.0）：

```text
close() returned in ms = 1
dir exists after close = false
child alive after close= true
PROBE RESULT = {"closeMs":1,"closeWaitedForHandshake":false,"dirRemovedAtClose":true,"childAliveAtClose":true}
```

即 TS 在 `close()` 当下就删目录（`dirRemovedAtClose:true` 一行）。

## Rust 行为

`src/pilotdeck-gateway/src/runtime/mcp/client.rs`（行号按 2026-11-07 origin/main 现核）：`close()`
（`:1245`）置 `epoch += 1`、清 `list_tools_cache`、`retire_connection()` 后，只对**当时已登记**且
`wait_on_close` 的清理 `await_cleanup`（`:1267`）；`spawn_cleanup`（`:603`）才把「关连接 + 删目录」
登记进 `State.cleanups`。在飞握手的目录此时尚未登记（`PerSessionDirectory` 还在 `run_connect`
局部，构造于 `:903`）：等握手落定、走到 `:957` 的 `state.epoch != epoch` 分支才
`state.spawn_cleanup(… dir.remove() …)`；握手超时路径（`:915-932`）同理把目录交给 detached cleanup
（`DEFAULT_HANDSHAKE_TIMEOUT_MS = 10_000`，`:94`）。该 detached cleanup 先 `handshake.await`（`:924`）
等已超时的握手任务落定才 `dir.remove()`——握手任务本身不再受 10 s 超时约束，删除的上界是 SDK
`initialize` 的请求期限 `DEFAULT_REQUEST_TIMEOUT_MSEC = 60_000`（TS SDK `shared/protocol.js:12`，
Rust 侧镜像 `client.rs:95-96`；自握手起算，与 10 s 握手超时同起点并行）再加 close 升级窗口
（`wire.rs::escalate` `:617-634`：`CLOSE_GRACE` 2 s + SIGTERM + 2 s + SIGKILL，约 4 s）——最晚约在
握手起算 60 余秒后，不是 10 s。生产收尾还会把这条 detached cleanup **join 进来**：`dispose()`
（`client.rs:1277-1288`）对二次快照到的**全部**已登记清理 `await_cleanup`（不按 `wait_on_close`
过滤），`McpRuntime::stop()`（`runtime.rs:238-245`）走的正是 `dispose()`——「优雅拆除同步阻塞
上述窗口（最坏把宿主 shutdown 卡近 1 分钟）」**只对二次快照时已登记（即握手已超时）的清理成立**；
在飞（未超时）握手的 cleanup 尚未登记、不在二次快照（`client.rs:1279-1284`）里，`stop()` 不 join
它、立即返回（≤2 s，#1782 `tests/mcp_client.rs:1834-1837` 钉住），宿主随即退出则该握手任务被
drop、目录残留——目录残留**不只**发生在不走 `stop()` 的拆除点，走了 `stop()` 但落在在飞窗口、
进程随后退出的拆除同样残留。

实测（探针 `probe_1751_close_during_inflight_handshake_keeps_session_dir`，源码
`_tmp/20261106-1751-1754-diff/rust-probe.patch`，命令
`cargo test --offline -p pilotdeck-gateway --test mcp_client probe_175 -- --nocapture --test-threads=1`
——过滤串 `probe_175` 同时选中 1751/1754 两探针，与该日志 `running 2 tests`、`19 filtered out`
一致，`--test-threads=1` 下顺序执行、输出混排，
原始输出 `_tmp/20261106-1751-1754-diff/rust-probe.log`）：`close()` 0 ms 返回时
`dir_exists_after_close = true`、500 ms 后仍 true；放行被闸住的 `initialize` 后迟到握手被判
`aborted`，目录才由 detached cleanup 删除（`dir_exists_after_gate_opened = false`）。

「目录最终会被删」只是**尽力而为**：`PerSessionDirectory::remove()`（`client.rs:555-560`）里
`spawn_blocking(remove_dir_all)` 的结果被 `let _ =` 丢弃，删除失败无日志无断言（如将死的子进程
仍在目录里新建文件致 `ENOTEMPTY` 时静默残留）；`wire.close()` 的 `escalate` 发完 SIGKILL **不等
子进程退出**（`wire.rs:617-634`），且只对**直接子进程 pid** 发信号、不杀进程组（`:630-631`），
孙进程无人回收。正常收尾（运行时存活到 detached cleanup 跑完且删除未失败）时目录最终会被删；
运行时在清理跑完前被直接拆除则清理任务被 drop，目录残留在 `$TMPDIR`（未实测，见「机器判据」
缺口 ③）。

## 范围

仅 stdio 传输 per-session 临时目录（`--user-data-dir=` 临时目录）在 `close()` 期间的寿命，可观察差异
一处：`close()` 返回那一刻目录是否存在——基线 false、端口 true 的窗口是**在飞握手（未落定）**，或
**该次尝试的 detached cleanup（握手超时分支以 `wait_on_close=false` 登记的清理）尚未完成**（含
握手落定后的 `wire.close()` 升级窗口与 `remove_dir_all` 完成之前；r5 按评审 DS concurrency#1
扩宽）：两种情形下该目录都未以 `wait_on_close` 登记（`close()` 只等 `wait_on_close` 清理，
`client.rs:1259` 过滤），`close()` 不等它删、返回时目录仍在——「目录尚未登记进 `State`」不是
充分描述（超时分支登记的 detached cleanup 已在 `State.cleanups` 里，只是 `wait_on_close=false`）；
已连接的常规收尾路径两侧同为 false（端口的 `retire_connection()` 已把目录登记为 `wait_on_close`
清理、`close()` 等它删完，仓内 `tests/mcp_client.rs:940-941` 即此断言），「关闭已连接客户端」不
构成本条的分歧场景；握手以非超时原因失败（含 60 s 请求超时）落定后目录装入 `per_session_dir`、
同样被 `close()` 等到删完，收尾路径同理。**status 走向不在本条**：
`close()` 之后基线被迟到握手抬回 `ready`、端口保持 `idle` / `aborted`，已由本账本第 4 条
`handshakeClose`（郑达奇 2026-10-21 已批）登记，本条不重复主张。不含：目录内容与命名规则、
`reconnect` 路径旧目录回收、子进程回收时机（含「删目录与关子进程先后」的取舍）、握手中断后的
重连语义。

## 机器判据

- TS 金样：`_tmp/20261106-issue-401/probe/probe-dispose-inflight.mts` 与 `.out`（Node v22.22.0，
  关键行 `dirRemovedAtClose:true`）；原样重跑 `_tmp/20261106-1751-1754-diff/ts-probe-dispose-inflight.out`。
- Rust 复算：`_tmp/20261106-1751-1754-diff/rust-probe.log`（原件只读；复算另存新文件名，
  `rust-probe.patch` 只 apply 到一次性树；该日志 1751/1754 两探针输出混排，按
  `dir_exists_*` / `session_dir` 与 `depth=` 内容区分，不按行序切）。
- origin/main 耐用用例：`tests/mcp_client.rs::timed_out_handshake_keeps_its_directory_until_late_close_then_removes_it`
  （`:899`，正常已连接收尾时目录已删）、`registry_dispose_joins_retired_directory_after_cancelled_close`
  （`:1087`）、`dispose_during_an_in_flight_handshake_removes_the_session_directory`（`:1774`，PR #1782
  合入：`McpRuntime::stop()` 不栅栏在飞握手 + 迟到握手落定后 detached cleanup 最终删目录）。
  缺口：① 在飞握手时 `close()` 返回目录仍在的正控、② #1782 已以轮询至最终删除的形式钉住删除
  结果但「收尾返回时已删」的定值形仍缺、③ 拆除点分两态实测（`McpRuntime::stop()`：join 全部
  快照时已登记清理、阻塞上述窗口，「返回时目录已删」是**条件值**——仅当超时 cleanup 已在二次
  快照前登记且 `remove_dir_all` 未失败（`client.rs:555-560` `let _ =` 丢弃错误、失败静默残留）
  时成立，在飞未超时窗口 `stop()` 不 join、返回时目录仍在；runtime 直接 drop / 进程拆除：清理
  任务被 drop、目录残留），均仍缺，已开跟进单 #2233（前置于 A6.5 批次复核，实测按窗口分列）。
  对 `dispose()` 返回时的目录状态：
  **握手可并发落定**（闸未闸住、迟到握手可落在 `close()` 快照与 `dispose()` 二次快照之间）时是
  交错值、不立正负断言（分析见 gateway-parity 同 ID 条目「类别」末段及其 `-R1` 更正）；**闸住握手**
  （仓内测试一律用的 `wait_file` 闸）时退化为确定值，但确定窗口是 **`min(handshake_timeout_ms,
  60 s)`**——截断它的是 SDK `initialize` 的 **60 s 请求超时**（`DEFAULT_REQUEST_TIMEOUT_MSEC
  = 60_000` 硬编码、不可由 options 延长：`client.rs:95-96` 定义、`:378-388` initialize 固定传
  该值、`wire.rs:552` 到点 `Err("Request timed out")`、`client.rs:355-364` 失败后转后台
  `wire.close()` 并立即返回），**不是握手超时**：闸住超过 60 s 后 initialize 请求超时、握手以失败
  落定（非超时分支），目录装入 `per_session_dir`（`client.rs:982`），`dispose()` 里 `close()` 的
  `retire_connection()` 把它登记为 `wait_on_close` 清理并等它删完——**返回时目录已删**（r5 实测
  探针 `_tmp/20261107-2225-r5/probe.log`，补丁与命令同目录：闸 70 s、`handshake_timeout_ms` 钉
  120 s，`start` 以 `MCP error -32001: Request timed out` 失败、目录仍在；`dispose()` 实测 0 ms
  返回、`dir_exists_after_dispose=false`——60 s 失败路径的后台升级已先行完成，紧随失败点调
  `dispose()` 时至多再等其剩余升级窗口（≤4 s））。故「`dispose()` 返回时目录必在」只在 initialize
  发出起 **60 s 内**成立（#1782 把 `handshake_timeout_ms` 钉到 120 s 只用于抑制 10 s 超时分支、
  不延长此窗口，`tests/mcp_client.rs:1808`）；期间目录未登记、二次快照不含该目录的清理（只含
  `close()` 刚登记的空 retired cleanup），`dispose()` 立即返回（≤2 s）。另一侧到点是握手超时先于
  60 s 触发（`handshake_timeout_ms < 60 s`，如默认 10 s，`client.rs:94`）：超时分支把 detached
  cleanup 登记、二次快照 join 它、阻塞到握手落定（最坏近 1 分钟），断言随机器负载翻转。#2233 立
  正控须把闸内时长钉在 `min(handshake_timeout_ms, 60 s)` 以内、且 `dispose()` 在 initialize 发出
  60 s 内调用，勿继承「一律不可断言」的过强理由。
